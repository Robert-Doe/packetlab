Module 10 — Tutorial

Goal: understand exactly why your whole household shares one public IP, and exactly why nothing from the internet can reach your laptop unless you explicitly allow it — as traced mechanisms, not as things you've just been told are true.

Step 1 — run the simulation

cd module-10-firewalls-and-nat
python nat_firewall_sim.py
Expected: 4 scenarios. Two internal hosts get the same-looking traffic PAT'd to the same external IP but different ports (Scenario 1); a legitimate reply gets NAT'd back and allowed (Scenario 2); a completely unsolicited inbound connection is dropped because no NAT/state entry exists for it (Scenario 3); and a spoofed-source inbound packet reusing a real external port is STILL dropped, because the firewall checks the full connection tuple, not just "is this port in use" (Scenario 4).
node nat_firewall_sim.js
Byte-identical output (verified during this module's build).

Step 2 — map it to real iptables/nftables syntax

Read iptables_reference.html fully. Find the single MASQUERADE rule that implements Scenario 1's behavior, and the two-line ESTABLISHED,RELATED + default-DROP pair that implements Scenarios 2-4's behavior.

Step 3 — confirm it against your own home router

Go to your home router's admin page (or pfSense/OPNsense from Module 09's virtual lab). Find the port forwarding section. Notice it always asks for BOTH an external port AND an internal IP:port — that's you manually creating a permanent NAT+firewall entry, exactly like iptables_reference.html's DNAT example, for a connection that would otherwise be dropped by Scenario 3's default behavior.

Step 4 (if you have Linux available) — the real rules, for real

If you have access to a Linux VM (your Module 09 virtual lab client VM works), try:

sudo iptables -t nat -L -n -v
sudo iptables -L FORWARD -n -v
Expected: if this machine does any NAT/forwarding at all, you'll see real rule counters incrementing as traffic matches them — the exact same MASQUERADE and ESTABLISHED,RELATED rules from Step 2, with real packet/byte counts next to each rule showing it actually firing.

Exercises before Module 11

  1. Add port exhaustion. A real NAT table has a finite port range (roughly 1024-65535 usable for PAT). Modify nat_firewall_sim.py/.js so next_external_port wraps or raises an error once it hits 65535, and explain why a home network with thousands of simultaneous connections (smart TVs, phones, IoT, all day) could theoretically exhaust this.
  2. Implement UDP's looser state tracking. Real firewalls track UDP "connections" too, despite UDP having no handshake (Module 07) — usually via a short idle timeout instead of FIN/RST detection. Add a simulated timeout to conn_state entries and show a UDP-style reply arriving just after the timeout gets dropped, even though it's a legitimate reply.
  3. Write the actual DNAT rule for your Module 09 lab. In your pfSense/OPNsense virtual lab, set up a port forward from an external port to a client VM's web server (Module 08's http_server_from_scratch.py makes a perfect target). Confirm the forward works, then look at pfSense's own Diagnostics → States page — you should see connection state entries exactly matching Scenario 2's ESTABLISHED concept, listed by pfSense itself.
Before Module 11: you should be able to explain, from memory, why port-scanning a home router from the internet finds almost everything closed, and why a game console or torrent client sometimes needs "port forwarding" enabled to work properly (hint: it needs UNSOLICITED inbound connections to reach it, which Scenario 3 shows is blocked by default). Module 11 builds a real WireGuard VPN tunnel — a different, deliberate way of reaching into a private network from outside, built on cryptographic authentication instead of the "did we see it leave first" state-tracking this module covered.
