Module 10 — Deep Theory: iptables Commands and Conntrack, Explained From Zero

1. Command-by-Command: Reading Real iptables Rules

sudo iptables -t nat -L -n -v

What each flag means: -t nat selects the NAT TABLE specifically — iptables organizes rules into separate tables by purpose (filter, the default, for allow/block decisions; nat for address/port translation; mangle for packet header modification), and without -t nat you'd see the (different) default filter table instead. -L means "List" the rules in the selected table. -n means "numeric" — show IP addresses and ports as raw numbers rather than resolving them to hostnames/service names (same reasoning as Module 07's netstat -n: faster, and avoids DNS lookups potentially leaking your activity or simply timing out). -v means "verbose" — additionally show packet and byte COUNTERS for each rule, letting you see exactly how much traffic has actually matched each rule since the counters were last reset.

sudo iptables -L FORWARD -n -v

What it does differently: lists only the FORWARD chain specifically (rather than every chain in a table) — recall from iptables_reference.html that FORWARD is where a router's allow/block decisions for traffic passing THROUGH it (not addressed to the router itself) actually happen — exactly the chain Scenario 3/4's DROP behavior in nat_firewall_sim.py models.

Why does sudo matter here specifically? Reading or modifying firewall rules is a privileged kernel operation on every major OS — an unprivileged process being able to READ your firewall rules could leak security-relevant information about what's exposed (mapping your attack surface for free); being able to MODIFY them without privilege would be a critical security hole. This is the same privilege-boundary reasoning Module 00c covered for systemd, and Module 03 covered for the ARP cache — a recurring pattern throughout this course.

2. MASQUERADE vs. SNAT: A Real, Precise Distinction

iptables_reference.html's MASQUERADE rule is technically a SPECIAL CASE of the more general SNAT (Source NAT) target. Plain SNAT requires you to specify the EXACT external IP to translate to (--to-source 203.0.113.7) — appropriate when your external IP is static and known in advance. MASQUERADE instead automatically uses WHATEVER IP the outbound interface currently has, looked up dynamically at the moment each packet is processed — essential for a home router whose ISP-assigned public IP can change (DHCP-leased, common for residential internet) without requiring you to update the firewall rule every time it does.

3. Connection Tracking (conntrack), Formally

The ESTABLISHED,RELATED match Module 10's reference covers relies on Linux's conntrack subsystem — a kernel-level table tracking the state of every connection passing through the firewall, keyed by the full 5-tuple (source IP, source port, destination IP, destination port, protocol). This is the REAL implementation of exactly what nat_firewall_sim.py's conn_state dictionary models in simplified Python.

conntrack stateMeaning
NEWThe first packet of a connection conntrack hasn't seen before
ESTABLISHEDPart of a connection where conntrack has seen traffic in BOTH directions
RELATEDNot literally part of an existing connection's 5-tuple, but logically associated with one (e.g., an FTP data connection related to an existing FTP control connection, or an ICMP error message related to an existing UDP/TCP flow)
INVALIDA packet conntrack cannot associate with any known connection state at all, sometimes indicating a malformed or deliberately crafted packet
Comprehensive exam framing: "Explain why the RELATED state exists as a category distinct from ESTABLISHED, using FTP as a concrete example." Active-mode FTP uses TWO separate TCP connections: a control connection (commands) and a SEPARATE data connection (file transfer), with the data connection's port negotiated dynamically WITHIN the control connection's own traffic. A naive stateful firewall tracking only exact 5-tuples would have no NEW-connection-permitting reason to allow the data connection's initial SYN — it doesn't match any existing connection's 5-tuple. RELATED specifically exists so a firewall can inspect application-layer protocol behavior (via a "connection tracking helper" module) and recognize "this new connection attempt was legitimately negotiated by an existing, trusted connection," permitting it without requiring a static, permanently-open rule for the entire dynamic port range.

4. Port Exhaustion, With Real Numbers (Exercise 1)

The dynamic/private port range (per IANA) is 49152-65535 — 16,384 ports. Many NAT implementations additionally use some of the "registered" range (1024-49151) for outbound PAT, giving roughly 64,000 usable ports total per external IP. A single Netflix 4K stream, a few IoT devices with frequent cloud check-ins, several browser tabs each opening multiple parallel connections, and background OS/app update checks can EASILY have several hundred simultaneous connections active in a typical household — nowhere near exhausting 64,000, but the math matters at a different scale: a LARGE ORGANIZATION behind a single NAT gateway (thousands of employees, each with dozens of simultaneous connections) can genuinely exhaust available ports, which is one real motivation for technologies like Carrier-Grade NAT using additional IP blocks specifically to expand available port pools beyond one IP's ~64,000.
