iptables/nftables Reference

How nat_firewall_sim.py's simplified model maps onto a real Linux firewall's actual chains. pfSense/OPNsense (Module 09) run on a BSD firewall (pf) with different syntax but the identical conceptual pipeline described below.

The chains a packet actually passes through

ChainWhen it runsWhat it's for
PREROUTINGImmediately on arrival, before routing decisionDNAT (destination NAT — e.g. port forwarding) happens here
INPUTAfter routing, if the packet is destined for this machineThe stateful ALLOW/DROP decision for traffic addressed to the firewall itself
FORWARDAfter routing, if the packet is passing through to another hostThe stateful ALLOW/DROP decision for traffic routed between networks — this is where nat_firewall_sim.py's Scenario 3/4 DROP decisions live on a real router
OUTPUTFor packets originating from this machine itselfRarely restrictive on a home router; matters more on a server you're hardening
POSTROUTINGJust before leaving an interfaceSNAT/MASQUERADE (source NAT) happens here — this is where Scenario 1's PAT translation actually occurs on a real Linux router

The exact rule that makes your home network's PAT work

# iptables (older, still extremely common)
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE

# nftables (modern replacement)
nft add rule nat postrouting oifname "eth0" masquerade

MASQUERADE/masquerade is a special case of SNAT that automatically uses whatever IP the outbound interface currently has — this is precisely what nat_firewall_sim.py's outbound() method does by always substituting self.external_ip, and it's why this exact one-line rule is almost universally what turns a bare Linux box into a home-router-style NAT gateway.

Stateful matching — the rule behind Scenario 2/3/4

# iptables
iptables -A FORWARD -m state --state ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -j DROP

# nftables
nft add rule filter forward ct state established,related accept
nft add rule filter forward drop

The first rule is EXACTLY nat_firewall_sim.py's inbound() check: allow only if this packet matches a connection state ("ct state established" = "this is return traffic for a connection we started"). The second rule is the default-deny fallback — literally Scenario 3's "no matching state, dropped" behavior, written as an explicit rule instead of implicit script logic.

A DNAT (port forwarding) rule, for comparison

# iptables -- forward external port 8080 to an internal web server
iptables -t nat -A PREROUTING -p tcp --dport 8080 -j DNAT --to-destination 192.168.1.50:80
iptables -A FORWARD -p tcp -d 192.168.1.50 --dport 80 -j ACCEPT
This is the ONE deliberate exception to Scenario 3's "unsolicited inbound is always dropped" rule — a port forward is you explicitly telling the firewall "actually, let inbound connections to THIS specific port reach THIS specific internal host, even with no prior outbound connection." Every home router's "port forwarding" admin page setting compiles down to a rule shaped exactly like this.
