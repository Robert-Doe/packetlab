Module 10 — Exam Practice

Answer out loud before revealing each answer.
Q1. What does the -t nat flag select, and what would you see instead if you ran iptables -L -n -v without it?
A: -t nat selects the NAT table specifically, which contains PREROUTING/POSTROUTING rules for address/port translation. Without -t nat, iptables defaults to the `filter` table -- a different table entirely, containing INPUT/OUTPUT/FORWARD allow-or-block rules rather than any translation rules, so omitting the flag would show completely different rule content, not an error.
Q2. Precisely distinguish MASQUERADE from plain SNAT, and explain why a home router specifically needs the former.
A: SNAT translates to an explicitly, statically specified external IP (--to-source X.X.X.X). MASQUERADE automatically uses whatever IP the outbound interface CURRENTLY has, looked up dynamically per-packet. A home router's ISP-assigned public IP is typically DHCP-leased and can change without notice -- MASQUERADE handles this automatically, while SNAT would require manually updating the rule every time the IP changed, which is impractical for a residential connection.
Q3. Define the four conntrack states (NEW, ESTABLISHED, RELATED, INVALID) precisely.
A: NEW: the first packet of a connection conntrack hasn't seen before. ESTABLISHED: part of a connection where traffic has been observed in BOTH directions. RELATED: not literally part of an existing connection's exact 5-tuple, but logically associated with one (e.g. an FTP data connection tied to an existing FTP control connection). INVALID: a packet conntrack cannot associate with any known connection state at all, sometimes indicating malformed or deliberately crafted traffic.
Q4. Using active-mode FTP as the example, explain precisely why the RELATED conntrack state needs to exist as a category distinct from ESTABLISHED.
A: Active-mode FTP uses two separate TCP connections: a control connection and a separate data connection whose port is negotiated dynamically WITHIN the control connection's own traffic. A firewall tracking only exact 5-tuples has no basis to permit the new data connection's initial SYN -- it doesn't match any existing connection's 5-tuple, so it would look exactly like an unsolicited new connection. RELATED lets a firewall (via a protocol-aware connection tracking helper) recognize this new connection attempt was legitimately negotiated by an already-trusted existing connection, permitting it without requiring a static rule leaving the entire dynamic port range permanently open.
Q5. Roughly how many usable outbound ports does a single external IP provide for PAT, and why does this number matter more for a large organization than a typical household?
A: Roughly 64,000 usable ports (the dynamic/private range plus commonly also part of the registered range). A typical household, even with many devices and simultaneous connections, rarely approaches even a small fraction of this. A large organization with thousands of employees behind a SINGLE NAT gateway, each with dozens of simultaneous connections, can genuinely approach or exhaust this limit -- a real motivation for technologies like Carrier-Grade NAT, which expand available port pools using additional IP blocks.
Q6. Why does reading (not just modifying) iptables rules require root/sudo privileges?
A: Firewall rules reveal security-relevant information about a system's exposed attack surface (what's allowed through, what NAT/port-forward mappings exist) -- allowing any unprivileged process to read this would let malware or an unprivileged attacker map out a system's defenses for free, without needing to actually probe from outside. This mirrors the same privilege-boundary reasoning applied to Module 03's ARP cache and Module 00c's systemd unit management -- security-relevant kernel state generally requires elevated privilege to even READ, not just modify.
Q7. Synthesis: connect conntrack's RELATED state to Module 12's WPA2 handshake trust model. What's the common underlying theme about "trusting something because it's connected to something already trusted"?
A: Both mechanisms extend trust transitively from an already-established, verified context rather than requiring independent verification of the new thing from scratch. RELATED trusts a new connection because it was legitimately negotiated within an already-ESTABLISHED, trusted connection's own traffic. Module 12's PTK derivation trusts the resulting session key because it's derived from an already-shared PMK (established once, via the expensive PBKDF2 step) combined with fresh per-session nonces -- neither mechanism re-verifies identity/trust from absolute zero every single time; both build efficiently on a previously-established trust anchor. The common theme: bootstrapping new, narrower trust decisions from a broader trust relationship already established, rather than paying the full verification cost repeatedly.
