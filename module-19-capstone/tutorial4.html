1. run_checker()'s Completeness Math, Traced Completely

total_checks = 4
checks_with_issues = len({
    "network" if any("VLAN" in i for i in all_issues) else None,
    "monitoring" if any("SIEM" in i or "detector" in i for i in all_issues) else None,
    "vulns" if any("emediat" in i or "assessment" in i for i in all_issues) else None,
    "incident" if any("Incident report" in i for i in all_issues) else None,
} - {None})
completeness_pct = round(100 * (total_checks - checks_with_issues) / total_checks)

Fully traced: a manifest with exactly 2 categories of issues

Suppose all_issues contains:
  "VLAN 'Lab' declares isolation rule ... but no matching firewall rule..."
  "Only 1 detector type(s) active..."
  (network AND monitoring both have issues; vulns and incident do not)

Building the SET literal, element by element:
  "network" if any("VLAN" in i for i in all_issues) else None
    -> "VLAN" appears in the first issue string -> "network"
  "monitoring" if any("SIEM" in i or "detector" in i for i in all_issues) else None
    -> "detector" appears in the second issue string -> "monitoring"
  "vulns" if ... else None -> no issue contains "emediat" or "assessment" -> None
  "incident" if ... else None -> no issue contains "Incident report" -> None

Set literal: {"network", "monitoring", None, None}
  -- as a SET, duplicate None values collapse to just one None
  -> {"network", "monitoring", None}

Subtract {None}: {"network", "monitoring", None} - {None} = {"network", "monitoring"}

checks_with_issues = len({"network", "monitoring"}) = 2

completeness_pct = round(100 * (4 - 2) / 4) = round(50.0) = 50%
Why build a SET of CATEGORY NAMES (deriving each one from a substring search over the issue MESSAGES) rather than just counting len(all_issues) directly? A single CATEGORY (say, "vulnerabilities") could produce MULTIPLE separate issue strings — e.g., three DIFFERENT unremediated findings would each generate their own line in all_issues — but this should count as ONE category being incomplete for the completeness PERCENTAGE, not three. Using a SET (which automatically deduplicates) keyed by CATEGORY, rather than counting raw issue lines, correctly answers "how many of the 4 BROAD AREAS have AT LEAST ONE problem," which is the actually meaningful completeness metric — mirroring exactly how a real project-completeness review would be summarized (4 broad requirement areas, each either "met" or "has at least one gap"), not a raw defect count that could be inflated by one area having many small issues while another has none.

for vlan in vlans:
    for rule in vlan.get("isolation_rules", []):
        key = (rule["from"], rule["to"], rule["action"])
        if key not in firewall_pairs:

Fully traced: why a DESIGNED isolation rule with no matching firewall rule gets flagged

Manifest declares, under vlans[0] (name="Lab"):
  isolation_rules: [{"from": "Lab", "to": "Main", "action": "BLOCK"}]

Manifest ALSO declares, under network.firewall_rules:
  [{"from": "Main", "to": "Lab", "action": "ALLOW"}]   <- notice: the
    OPPOSITE direction was actually implemented, not the one that was
    DESIGNED

firewall_pairs = {("Main", "Lab", "ALLOW")}

Checking the Lab VLAN's isolation_rules:
  key = ("Lab", "Main", "BLOCK")
  key not in firewall_pairs?  ("Lab","Main","BLOCK") vs the SET
  containing only ("Main","Lab","ALLOW") -- NOT a match (different
  tuple entirely) -- ISSUE FLAGGED:
  "VLAN 'Lab' declares isolation rule Lab -> Main (BLOCK) but no
   matching firewall rule was found -- the plan isn't enforced."

This exact mechanism directly implements Module 09's own asymmetric Main/Lab design (Section 2 of that module's own tutorial4.html) — the checker isn't merely confirming "SOME firewall rule exists somewhere," it's confirming the EXACT (from, to, action) triple you DESIGNED was ACTUALLY implemented, catching precisely the kind of subtle direction-reversal mistake a human reviewer might miss on a casual read-through but a tuple-equality check catches immediately and precisely.

3. Why The 5 Rounds Are Ordered The Way They Are

RoundWhat it doesWhy THIS position in the sequence
1. RedCause a real incidentMust happen FIRST — there is nothing to detect, reconstruct, or remediate without a real, concrete incident having actually occurred
2. BlueDetect it via monitoring, BLIND to Round 1's specificsMust happen with your monitoring pipeline ALREADY built (Modules 14/15) — testing detection AFTER causing the incident (not before) is what makes this a genuine test of whether your OWN monitoring actually works, not a demonstration you already knew would succeed
3. ForensicsReconstruct from evidence ALONE (not memory)Deliberately performed with the FULL picture already known to you personally, specifically so you can COMPARE your reconstruction against ground truth and identify exactly where evidence was insufficient (Module 18's own "reconstructing from evidence alone is the actual skill being tested" framing, now given a real ground-truth answer key to check against)
4. RemediateFix it, then RE-ATTACK to confirm the fix worksMust come AFTER forensics specifically because you need the FULL understanding of what happened (Round 3's output) to know what to actually fix — remediating before fully understanding the incident risks fixing the wrong thing
5. Write it upProduce the actual incident report deliverableLast, because it SYNTHESIZES everything from all 4 prior rounds into the one artifact a real stakeholder would actually read — Module 18's own framing that "the technical timeline is the input, not the output" applies directly here
Comprehensive exam framing: "Why can't Round 4 (remediation) simply happen immediately after Round 1, skipping Rounds 2-3, if the goal is just to fix the vulnerability?" Because the CAPSTONE'S actual goal is not merely "have a secure network" — it's demonstrating the FULL, integrated skillset this course built: detecting an incident with your OWN monitoring (Round 2), and reconstructing it forensically from evidence alone (Round 3), are THEMSELVES the skills being validated, not optional steps on the way to remediation. Skipping them would mean the capstone only demonstrates "I can patch a known vulnerability," missing the detection-engineering and forensic-reasoning components that Modules 14, 15, and 18 specifically built toward — the ORDERING enforces that ALL of these skills get genuinely exercised, in the sequence a real security incident response process actually follows.

4. Round 2's Blinding — Why It's Methodologically Necessary

Why does the playbook specifically instruct "without looking at your Round 1 notes" for Round 2's detection test? This is a genuine, real EXPERIMENTAL CONTROL, directly connecting to Module 21's own research-methodology material (specifically its literature-review/ methodology framing of rigorous, falsifiable testing): if you consciously or unconsciously TAILOR your monitoring review toward what you KNOW you just did (rather than genuinely, independently checking what your pipeline's OWN detectors actually flagged), you risk a FALSE POSITIVE CONCLUSION about your monitoring's real effectiveness — believing it "worked" because you already knew what to look for, not because it would have genuinely caught the incident on its own. Blinding yourself to your own prior knowledge, as much as practically possible, is exactly the discipline that makes Round 2 an honest TEST of your monitoring rather than a confirmation exercise — precisely why the playbook frames "if nothing fired, that's a real, valuable finding" rather than treating a detection failure as something to work around or explain away.

5. Round 4's Verification Loop — "Mean It, Because You Just Verified It"

Precisely why re-running the EXACT SAME attack after remediation matters

Applying a fix (patching vsftpd, closing a port, adding a firewall rule) and simply ASSUMING it worked is exactly the "asserted, not verified" failure mode Module 09's own tutorial4.html Section 2 warned against (isolation must be "verified with an actual ping test, not just asserted"). Round 4's explicit instruction to RE-RUN Round 1's exact attack, and CONFIRM it now fails, applies that same empirical-verification discipline to remediation specifically — a fix that LOOKS correct on inspection (the right version number now shows in a config file, the right firewall rule now exists in a config) could still be wrong in a way only an actual re-attempt reveals (a typo in the rule, a service that didn't actually restart with the new config, a rule in the wrong chain per Module 10's own PREROUTING/FORWARD ordering lesson). Setting "remediated": true in your manifest is only HONEST once you've actually performed this verification — which is precisely why check_vulnerabilities() flags ANY finding lacking this field, treating an un-remediated (or merely ASSERTED-remediated without verification) finding as a genuine, real gap.

6. Full Code Walkthrough — The String-Matching Completeness Categorization

"vulns" if any("emediat" in i or "assessment" in i for i in all_issues) else None,
Brain power: why does this line search for the substring "emediat" specifically, rather than the more naturally-spelled "remediat"? Searching for a SHARED ROOT substring, stripped of its leading letter, is a defensive technique that stays robust to varying PREFIXES around that root — "remediated," "unremediated," and a hypothetical "misremediated" all contain "emediat" as a substring regardless of what comes before it, whereas a search anchored to a specific FULL word could silently fail to match a differently-prefixed variant introduced by a future wording change. This is the same general "match on a stable fragment, not on assumed exact phrasing" instinct as Module 18 Section 3's known-bad-payload substring matching — cheap insurance against a message being reworded later in a way that would otherwise silently break this exact check.

8. Troubleshooting And Common Confusions

Common mistake: treating 100% completeness as the finish line rather than the starting floor. This module's own brief is explicit: "Getting to 100% here is a floor, not a ceiling." The checker verifies STRUCTURAL/INTERNAL consistency only (do your pieces match each other) — it cannot and does not evaluate whether your network DESIGN is actually sound, whether your remediation was the RIGHT fix, or whether your incident report is genuinely well-reasoned. A 100% score is necessary evidence your capstone is COMPLETE in the specific senses this checker can verify — it is not suficient evidence your capstone demonstrates real mastery, which is why the tutorial's own final step (explaining your build out loud, from memory, without notes) is the ACTUAL test of mastery, not the checker's percentage.
