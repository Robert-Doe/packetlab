Module 08 — Tutorial

Goal: build the three protocols that make the internet usable to humans — DNS (names instead of IPs), DHCP (automatic addressing), and HTTP (the actual request/response format every web page rides on) — and see exactly what a real client (curl, your own future browser code) requires from each.

Step 1 — DNS: a real authoritative server, real wire format

cd module-08-core-application-protocols
python dns_server.py
# separate terminal
python dns_client.py
Expected: lab.test. and www.lab.test. resolve to their configured IPs; nonexistent.test. comes back NXDOMAIN (rcode 3). Every byte on the wire was built with struct, same technique as Module 02's layer_builder.py — DNS is just another protocol with a defined byte layout, not a special case.
If you have dig installed (standard on Linux/Mac, not on Windows by default), you can also try: 
dig @127.0.0.1 -p 5053 lab.test.
Windows' built-in nslookup does NOT reliably support a custom port across versions (confirmed during this module's own testing — it silently queried the real resolver instead) — dns_client.py is this module's verified, cross-platform way to test the server.

Step 2 — DHCP: DORA, safely simulated

python dhcp_dora_sim.py
Expected: two clients acquire leases normally, a third client's re-DISCOVER gets its existing lease offered back (not a new one), pool exhaustion after the 3-address pool fills up (the 4th client gets no offer at all — this is literally what causes a real device to fall back to a 169.254.x.x APIPA address), and a released lease gets handed to a new client.
Why this isn't a real DHCP server: a real DHCP server binds to UDP ports 67/68 and listens for broadcast traffic on your actual LAN. If you ran one on your home network, it would compete with your router's own DHCP server for every device that boots up — and if yours answered first, a real device could get a bogus lease and lose connectivity. That's a real risk to other people's devices in your house, not a hypothetical one, so this module simulates the protocol's logic entirely in software instead. See ../SAFETY.md.

Step 3 — HTTP: what Flask was hiding from you

python http_server_from_scratch.py
# separate terminal -- use a REAL HTTP client, not this course's own code
curl -i http://127.0.0.1:8090/
curl -i http://127.0.0.1:8090/about
curl -i http://127.0.0.1:8090/nope
curl -i -X POST http://127.0.0.1:8090/
Expected: 200 responses for the two known routes, 404 for /nope, 405 for the POST request — and critically, curl (a real, independent HTTP client with no special knowledge of this course) is completely satisfied by every response, because the bytes this server sends are genuinely valid HTTP/1.1, assembled by hand with plain string formatting, no framework involved.

Step 4 — compare against every earlier module's servers

Every server before this module (Module 01's dashboard, Module 02's target server, Module 07's echo servers) used Flask. Open http_server_from_scratch.py next to any of them — notice everything Flask was doing invisibly: parsing the request line, splitting headers on :, building a correctly-formatted status line, setting Content-Length to the exact byte count. None of that is Flask magic — it's exactly the code you just wrote, just usually hidden behind one line: return "some string".

Exercises before Module 09

  1. Add a second DNS record type. Extend dns_server.py/.js to answer type 28 (AAAA, IPv6) queries for a new zone entry, alongside the existing A records. You'll need to change the RDATA length from 4 to 16 bytes and encode an IPv6 address's 16 bytes correctly.
  2. Break http_server_from_scratch.py on purpose. Send a request with curl --http1.0 instead of the default HTTP/1.1, and watch how parse_request handles (or mishandles) the different version string. Then try sending a request with NO blank line at all (a raw socket write, not curl) and confirm the server hangs on recv() forever — this is exactly why DECISIONS.md flags the single-recv() simplification as something a production server can't get away with.
  3. Give the DHCP simulation lease expiration. Add a simulated "tick" counter and a lease duration; after a lease's tick count exceeds its duration without renewal, automatically release it back to the pool. This is the piece real DHCP servers have that this module's simplified simulation doesn't.
Before Module 09: you should be able to explain what DNS, DHCP, and HTTP each actually do at the byte level, not just "DNS resolves names." Module 09 takes everything from Modules 01-08 out of pure simulation and onto your actual home network — configuring your real Cox modem into bridge mode and standing up your own router/firewall in front of it.
