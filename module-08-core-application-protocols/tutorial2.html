Module 08 — Deep Theory: DNS, DHCP, HTTP, Command by Command

1. Command-by-Command: Testing the DNS Server

dig @127.0.0.1 -p 5053 lab.test.

What each piece means: dig ("domain information groper") is the standard Unix DNS query tool. @127.0.0.1 tells it WHICH DNS server to query directly (without @, dig uses your system's configured default resolver) — the @ syntax is dig-specific shorthand for "query this server." -p 5053 specifies a non-default port (DNS normally uses port 53; this course's server deliberately uses 5053 to avoid needing root/admin privileges — see Module 08's own DECISIONS.md). The final argument, lab.test., is the name being queried — note the TRAILING DOT, which formally denotes a "fully qualified domain name" (FQDN) — a name anchored to the DNS root, as opposed to a relative name that might have a search-domain suffix appended by the resolver.

Why nslookup (Windows) failed where dig succeeds

This was a real, confirmed finding during this module's build: modern Windows nslookup's support for specifying a custom port alongside a custom server is inconsistent across Windows versions — in some cases it silently ignores the port and queries the real system resolver instead, which would give a confusing false "it doesn't work" impression when the SERVER was actually fine. This is exactly why this module's own dns_client.py (built with Python's socket module directly, giving full control over exactly which host/port is queried) is the verified, reliable cross-platform test path, with dig offered only as an optional extra for students who happen to have it.

2. DNS Message Structure, Fully Formal

Every DNS message (query or response) shares one structure: a 12-byte header (containing a 16-bit transaction ID for matching queries to responses, flags including the RCODE error/status field, and 4 count fields for how many entries follow in each section), followed by up to 4 sections: Question, Answer, Authority, Additional. This course's dns_server.py only populates Question and Answer, but real DNS responses often use Authority (naming which server is authoritative for a zone) and Additional (bonus records the client is likely to need next, saving a round-trip) too.

Comprehensive exam framing: "Why does the DNS header include a 16-bit transaction ID, given that DNS typically runs over UDP (connectionless)?" Because UDP provides no built-in mechanism to match a response to its originating request — unlike TCP, where a connection's own state implicitly associates request and response. The transaction ID lets a client that may have MULTIPLE outstanding DNS queries in flight simultaneously (to the same or different servers) correctly match each incoming response back to the specific query that triggered it, and reject responses whose ID doesn't match anything outstanding (a real, if weak, defense against off-path DNS response spoofing — `dns_client.py`'s own `assert recv_id == sent_id` check demonstrates exactly this).

3. DHCP's DORA, in Full RFC 2131 Detail

The reason DORA is 4 messages, not 2 (a simple request/response), traces to a fundamental bootstrapping problem: a freshly-booted device has NO IP address yet, meaning it cannot be addressed directly by anything. DISCOVER must be broadcast (the only way to reach "everyone," since the client has no specific server to address). Multiple DHCP servers on the same segment might all respond with an OFFER. The client's REQUEST is ALSO broadcast — specifically so that every OTHER server that made an offer can see this broadcast and understand their own offer was declined, letting them release that tentatively-reserved address back to their own pool without ever receiving a direct rejection message.

Why does dhcp_dora_sim.py model this as a pure simulation instead of a real server? A real DHCP server binds to UDP port 67/68 and listens for BROADCAST traffic on the actual physical/Wi-Fi segment — on a home network, this is traffic from every device in the house, not just a test client. A buggy or misconfigured simulated server racing against your home router's own real DHCP server, and winning that race for a REAL device's DISCOVER broadcast, could hand that device a bogus lease and disconnect it — a real risk to other people's devices, not a hypothetical one, which is why this module's simulation never binds to a real network interface at all.

4. HTTP Status Codes, Systematically

http_server_from_scratch.py's 200/404/405 responses are three members of a formally organized system, RFC 9110's status code classes:

RangeClassMeaning
1xxInformationalRequest received, processing continues (rare in ordinary use; e.g. 100 Continue)
2xxSuccessThe request was successfully received, understood, and accepted (200 OK is the workhorse of this class)
3xxRedirectionFurther action needed to complete the request (e.g. 301 Moved Permanently)
4xxClient ErrorThe request itself was malformed or invalid (404 Not Found, 405 Method Not Allowed)
5xxServer ErrorThe request was valid, but the server failed to fulfill it (500 Internal Server Error)
Brain power: why is 404 a 4xx (client error) rather than a 5xx (server error), given that the SERVER is the one deciding a route doesn't exist? Because from HTTP's perspective, the CLIENT made an error — it asked for a resource that doesn't exist at this server, which is categorized as a problem with the REQUEST itself (an invalid target), not a failure of the server's own processing. This distinction matters practically: a well-behaved client should generally NOT retry a 4xx request unmodified (the request itself was the problem), while retrying a 5xx request after a delay is often reasonable (the server may recover).
