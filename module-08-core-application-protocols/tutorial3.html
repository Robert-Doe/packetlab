Module 08 — Exam Practice

Answer out loud before revealing each answer.
Q1. Why does the DNS header include a 16-bit transaction ID, given that DNS typically runs over connectionless UDP?
A: UDP provides no built-in mechanism to associate a response with its originating request, unlike TCP where connection state implicitly does this. The transaction ID lets a client with multiple outstanding queries correctly match each incoming response to the specific query that triggered it, and reject responses whose ID doesn't match any outstanding query -- providing some (weak) protection against off-path response spoofing.
Q2. Why must both the DHCP DISCOVER and REQUEST messages be broadcast, rather than the REQUEST being unicast directly to the chosen server?
A: DISCOVER must be broadcast because the client has no IP address yet and no specific server to address it to. REQUEST is ALSO broadcast specifically so every OTHER DHCP server that made a competing OFFER can observe the broadcast and learn their own offer was declined -- letting them release that tentatively-reserved address back to their own pool, without needing a separate direct rejection message from the client.
Q3. Why is 404 Not Found classified as a 4xx (client error) rather than a 5xx (server error), given that the server is the one deciding the resource doesn't exist?
A: HTTP's status code classification reflects WHOSE fault the problem is attributed to in the request/response model: 4xx means the request itself was invalid or malformed in some way (asking for a nonexistent resource counts as this); 5xx means the request was valid but the server failed to fulfill it. This distinction has practical consequences -- a well-behaved client generally should NOT blindly retry a 4xx request unmodified, since the request itself was the problem, while retrying a 5xx request after a delay is often reasonable since the server may recover.
Q4. Why does this course's DNS server bind to port 5053 instead of the standard port 53, and why does dig's -p flag matter for testing it?
A: Port 53 is a "privileged" port (below 1024), requiring root/administrator privileges to bind on every major OS. Binding to 5053 instead avoids that privilege requirement and avoids potentially conflicting with a real DNS resolver already running on port 53. dig's `-p` flag is necessary specifically because dig otherwise assumes the standard port 53 -- without specifying `-p 5053`, dig would query the wrong port entirely and get no response from this course's server.
Q5. Explain the real risk that would exist if you ran dhcp_dora_sim.py as an actual UDP-bound server on your home network instead of a pure simulation.
A: A real DHCP server listens for broadcast DISCOVER traffic from ANY device on the physical/Wi-Fi segment, not just an intended test client -- on a home network, this includes every real device in the house. If this simulated server raced against the home router's own legitimate DHCP server and won for a real device's DISCOVER broadcast, that real device could receive a bogus lease (wrong gateway, wrong DNS, or an address conflicting with another device) and lose network connectivity -- a genuine risk to other people's devices, not a hypothetical one.
Q6. What specifically does http_server_from_scratch.py's construction demonstrate that using Flask (as every earlier module's server did) would hide?
A: Every mechanical step Flask performs invisibly: parsing the raw request line and headers from bytes read off the socket, determining the correct status line and reason phrase for a given response, computing and setting an accurate Content-Length header matching the exact byte count of the response body, and formatting the blank-line-terminated header block per HTTP's own wire format requirements. None of this is framework magic -- it's ordinary string/byte manipulation that Flask (and any web framework) does on the developer's behalf, usually hidden behind a single high-level return statement.
Q7. Synthesis: connect DNS's transaction ID (weak anti-spoofing) to Module 13's certificate-based authentication (strong anti-spoofing). Why is one "weak" and the other "strong"?
A: DNS's transaction ID is a 16-bit value (65,536 possible values) that must merely be GUESSED correctly by an attacker attempting to inject a forged response -- computationally quite feasible for a motivated off-path attacker, especially combined with other weaknesses (predictable source ports, multiple guesses). This is why DNS cache poisoning has been a real, practical attack class, and why DNSSEC (cryptographic signing of DNS records) exists as a stronger fix. Module 13's certificate-based authentication instead relies on cryptographic signatures backed by computationally infeasible-to-forge private keys (RSA/ECDSA) verified against a trusted root -- a fundamentally different and much stronger security property than "hope the attacker doesn't guess a 16-bit number," which is why TLS-secured connections don't suffer from the equivalent of DNS spoofing in the same practical way.
