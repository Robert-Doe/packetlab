Module 03 — Tutorial

Goal: watch a switch learn MAC addresses, flood what it doesn't know, forward what it does, and refuse to cross a VLAN boundary — all from a simulation you can read line-by-line, then confirm the same ARP mechanic on your own real home network.

Step 1 — run the simulator

cd module-03-datalink-switching-arp
python switch_sim.py
Expected output: three scenarios. Scenario 1: PC-A broadcasts an ARP request, the switch logs "learned" for PC-A's MAC, floods to VLAN 10 only, PC-B replies, switch learns PC-B's MAC too, and forwards the reply as a known unicast. Scenario 2: PC-A ARPs for a VLAN-20 host's IP — the flood happens but stays inside VLAN 10, so no reply ever comes back. Scenario 3: a second frame to PC-B now forwards directly to port 2 instead of flooding, because the CAM table already has the answer. 
node switch_sim.js
Identical scenario-by-scenario output (verified during this module's build — diffed the scenario headers between both languages).

Step 2 — read the code, not just the output

Open switch_sim.py and find Switch.receive(). This ~15-line method is the entire job of a real Layer 2 switch:

1. Learn: record (VLAN, source MAC) -> incoming port
2. If destination is broadcast -> flood within this VLAN
3. Else if destination MAC is in the CAM table -> forward to that ONE port
4. Else (unknown unicast) -> flood within this VLAN anyway

Real switch ASICs do this in hardware at line rate with a much bigger, hardware CAM table and MAC aging timers — but the algorithm is exactly this. There's no more "magic" underneath a $50,000 enterprise switch's Layer 2 forwarding decision than what you just read.

Step 3 — confirm ARP for real, on your own network

# clear your ARP cache first (needs admin/sudo)
# Windows (as Administrator):
arp -d *
# macOS/Linux:
sudo ip neigh flush all      (Linux)
sudo arp -a -d                (macOS, per-entry)

# now generate a fresh ARP exchange:
ping -n 1 192.168.0.1        REM Windows -- replace with your real gateway
ping -c 1 192.168.0.1        # macOS/Linux

# check the result:
arp -a
Expected: before the ping, your gateway is absent (or marked incomplete) from arp -a. After one ping, it appears with a real MAC address — that ping's ICMP packet couldn't even be sent at Layer 2 until your machine ARP'd for the gateway's MAC first, exactly like PC-A did for PC-B in the simulator.

Step 4 — VLANs on your own router (read-only, no changes)

Log into your home router's admin page (usually http://192.168.0.1 or similar — check Module 01's dashboard for your real gateway address). Look for a "VLAN" or "Guest Network" section — most consumer routers implement guest Wi-Fi as a separate VLAN specifically so guest devices can't ARP for / reach your main network's devices. That's the exact isolation Scenario 2 demonstrated, running on hardware in your house right now. You don't need to change anything — just find the setting and confirm it exists.

Exercises before Module 04

  1. Add MAC aging. Real CAM table entries expire (typically after 300 seconds of inactivity) so a switch doesn't hold stale port mappings forever. Add a timestamp to each CAM table entry and an age_out(current_time, max_age) method that removes stale entries, in both the Python and JS versions.
  2. Add a 5th host on a trunk port. A trunk port carries multiple VLANs tagged (as opposed to the "access ports" every host in this simulation currently uses, which carry one untagged VLAN each). Model a trunk port that maps to a list of allowed VLANs instead of a single one, and have frames leaving that port carry an explicit 802.1Q tag (which build_frame/buildFrame already supports — you built the piece you need in Module 02/03, just wire it up).
  3. Simulate a MAC flooding attack. Write a loop that sends frames from thousands of random fake source MACs into the switch. Watch the CAM table grow unbounded. This is the setup for a real attack (CAM table overflow forces the switch into "fail open" flooding-everything mode) — don't build the exploit yet, just observe the CAM table's growth. Module 18 revisits this as an incident to forensically reconstruct.
Before Module 04: you should be able to explain, without notes, why a switch floods an unknown-unicast frame identically to how it floods a broadcast frame (same mechanism, same reason: "I don't know where this needs to go, so I'll send it everywhere it's allowed to go"). Module 04 moves up one layer — IP addressing and subnetting — where "allowed to go" starts being about routing between different broadcast domains like the VLAN 10/VLAN 20 split you just built.
