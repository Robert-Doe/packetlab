Module 03 — Deep Theory: Switching, ARP, and VLANs, Command by Command

1. Command-by-Command: Clearing and Rebuilding Your ARP Cache

arp -d * (Windows, run as Administrator)

What it does: deletes every entry in your machine's ARP cache. Why admin/root is required: the ARP cache is shared kernel state that affects how EVERY process on your machine resolves IP-to-MAC mappings — an unprivileged process being able to wipe it (or worse, insert fake entries) would be a serious security hole, since it would let any user-level program potentially redirect other processes' traffic. This same privilege requirement is why Module 03's own switch_sim.py never touches your machine's REAL ARP cache at all — it's a pure software model with its own separate, in-memory table, entirely sidestepping the need for elevated privileges.

sudo ip neigh flush all (Linux)

What it does: the modern Linux equivalent of arp -d *. "neigh" (neighbor) is Linux's more general term for this table, because the same underlying mechanism (and largely the same kernel table) also handles IPv6's Neighbor Discovery Protocol, which plays a role similar to ARP but works differently under the hood (NDP uses ICMPv6 messages rather than a dedicated EtherType, and doesn't rely on broadcast the way ARP does — IPv6 has no broadcast address at all, using multicast instead).

ping -n 1 192.168.0.1 / ping -c 1 192.168.0.1

What the flags mean: -n 1 (Windows) and -c 1 (Mac/Linux) both mean "send exactly 1 ping and stop" — without this flag, ping on Linux/Mac runs forever until you manually stop it (Ctrl+C), while Windows defaults to sending exactly 4 and stopping automatically. Why this triggers a fresh ARP entry: your machine cannot send ANY IP packet to a destination on your local network segment without first knowing that destination's MAC address (Ethernet frames are addressed by MAC, not IP — this is the entire reason ARP exists, bridging Layer 3 addressing to Layer 2 addressing). Since you just flushed the cache, this ping FORCES a fresh ARP request/reply exchange before the ICMP echo can even be transmitted.

2. The Switch Algorithm, Formally

switch_sim.py's Switch.receive() implements what's formally called "transparent bridging" (or "learning bridge" behavior) — the algorithm EVERY Ethernet switch uses, whether a $20 home switch or a $50,000 enterprise chassis:

function receive(frame, incoming_port):
    learn: CAM_table[(vlan, frame.source_mac)] = incoming_port
    if frame.destination_mac == BROADCAST:
        flood(frame, vlan, except=incoming_port)
    elif (vlan, frame.destination_mac) in CAM_table:
        forward(frame, CAM_table[(vlan, frame.destination_mac)])
    else:
        flood(frame, vlan, except=incoming_port)  # "unknown unicast flooding"
Comprehensive exam framing: "Is a switch a Layer 2 or Layer 3 device, and does this algorithm ever need to inspect an IP address?" A switch is purely Layer 2 — every decision in the algorithm above operates ENTIRELY on MAC addresses and VLAN tags; it never looks at an IP header at all, even when the frame it's forwarding happens to contain an IP packet inside it. This is precisely why a switch can forward ARP requests, IPv4 packets, IPv6 packets, or any other EtherType identically — its forwarding decision is blind to what's encapsulated inside the frame it's moving.

3. ARP's Complete Message Exchange, Formally

ARP (RFC 826) defines exactly two message types: REQUEST ("who has IP X? tell IP Y") and REPLY ("IP X is at MAC Z"). A request is always sent to the broadcast MAC address (since the sender, by definition, doesn't yet know who to address it to directly) — a reply is sent as a UNICAST directly back to the requester's MAC (learned from the request's own source MAC field), which is why switch_sim.py's Scenario 1 shows the request FLOODING but the reply FORWARDING to one port only.

4. 802.1Q VLAN Tagging, the Actual Bytes

An 802.1Q tag is 4 extra bytes inserted into an Ethernet frame, immediately after the source MAC address and before the EtherType field: a 2-byte Tag Protocol Identifier (always 0x8100, signaling "this frame is tagged") followed by a 2-byte Tag Control Information field, whose lowest 12 bits are the actual VLAN ID (allowing VLAN IDs 0-4095, though 0 and 4095 are reserved). build_frame()'s vlan_id parameter constructs exactly this structure — the same bit-masking technique (tci & 0x0FFF) Module 00a's boolean algebra chapter covered.

Why does a 12-bit VLAN ID field cap you at 4096 VLANs? 12 bits can represent exactly 2^12 = 4096 distinct values (0 through 4095). This is a real, hard architectural limit of 802.1Q specifically — large enterprise/cloud environments that need MORE isolated segments than 4096 use additional technologies layered on top (VXLAN, using a 24-bit identifier instead, supporting over 16 million segments) precisely to work around this ceiling.

5. MAC Flooding: Why Exercise 3 Matters for Real Security

A switch's CAM table has finite hardware memory. A MAC flooding attack deliberately sends frames from thousands (or millions) of distinct, often randomly-generated source MAC addresses, exhausting the CAM table's capacity. Once full, many real switches (historically, particularly older/cheaper hardware) "fail open" — reverting to flooding EVERY frame to EVERY port, because they can no longer learn new entries but must still forward traffic somehow. This transforms a switch, temporarily, into the equivalent of an old-style hub — meaning an attacker on any port can now see traffic addressed to any OTHER host on that segment, a direct violation of the isolation switches normally provide.
