Module 05 — Tutorial

Goal: trace a packet through hand-built static routes, then watch the exact moment distance-vector routing (RIP) can lie to itself — and see why link-state routing (OSPF) structurally can't make that mistake.

Step 1 — static routing and longest-prefix match

cd module-05-routing-fundamentals
python static_routing.py
Expected: three routing tables printed (R1, R2, R3), then four traced packets. Watch the third trace especially — a packet to 8.8.8.8 matches nothing specific on R1, falls through to its 0.0.0.0/0 default route, and "exits the topology" — this is literally what your home router does with every packet you send to the internet.
node static_routing.js
Identical trace output (verified during this module's build with a byte-diff, modulo Windows line-ending differences).

Step 2 — RIP's count-to-infinity, actually happening

python routing_protocols_sim.py
Expected: Part 1 shows a 3-router chain converge normally, then a broken link causes R1 and R2's metric to R3 to climb — oscillating between the two routers — over roughly 14 rounds before finally both settle at 16 (RIP's real "infinity" constant, from RFC 2453). Part 1b re-runs the same failure with split-horizon enabled: convergence to "unreachable" happens in a single round instead.
This bug was real during this module's own development. The first version of DVRouter.receive() only accepted a neighbor's advertisement if it was strictly better than the current route — which is correct Bellman-Ford relaxation, but ALSO meant a router never revised a stale route that had gotten worse via its own current path, producing permanently wrong (not just slowly wrong) routing tables. The fix was one line: if the advertisement comes from the neighbor you're currently routing through, you must accept their update even when it's worse, because they ARE your route's source of truth. Re-derive this yourself in Exercise 1 below — it's the single most important line in the whole file.

Step 3 — OSPF's link-state approach, side by side

Still in the same run, Part 2 floods each router's own direct links to build a full topology graph, then runs Dijkstra locally at every router. Compare the "Step 3" output (after breaking the same link) to Part 1's 14 rounds of oscillation — OSPF's version reaches the correct "unreachable" answer the instant the link-down news is flooded, with no intermediate bad state at all.

Step 4 — watch your own home router's route table

# Windows
route print
# macOS/Linux
netstat -rn        (or: ip route)
Expected: a default route (0.0.0.0 destination) pointing at your gateway — the exact mechanism static_routing.py's Step 1c trace demonstrated. Home routers essentially never run RIP or OSPF themselves (both are typically enterprise/ISP-grade protocols) — they use exactly the static default-route pattern from this module, which is worth confirming on real output rather than taking on faith.

Then put the fix back and explain in your own words why it's necessary.
  2. Add a 4th router with a redundant path. Extend base_links()/baseLinks() so R1 and R3 also have a direct link (making a triangle: R1-R2-R3-R1). Re-run the link-failure scenario — does split horizon alone still prevent count-to-infinity with a real alternate path available, or do you need "split horizon with poison reverse" (advertise the broken route back as explicit infinity rather than just omitting it)? Implement poison reverse if you find a case where plain split horizon isn't enough.
  3. Extend static_routing.py with route summarization. Confirm longest-prefix-match still picks the more specific /24 route when both match — this is exactly how real ISPs use summarization without breaking more-specific routing.
