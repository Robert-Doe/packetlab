Module 05 — Deep Theory: Routing Algorithms, Command by Command

1. Command-by-Command: Reading Your Own Router's Table

route print (Windows) / netstat -rn or ip route (Mac/Linux)

What each does: asks your OS kernel to print its OWN routing table — the same conceptual structure static_routing.py's Router class models, but this is the REAL table your machine consults for every single packet it sends. netstat -rn's -r flag means "show routing table" (netstat's default without flags shows active connections, a completely different report) and -n means "show numeric addresses, don't resolve hostnames" — without -n, netstat would try to reverse-DNS-lookup every address in the table, which is slow and usually shows you less useful information than the raw IP. ip route is the modern Linux replacement for the older, now-deprecated route command, part of the iproute2 toolset.

Why will you see a 0.0.0.0 destination in your own table? That's your default route — literally the same 0.0.0.0/0 entry static_routing.py's R1 has, pointing at your gateway. Every packet whose destination doesn't match any more specific route in your table falls through to this entry, exactly like the Step 1 trace to 8.8.8.8 demonstrated.

2. Longest-Prefix Match, Formally

When multiple routes in a table could all technically match a given destination address, the router ALWAYS selects the one with the MOST specific (longest) prefix — never the first one added, never based on any other tiebreaker. This is not a convention or a "best practice"; it's a hard requirement of every IP routing implementation, because it's the only rule that makes route summarization (Exercise 3) and default routes coexist sensibly: a 0.0.0.0/0 default route matches LITERALLY EVERY address, but a router with any more specific route for a given destination must prefer that more specific route, or default routes would make all other routing entries pointless.

3. Bellman-Ford, Formally (What RIP Actually Runs)

RIP implements the Bellman-Ford algorithm for finding shortest paths in a graph. The core relaxation step: for each neighbor's advertised distance to a destination, compute (neighbor's advertised distance + cost of the link to that neighbor); if this is BETTER than your current known distance to that destination, adopt it. Run this repeatedly across all routers until nothing changes ("convergence"). This is provably correct for a STATIC graph with no failures — the bug this module's own build hit (see tutorial.html's callout) arose specifically from a subtlety Bellman-Ford's textbook description doesn't address: what happens when the graph CHANGES (a link fails) after the algorithm already converged.

Comprehensive exam framing: "Why is Bellman-Ford's standard 'only accept a strictly better distance' relaxation rule insufficient for a REAL, dynamically-changing network, and what's the minimal fix?" The textbook algorithm assumes the graph is fixed while it runs — it has no concept of "this route I'm currently using just got worse." A router whose current path degrades will never revise away from it under strict relaxation, because the new (worse) distance is never "better than current." The minimal fix: a router must unconditionally accept updates from whichever neighbor is its CURRENT next-hop for a destination, even when the update is worse — because that neighbor IS the router's sole source of truth for that specific route, not one alternative among many to be compared.

4. Why Split Horizon Isn't Always Enough (Exercise 2's Real Answer)

Split horizon (never advertise a route back to the neighbor you learned it from) fully solves the 2-router ping-pong this module demonstrated — but with a THIRD router providing a genuine alternate path (a triangle topology), a more subtle failure mode remains possible: Router A might advertise a route to Router C that A itself learned from Router B, and Router C might advertise a DIFFERENT (also stale) route back that eventually loops through B again via a path split horizon's simple "don't tell the neighbor you learned it from" rule doesn't catch, because the stale information is now traveling through a THIRD party rather than bouncing directly between two routers. "Split horizon with poison reverse" (explicitly advertising a now-unreachable route back as INFINITY, rather than just omitting it) closes more of this gap by making the "this route is dead" information propagate explicitly and immediately along more paths, rather than requiring it to be inferred from an absence.

5. Dijkstra's Algorithm, Formally (What OSPF Actually Runs)

Given a complete graph (every router has flooded its own direct links to every other router, so everyone has an IDENTICAL copy of the full topology), Dijkstra's algorithm computes shortest paths from one starting node to every other node by maintaining a set of "settled" nodes (shortest path definitively known) and repeatedly selecting the closest unsettled node, relaxing its neighbors' distances, until every node is settled. Unlike Bellman-Ford, Dijkstra requires the FULL graph structure up front — it cannot operate on partial, neighbor-summarized information the way distance-vector protocols do, which is PRECISELY why link-state protocols don't have a count-to-infinity failure mode: there's no summarized intermediate belief to go stale, because every router computes directly from the complete, freshly-flooded topology every time.
