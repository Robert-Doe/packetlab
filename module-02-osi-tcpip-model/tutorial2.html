Module 02 — Deep Theory: OSI vs. TCP/IP, Command by Command

1. Why Two Competing Models Exist At All

The OSI model (7 layers: Physical, Data Link, Network, Transport, Session, Presentation, Application) was developed by the ISO in the early 1980s as a THEORETICAL reference — a way to reason about networking in the abstract, designed so any vendor's Layer N implementation could theoretically interoperate with any other vendor's Layer N+1, as long as both honored the interface between layers. TCP/IP (4 layers: Link, Internet, Transport, Application) is not a competing theory — it's the protocol suite that actually shipped and won, developed separately (DARPA-funded, 1970s) and standardized through RFCs, not a formal standards body's abstract model. You use OSI vocabulary to TALK about networking (everyone says "Layer 2," "Layer 3," "Layer 7") while the actual bytes on the wire follow TCP/IP's simpler structure.

2. Command-by-Command: What tutorial.html Actually Had You Do

python layer_builder.py

What it does: runs a Python script that calls struct.pack() repeatedly to assemble raw bytes representing an Ethernet header, then an IPv4 header, then a TCP header, then an HTTP request — concatenated together into one buffer, then printed as hex. Why struct.pack specifically: Python's built-in struct module takes a "format string" describing exactly how many bytes each value should occupy and in what byte order, then packs Python values into a raw bytes object matching that layout — exactly the manual, byte-precise control Module 00b's C structs also demonstrated, just in Python instead of C.

node layer_builder.js

What it does: the identical construction using Node's Buffer class instead of Python's struct module — different API, identical resulting bytes, confirmed byte-for-byte during this module's original build.

Installing Wireshark (wireshark.org, with Npcap on Windows)

Why Npcap specifically, on Windows: capturing raw network traffic — seeing every byte crossing an interface, not just the data your own program sent or received — requires a special OS-level driver, because ordinary application-level sockets are deliberately NOT given this level of access (a normal program can only see traffic addressed to it). Npcap is that driver for Windows (the direct successor to the older WinPcap project); macOS and Linux have this capability built into the kernel already (accessed via libpcap), which is why only Windows needs an extra installation step here.

tcp.port == 8080 (the Wireshark display filter)

What it does: Wireshark, by default, CAPTURES everything crossing the selected interface (potentially thousands of packets from unrelated background traffic — DNS lookups, cloud sync software, etc.) but only DISPLAYS packets matching your filter expression. tcp.port == 8080 means "show me only packets where the TCP source OR destination port is 8080" — Wireshark's filter language understands protocol fields by name (tcp.port, ip.addr, http.request.method, etc.), which is why learning this filter syntax (not just clicking through a GUI menu) is the actual skill worth building.

Why filter the DISPLAY rather than the capture itself? Because you often don't know exactly what you're looking for until AFTER you've captured — filtering only the view, while keeping the full capture underneath, lets you change your filter and re-examine the same data without re-capturing. (Wireshark does also support CAPTURE filters, a separate, stricter mechanism applied before packets are even recorded — useful when capture volume itself is the problem, e.g. on a busy production link, but not needed for this module's small localhost test.)

Edit → Find Packet (Step 4)

What it does: searches every captured packet's raw bytes (not just the summary line) for a string you specify — this is literally scanning the same hex bytes layer_builder.py prints, just for whichever packet actually contains your marker string, proving the exact server-side response text made it onto the wire unmodified.

3. Why Layers 5/6 Have No Header — Formally

OSI's Session layer (managing a logical conversation, independent of the underlying connection) and Presentation layer (data format translation/encoding, e.g. character sets, compression, encryption framing) were designed as SEPARATE concerns from Application layer logic. In practice, every real-world application protocol (HTTP, SMTP, DNS) simply handles session state and data formatting ITSELF, as part of its own application-layer design, rather than delegating to a separate protocol layer underneath. TLS (Module 13) is sometimes informally described as "Presentation layer" functionality (it does provide encoding/encryption), but architecturally it sits BETWEEN Transport and Application as its own protocol with its own header — not as OSI's Presentation layer literally implemented. This is the concrete, structural reason a Wireshark capture never shows "Layer 5" or "Layer 6" headers: those layers were never implemented as distinct wire-format protocols by anyone, ever, at internet scale.

Comprehensive exam framing: "A student claims TLS is 'the presentation layer, implemented.' Evaluate this claim." Partially correct at best: TLS does perform encoding/encryption, functionality OSI assigned to Presentation — but TLS is architecturally its own protocol with its own header format, sitting between Transport and Application in the TCP/IP stack, not literally OSI's Presentation layer given form. The mapping is a loose ANALOGY useful for building intuition, not a precise architectural correspondence — a strong exam answer should flag this distinction rather than assert the equivalence uncritically.

4. Encapsulation, As a Formal Operation

layer_builder.py builds bytes INSIDE OUT: HTTP payload first, wrapped by a TCP header, wrapped by an IP header, wrapped by an Ethernet header. Formally, encapsulation is a PREPEND operation at each layer — each layer takes the ENTIRE previous layer's output (header + whatever it already contained) as an opaque blob of data, and prepends its own header in front, without inspecting or modifying what it's wrapping. This "opacity" property is fundamental: the Ethernet layer has no idea whether the payload it's carrying is IP, ARP, or something else entirely (which is exactly what the ethertype field communicates to the receiver — "here's what kind of thing you'll find once you strip MY header off").
