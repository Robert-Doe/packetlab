Module 02 — Exam Practice

Answer out loud before revealing each answer.
Q1. OSI has 7 layers; TCP/IP has 4. Is TCP/IP "missing" 3 layers, or is this framing wrong? Explain precisely.
A: The framing is imprecise. TCP/IP doesn't lack functionality OSI's top layers describe (session management, data presentation/encoding) -- it simply never separated that functionality into distinct WIRE-FORMAT PROTOCOLS with their own headers. Every real-world application protocol (HTTP, DNS, SMTP) handles session state and data formatting as part of its OWN application-layer design. OSI is a 7-layer REFERENCE MODEL for reasoning about networking abstractly; TCP/IP is the protocol suite that actually shipped, with 4 layers because that's what real implementations needed distinct headers for.
Q2. What does the Ethernet frame's EtherType field communicate, and why is this necessary given that Ethernet itself doesn't understand IP?
A: EtherType tells the receiver what protocol is encapsulated inside the Ethernet payload (0x0800 for IPv4, 0x0806 for ARP, 0x86DD for IPv6, etc.). It's necessary because encapsulation is opaque by design -- the Ethernet layer doesn't inspect or understand what it's carrying, it just wraps arbitrary bytes in its own header. Without an explicit "what's inside" field, the receiving stack would have no way to know which higher-layer protocol should parse the payload next.
Q3. Why does Wireshark on Windows require an additional driver (Npcap) that macOS/Linux don't need?
A: Raw packet capture -- seeing every byte crossing an interface regardless of whether it's addressed to your own program -- requires privileged, OS-level access that ordinary application sockets deliberately don't have. macOS and Linux have this capability built into their kernels (accessed via libpcap); Windows requires a separate kernel-level driver (Npcap, successor to WinPcap) to provide the equivalent capability, which is why it must be installed alongside Wireshark specifically on Windows.
Q4. Explain the difference between a Wireshark CAPTURE filter and a DISPLAY filter, and why this module's tutorial used a display filter.
A: A capture filter is applied BEFORE packets are even recorded -- packets not matching it are never captured at all, useful for reducing capture volume on high-traffic links. A display filter is applied to ALREADY-CAPTURED data, only affecting what's shown, with the full capture still available underneath and re-filterable without re-capturing. This module used a display filter (`tcp.port == 8080`) because the capture volume (localhost, one test exchange) was small enough that filtering the view -- with the option to broaden the filter later without re-capturing -- was more useful than restricting what got recorded in the first place.
Q5. Precisely define "encapsulation" as an operation, using the specific terms opaque and prepend.
A: Encapsulation is the operation where each protocol layer PREPENDS its own header in front of the entire output of the layer above it, treating that entire prior output as an OPAQUE blob of data -- without inspecting or modifying its contents. This is why `layer_builder.py` builds bytes inside-out (payload first, then TCP header prepended, then IP header prepended to THAT, then Ethernet header prepended to the whole thing) -- it's literally performing the encapsulation operation in the same order a real network stack does.
Q6. A student claims "TLS is literally OSI's Presentation layer." Evaluate this claim precisely.
A: Partially correct at best, and imprecise if stated as an equivalence. TLS does perform functionality OSI assigned to the Presentation layer (encryption, a form of data encoding), but TLS is architecturally its OWN protocol with its own header format, sitting between the Transport and Application layers in the TCP/IP stack -- it is not literally OSI's Presentation layer implemented as a distinct, separable layer the way OSI's model describes. The mapping is a useful loose analogy for building intuition, not a precise architectural correspondence that should be asserted as fact on an exam.
Q7. Synthesis: why does understanding "OSI is a reference model, TCP/IP is what shipped" matter for reading a real Wireshark capture, beyond just trivia?
A: It sets correct expectations for what you'll actually see: exactly 4 (or effectively, in Wireshark's own labeling, closer to 5 with Frame/Ethernet/IP/Transport/Application) distinct header layers in any real capture, never separate Session or Presentation headers no matter how carefully you look. A practitioner who expects to find OSI's full 7 layers as distinct wire-format sections in a real capture will be confused by their absence; understanding WHY they're absent (never implemented as separate wire protocols at internet scale) turns that absence from a confusing gap into an expected, well-understood fact about how TCP/IP actually works.
