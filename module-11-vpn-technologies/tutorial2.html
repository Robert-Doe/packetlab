Module 11 — Deep Theory: WireGuard's Handshake and Commands, From Zero

1. Command-by-Command

wg-quick up ./laptop.conf

What it actually does, step by step: wg-quick is a convenience wrapper script around the lower-level wg tool and standard OS networking commands. It (1) creates a new virtual network interface (typically named wg0), (2) loads your config file's [Interface] section (your private key, your tunnel-internal IP address) onto that interface, (3) loads each [Peer] section (their public key, their real-world Endpoint, and AllowedIPs defining which destination IPs should be routed through this tunnel), and (4) adds routing table entries so traffic to those AllowedIPs gets sent out the new wg0 interface instead of your normal default route. Why this matters: nothing here is magic — it's the same interface creation and routing table manipulation Module 05's routing theory already covered, just automated by one convenience command.

ping 10.10.0.2 (the tunnel address, Step 3)

Why this proves the tunnel actually works, mechanically: 10.10.0.0/24 exists NOWHERE on your real physical/Wi-Fi network — it's an address space WireGuard itself creates, purely virtual, existing only because both machines' wg-quick up commands added routing entries for it. A successful ping here means your OS's routing table correctly sent the ICMP packet to the wg0 interface (per Step 1's routing table addition), WireGuard's driver encrypted and re-wrapped it as a UDP packet to the peer's REAL endpoint address, the peer's WireGuard driver decrypted it and delivered it to ITS wg0 interface, and its own OS correctly recognized 10.10.0.2 as one of its own addresses and replied — a complete, real, multi-step round trip through the tunnel, not a simulation.

2. The Noise Protocol Framework, at a Conceptual Level

WireGuard doesn't invent its own handshake protocol from scratch — it implements a specific, pre-defined "handshake pattern" from the Noise Protocol Framework (a formal specification for building secure handshakes from composable building blocks, itself independently analyzed by cryptographers). Specifically, WireGuard uses Noise's IK pattern: both peers already know each other's static public keys in advance (from the config files — this is exactly why wg_config_generator.py hardcodes both sides' public keys into each other's config, rather than negotiating identity during the handshake itself), and the handshake's job is purely to establish a FRESH, ephemeral session key for THIS particular session, while authenticating both sides using their already-known static keys.

Why does this differ from Module 00a's raw Diffie-Hellman demo? Module 00a's DH demo established a shared secret with ZERO authentication — either party in that demo could have been an impersonator, and the protocol would never notice. WireGuard's Noise IK handshake performs DH key exchange (conceptually the same mathematical operation, using X25519 elliptic curve DH rather than the toy modular exponentiation from Module 00a) COMBINED with proving possession of a known, pre-configured private key — solving exactly the authentication gap Module 00a's deep theory flagged as raw DH's core weakness.

3. Why UDP, Despite Wanting Reliable Delivery (Exercise 3's Answer, Formalized)

The traffic RIDING INSIDE a WireGuard tunnel might itself be TCP (needing reliability) — but the TUNNEL PROTOCOL ITSELF doesn't need to duplicate that reliability at its own layer, for a specific reason: TCP-over-TCP (running a TCP-based tunnel carrying TCP traffic inside it) produces a well-documented pathological interaction called "TCP meltdown" — the inner TCP connection's own retransmission/congestion control logic fights against the outer tunnel TCP connection's retransmission/congestion control logic, each unaware of the other, producing dramatically WORSE performance than either layer alone would. UDP, having no such built-in reliability/congestion machinery to conflict, avoids this entirely — the inner protocol's own reliability mechanism (if any) operates cleanly, with the tunnel just carrying opaque encrypted bytes without adding a second, conflicting reliability layer on top.
