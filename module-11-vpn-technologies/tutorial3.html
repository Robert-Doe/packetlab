Module 11 — Exam Practice

Answer out loud before revealing each answer.
Q1. List, in order, the four things wg-quick up actually does when bringing up a tunnel.
A: (1) Creates a new virtual network interface (e.g. wg0). (2) Loads the [Interface] section (private key, tunnel-internal IP) onto that interface. (3) Loads each [Peer] section (their public key, real-world Endpoint, and AllowedIPs). (4) Adds routing table entries so traffic destined for each peer's AllowedIPs is sent out the new interface instead of the normal default route.
Q2. Why does a successful ping to the tunnel-internal address (e.g. 10.10.0.2) constitute real proof the tunnel works, rather than a coincidental success?
A: That address space exists nowhere on the real physical/Wi-Fi network -- it's purely virtual, created only because both machines' wg-quick commands added routing entries for it. A successful ping requires the OS routing table to correctly direct the packet to the WireGuard interface, WireGuard to encrypt and re-wrap it as a real UDP packet to the peer's actual endpoint, the peer to decrypt and deliver it to its own virtual interface, and that peer's OS to recognize the destination as its own and reply -- a complete, genuine multi-step round trip, not something that could succeed by coincidence.
Q3. What specifically does the Noise IK handshake pattern assume about both peers BEFORE the handshake begins, and why does this matter for WireGuard's config file design?
A: It assumes both peers already know each other's static public keys in advance, from prior out-of-band exchange. This is exactly why WireGuard config files hardcode both sides' public keys into each other's [Peer] section ahead of time -- the handshake's job is not to negotiate or discover identity, only to establish a fresh session key while authenticating using those already-known static keys.
Q4. Explain precisely what problem WireGuard's Noise-based handshake solves that Module 00a's raw Diffie-Hellman demo did not.
A: Authentication. Module 00a's DH demo established a shared secret with zero verification of either party's identity -- an impersonator could have participated and the protocol would never notice (the exact man-in-the-middle vulnerability Module 00a's own deep theory covered). WireGuard's Noise IK handshake combines the same underlying DH key exchange mathematics (via X25519) with proof of possession of a known, pre-configured private key, closing that authentication gap.
Q5. Explain "TCP-over-TCP meltdown" and why it motivates WireGuard's choice of UDP as its transport protocol.
A: If a tunnel protocol itself runs over TCP while carrying TCP traffic inside it, the inner connection's own retransmission/congestion-control logic and the outer tunnel connection's retransmission/congestion-control logic operate independently and unaware of each other, producing pathological interactions that degrade performance dramatically worse than either layer alone. UDP has no such built-in reliability/congestion machinery to conflict with an inner protocol's own mechanisms, so WireGuard uses UDP as its transport, letting whatever's actually inside the tunnel (which might be TCP) handle its own reliability cleanly without a second, conflicting layer imposed on top.
Q6. Why does the tutorial specify capturing on the REAL network interface, not the WireGuard (wg0) interface, to observe the encrypted opacity described in Step 4?
A: Capturing on the wg0 interface itself would show traffic AFTER WireGuard has already decrypted it (on the receiving side) or BEFORE it's been encrypted (on the sending side) -- i.e., the plaintext inner traffic, which defeats the point of the demonstration. Capturing on the REAL underlying network interface shows exactly what an observer positioned anywhere on the actual physical/Wi-Fi network path would see: only the outer, encrypted UDP wrapper, with the inner plaintext traffic never exposed at that vantage point.
Q7. Synthesis: connect AllowedIPs' role in this module to Module 05's routing table concept, and explain why widening it (Exercise 1) changes tunnel behavior from point-to-point to site-to-site.
A: AllowedIPs serves double duty: it's both a routing table entry (which destinations get sent through this tunnel interface, exactly Module 05's routing table concept) AND a cryptographic authorization boundary (WireGuard will only accept decrypted packets FROM a peer if their source address falls within that peer's configured AllowedIPs, rejecting anything outside it). A narrow /32 AllowedIPs (point-to-point) only routes traffic to that one specific tunnel address. Widening it to a full subnet means an entire remote network's address range gets routed through the tunnel -- transforming the tunnel from "a private link between exactly two tunnel addresses" into "a gateway routing an entire remote LAN's traffic," which is precisely what site-to-site VPN means operationally.
