Module 11 — Tutorial

Goal: generate a real, cryptographically valid WireGuard tunnel configuration, then actually bring the tunnel up between two machines you control, and watch Wireshark show you nothing useful at all — the point.

Step 1 — generate real keys

cd module-11-vpn-technologies
python -m venv venv && venv\Scripts\activate
pip install -r requirements.txt
python wg_keygen.py
Expected: a real 32-byte X25519 private/public key pair, base64-encoded exactly like wg genkey would produce. The script independently re-derives the public key from the private key and confirms they match — this is genuinely how WireGuard's own key relationship works, verified during this module's build.
node wg_keygen.js
Same verification, using Node's built-in crypto module instead — no npm dependency needed.

Step 2 — generate a real two-peer tunnel config

python wg_config_generator.py
Expected: two complete .conf files, laptop.conf and vps.conf. Confirmed during this module's build: each side's listed peer PublicKey is the REAL, independently-derived public key of the other side's PrivateKey — these aren't placeholder-looking strings, they're a genuinely matched key pair you could paste into real WireGuard installations right now.

Step 3 — bring up a real tunnel (requires 2 machines/VMs + WireGuard installed)

Install WireGuard on two machines you control — your Module 09 virtual lab's two VMs work well for this, or any two devices on your own network. Get official installers from wireguard.com/install (this course doesn't download anything on your behalf).

  1. Run python wg_config_generator.py, save the two outputs as laptop.conf and vps.conf.
  2. Edit the Endpoint line in laptop.conf to point at whatever address your "vps" machine is actually reachable at on your network (its real LAN IP is fine for a lab test).
  3. Copy each config to its respective machine.
  4. On each machine: wg-quick up ./laptop.conf (or vps.conf).
  5. From "laptop," run ping 10.10.0.2 — this is the TUNNEL address, not either machine's real IP.
Expected: the ping succeeds, routed entirely through the encrypted tunnel, even though 10.10.0.0/24 doesn't exist anywhere on your real network — WireGuard created it.

Step 4 — capture it in Wireshark and see nothing

Capture on either machine's real network interface (not the WireGuard interface itself) while pinging across the tunnel. Filter to udp.port == 51820.

Expected: you'll see UDP packets between the two real IPs, but the payload is opaque encrypted bytes — no ICMP, no readable structure, nothing resembling the ping you just sent. Compare this directly to Module 02's Wireshark capture of a plaintext HTTP request, where every header was fully readable. This IS what "VPN" concretely means at the packet level: your actual traffic (the ping, and anything else routed through the tunnel) is completely invisible to anything observing the real network path — only the tunnel's own encrypted UDP wrapper is visible.

Exercises before Module 12

  1. Widen AllowedIPs for a site-to-site scenario. Modify wg_config_generator.py/.js so instead of a /32 (just the other peer's tunnel address), AllowedIPs covers a whole subnet — simulating "route my entire home LAN through this tunnel to a remote site's entire LAN," not just point-to-point.
  2. Add a 3rd peer. Extend the generator to build a 3-peer configuration (a simple hub-and-spoke, one central peer two others connect to). You'll need to add multiple [Peer] blocks to the hub's own config.
  3. Compare to Module 07's TCP handshake. WireGuard runs over UDP, not TCP — no 3-way handshake, no connection state machine like Module 07's tcp_state_machine.py. Instead it does its own cryptographic handshake (Noise protocol framework) before any data flows. Research and write 3-4 sentences on why a VPN protocol would choose UDP as its transport despite wanting reliable delivery for the traffic riding inside it.
