Module 06 — Tutorial

Goal: everything you've done as text output in Modules 01-05 becomes something you build visually, on simulated real Cisco hardware, with real IOS syntax — and you get an objective, scriptable way to check whether you built it right.

What this module can and can't do for you. Cisco Packet Tracer is a licensed GUI application (free for anyone via a Cisco Networking Academy / Skills for All account) — it's not something this course can install, launch, or click through on your behalf. This module gives you exact, tested topology specs and real IOS command sequences to type yourself, plus topology_validator.py/.js — which ARE fully working, tested code — to check your results against. Nobody but you can verify the Packet Tracer side; the validator's job is to make that verification objective instead of "does it look right to me."

Step 0 — get Packet Tracer

Go to Cisco's Networking Academy site and sign up for a free Skills for All account, then enroll in the free "Getting Started with Cisco Packet Tracer" self-paced course — this gives you the download and license at no cost. This is the standard, legitimate path every CCNA student uses; there's no other officially supported way to obtain it.

Step 1 — Topology 1: two PCs, one switch

Follow topology_configs/topology1_two_pcs_one_switch.md exactly. No routing, no IOS config beyond IP addressing the PCs — this is Module 03's switch simulator made visual.

Expected: ping 192.168.1.20 from PC0 succeeds. Switch to Simulation mode, re-send the ping, and step through it packet-by-packet — you'll see the ARP broadcast flood, the unicast reply, then the actual ICMP exchange, exactly matching Module 03's switch_sim.py log output, just rendered as animated packets instead of print statements.

Step 2 — Topology 2: two LANs, one router hop

Follow topology_configs/topology2_two_lans_one_hop.md. Type every IOS command yourself rather than copy-pasting — the point is muscle memory, not just a working topology.

cd module-06-packet-tracer-mastery
python topology_validator.py topology_configs/topology2_two_lans_one_hop.json
Expected: the validator's show ip route output for R1 and R2 should match your real Packet Tracer show ip route output line for line. If it doesn't, re-read the command reference's note on no shutdown first — it's the most common single mistake.

Step 3 — Topology 3: the Module 05 chain, rebuilt on real IOS

Follow topology_configs/topology3_three_router_chain.md. This is deliberately identical addressing to Module 05's static_routing.py.

python topology_validator.py topology_configs/topology3_three_router_chain.json
Expected: validator output matches your Packet Tracer show ip route AND matches Module 05's static_routing.py trace for the same source/destination pairs — three independent representations (pure-Python simulation, JSON-driven validator, real simulated Cisco IOS) of the same 3-router topology, all agreeing.

Step 4 — traceroute, for real

On PC-A's Command Prompt in Topology 3:

tracert 198.51.100.20
Expected: exactly 3 hops listed (R1, R2, R3's addresses) before reaching the destination — traceroute works by sending packets with increasing TTL and reporting whichever router's interface sends back the "TTL exceeded" message at each hop, which is also why the hop count you see here should exactly match the hop 1/2/3 lines topology_validator.py printed.

Exercises before Module 07

  1. Break something on purpose. In Topology 3, remove R2's static route to 198.51.100.0/24 (no ip route 198.51.100.0 255.255.255.0 10.0.23.2) and re-run the ping from PC-A. Confirm it now fails, and use traceroute to see exactly where it dies. Update topology3_three_router_chain.json to remove the same route and confirm the validator predicts the same failure point.
  2. Add a 4th topology of your own design. Using your real home network's subnet (from Module 01) as inspiration, design a small topology with 2 routers and 3 LANs that mirrors something like your actual house's segmentation. Write its JSON file, build it in Packet Tracer, and validate both.
  3. Convert Topology 2 to use RIP instead of static routes. Replace the ip route commands with: 
    router rip
 version 2
 network 192.168.10.0
 network 10.0.1.0
    (equivalent commands on R2 for its own networks). Confirm show ip route now shows a R code instead of S for the remote network, and connect this back to Module 05's distance-vector simulation — you're now looking at real RIP-learned routes instead of Bellman-Ford math on paper.
Before Module 07: you should be comfortable typing IOS interface and static-route configuration from memory, and confident reading show ip route output well enough to predict a ping's path before running it. Module 07 goes back down to the Transport layer you briefly touched in Module 02 — this time building real client/server socket programs and watching TCP's actual state machine (not just the 3-way handshake) play out.
