Module 06 — Exam Practice

Answer out loud before revealing each answer.
Q1. Why does IOS require a separate "enable" step to reach Privileged EXEC mode, rather than granting full configuration access immediately upon connecting?
A: It's a deliberate graduated-privilege safety design: User EXEC mode allows only harmless, read-only commands, so simply connecting to a router (even without authorization to make changes) cannot accidentally or immediately lead to a configuration change. The explicit "enable" step (often password-protected on real hardware) requires a deliberate, separate action before any configuration-capable mode becomes accessible.
Q2. Why do every interface on a Cisco device start administratively down by default, requiring an explicit "no shutdown"?
A: It's a safe-by-default design: a freshly-installed or freshly-configured device should do nothing on any interface until a human explicitly activates it, preventing unintended traffic flow through a partially- or incorrectly-configured interface. This is why forgetting "no shutdown" is the single most common configuration mistake -- the interface silently does nothing, with no error message, until this explicit command is given.
Q3. Why does "ip route"/"ip address" require dotted-decimal subnet masks rather than CIDR notation, when CIDR is used everywhere else in modern networking documentation?
A: This is a genuine, historical syntax inconsistency in real Cisco IOS -- these specific commands were defined before CIDR notation became universal, and their dotted-decimal mask requirement has remained for backward compatibility ever since, even though other parts of IOS and virtually all modern documentation use CIDR notation. It's not derivable from first principles -- it must simply be known/memorized as a real quirk of the actual command syntax.
Q4. What's the operational difference between a route shown with an 'S' code versus an 'R' code in show ip route, beyond how each was entered?
A: An 'S' (static) route has no self-healing behavior -- it remains in the routing table exactly as configured, even if its next-hop becomes unreachable, until a human manually changes or removes it. An 'R' (RIP-learned) route is dynamic -- if the underlying connectivity that route depends on fails, RIP's own convergence process will eventually detect this (subject to the count-to-infinity/split-horizon behaviors covered in Module 05) and update or remove the route automatically, without human intervention.
Q5. Why does RIPv2 support VLSM-designed networks correctly while RIPv1 does not?
A: RIPv1 was designed under classful addressing assumptions and does not carry subnet mask information in its route advertisements at all -- it assumes a network's mask can be inferred from its class (A/B/C), which fails for any VLSM-designed network using non-default subnet masks. RIPv2 added explicit subnet mask information to its advertisements specifically to support CIDR/VLSM-designed networks correctly, which is why `version 2` is specified explicitly in this module's configuration rather than relying on RIP's older default.
Q6. Explain, mechanically, why Packet Tracer's simulated traceroute produces hop counts that exactly match a pure-Python simulation (topology_validator.py) of the same topology.
A: Both are correctly implementing the identical underlying mechanism: TTL-exhaustion-triggered ICMP "Time Exceeded" replies from each router along the path (Module 01's deep theory covers this precisely). Packet Tracer's simulated IOS genuinely implements real IP/ICMP semantics rather than faking hop counts, and `topology_validator.py`'s longest-prefix-match trace logic reasons about the identical routing decisions each real router would make -- two independent, correct implementations of the same real mechanism naturally agree.
Q7. Synthesis: why does this course insist you type every IOS command yourself in Packet Tracer rather than providing a pre-built, importable topology file?
A: Command syntax fluency (recalling the exact sequence of `interface`, `ip address`, `no shutdown`, `ip route` etc. without looking it up) is itself a real, testable skill -- both for practical network administration and for any timed technical assessment (a comprehensive exam, a certification exam, a technical interview) that expects you to configure a device live rather than recognize a pre-written configuration. Copy-pasting or importing a working configuration would produce an identical-LOOKING result while completely skipping the actual skill being built -- muscle memory for the commands themselves, not just recognition of correct output.
