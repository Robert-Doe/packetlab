Module 14 — Tutorial

Goal: detect a port scan and a C2 beacon in real Zeek log format using your own statistical reasoning, then write and fire real Suricata-syntax signature rules — before installing the real tools in Module 09's lab.

Step 1 — generate synthetic traffic and find the attacks in it

cd module-14-network-security-monitoring
python generate_conn_log.py
python conn_log_analyzer.py
Expected: the port-scan detector finds 192.168.1.30 touching 15+ distinct ports on 192.168.1.99 within 10 seconds. The beaconing detector finds 192.168.1.10 -> 203.0.113.66:443 with ~60-second intervals and low jitter. Neither pattern was labeled in the log file — both were found purely from statistical properties of the connection records.
A real refinement made during this module's own testing: the first version of the beaconing detector also flagged the port scan (fast, perfectly-regular connections are "low jitter" too). Adding a same-destination-port requirement and a minimum-interval threshold fixed this — real beacons hit the same port repeatedly; a scan doesn't. This is a genuine lesson about detection engineering: a single signal is rarely enough, and false-positive overlap between detectors is normal, not a bug to be embarrassed about.

Step 2 — the JS variant, and cross-format compatibility

node generate_conn_log.js
node conn_log_analyzer.js conn_node.log
python conn_log_analyzer.py conn_node.log
Expected: the Python analyzer correctly reads the Node-generated log file and finds the identical patterns — confirmed during this module's build. The Zeek conn.log TSV format is just text; nothing about it is Python- or Node-specific.

Step 3 — Suricata/Snort-style signature matching

python mini_ids_rules.py
Expected: 4 alerts out of 7 sample HTTP-like packets — a SQL injection attempt, a directory traversal attempt, a cleartext password field, and a suspicious User-Agent string. The 3 benign packets produce no alerts. Read DEFAULT_RULES_TEXT — this is genuine Suricata/Snort rule syntax, not an invented format.

Work through wireshark_mastery_checklist.html completely, against any capture you saved from an earlier module. Pay special attention to Statistics → Conversations — sort by bytes and confirm you can identify the largest data transfer in any capture within seconds.

Exercises before Module 15

  1. Add a data-exfiltration detector. A large, one-directional data transfer (huge orig_bytes, tiny resp_bytes) to an unfamiliar external host is a classic exfiltration signature. Add detect_large_exfil() to both language variants.
  2. Write a rule that fires on your own Module 08 traffic. Add a rule to mini_ids_rules.py/.js matching the marker string from Module 08's HTTP server (LAYER-DEMO-PAYLOAD-92f1 from Module 02, or Module 08's own hand-rolled server's body text) and confirm it fires against a real captured request.
  3. Reduce false positives further. Real production IDS tuning is mostly about reducing false positives without missing real attacks. Add a "well-known good beacon" allowlist (e.g., legitimate periodic health-check traffic) to detect_beaconing and explain, in a few sentences, why allowlisting known-good regular traffic is usually safer than trying to make the detection threshold itself smarter.
Before Module 15: you should be able to explain, from memory, what makes beaconing traffic statistically different from normal human browsing, and be comfortable reading and writing basic Suricata-style signature rules.
