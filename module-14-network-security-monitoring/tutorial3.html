Module 14 — Exam Practice

Answer out loud before revealing each answer. This module's base-rate question is a classic comprehensive-exam favorite -- make sure you can actually do the arithmetic, not just recite the conclusion.
Q1. Why does the beaconing detector use the coefficient of variation (stdev/mean) rather than raw standard deviation alone?
A: Raw standard deviation measures absolute variability, not comparable across beacons with different mean intervals -- a beacon checking in every 300 seconds would appear to have "larger" variability than one checking in every 5 seconds even if both are equally precise RELATIVE to their own timing. The coefficient of variation scales variability by the mean, correctly identifying both as similarly suspicious if their timing precision is proportionally similar, regardless of the absolute interval length.
Q2. In Suricata/Snort rule syntax, distinguish the "header" from the "options," and explain what sid is for.
A: The header (`action protocol src_ip src_port -> dst_ip dst_port`) specifies WHICH traffic the rule considers at all (action to take, protocol, source/destination). The options (in parentheses) specify the actual matching CONDITIONS (content patterns, case sensitivity) and metadata (message text, signature ID). sid (signature ID) is a required, globally unique identifier letting a rule be referenced, tuned, or disabled individually without needing to match on its full text content.
Q3. Work through the base rate fallacy arithmetic: a detector has a 1% false positive rate, is run against 2,000,000 connections per day, of which 20 are actually malicious (assume perfect recall). How many false positives versus true positives would an analyst see?
A: False positives: 2,000,000 x 1% = 20,000. True positives: 20 (given). The analyst sees roughly 20,000 false alarms for every 20 real attacks -- over 99.9% of all alerts are noise, despite the detector's seemingly excellent 99% accuracy. This is the core arithmetic behind "alert fatigue" in real Security Operations Centers.
Q4. Precisely define precision and recall, and explain why improving one often degrades the other.
A: Precision = True Positives / (True Positives + False Positives) -- "of everything flagged, how much was real." Recall = True Positives / (True Positives + False Negatives) -- "of everything real, how much was caught." A detector tuned to catch more real attacks (higher recall, e.g. loosening thresholds) will typically also flag more borderline/ambiguous benign cases (lower precision). A detector tuned to only fire when very confident (higher precision) will typically miss some subtler real attacks (lower recall) -- the two generally trade off against each other along a continuous tuning spectrum.
Q5. Why does content-based signature matching (mini_ids_rules.py) fundamentally miss novel attacks that behavioral detection (conn_log_analyzer.py) might catch, and vice versa -- what does behavioral detection fundamentally miss that signature matching catches precisely?
A: Content matching can only detect patterns explicitly defined in advance -- a novel attack using different exact bytes for the same underlying technique evades it entirely. Behavioral detection catches statistically anomalous PATTERNS regardless of specific byte content, but cannot identify WHICH specific known threat is present, only that something looks unusual -- and it's inherently more prone to false positives on legitimate but unusual traffic. Signature matching, in exchange, gives precise, high-confidence identification ("this is signature X") for KNOWN threats specifically, something purely statistical detection cannot provide.
Q6. Why did the first version of detect_beaconing() also flag the synthetic port scan, and what does the fix reveal about detection engineering generally?
A: Fast, perfectly-regular connection timing (low jitter) is a property BOTH beaconing and a fast automated port scan share -- the original jitter-only check couldn't distinguish them. The fix (requiring same-destination-port and a minimum interval) added a DIFFERENT distinguishing signal rather than tightening the existing threshold. This reveals a general detection-engineering lesson: fixing a false positive by finding a genuinely distinguishing FEATURE is usually more robust than fixing it by adjusting a threshold, which often just shifts the boundary rather than resolving the underlying ambiguity.
Q7. Synthesis: why do real production security programs run signature-based IDS (Suricata/Snort) AND behavioral/statistical detection AND a SIEM (Module 15) together, rather than picking the "best" one?
A: Each approach has a distinct, non-overlapping blind spot: signature matching misses novel/obfuscated attacks; behavioral detection misses precise identification and is prone to its own false positive patterns; and neither alone provides the CORRELATION and historical/contextual analysis a SIEM enables (connecting a signature alert to a behavioral anomaly to a host-level log entry, potentially across a long time window). Defense in depth means layering DIFFERENT-FAILURE-MODE detection mechanisms so that an attack technique evading one layer is more likely to be caught by another -- the same underlying logic as Module 09's network segmentation, applied to detection instead of network access.
