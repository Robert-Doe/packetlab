1. Zeek's conn.log Format, Field By Field

parse_conn_log()'s field unpacking — ts, uid, orig_h, orig_p, resp_h, resp_p, proto, service, duration, orig_bytes, resp_bytes — corresponds EXACTLY to real Zeek conn.log's own (simplified, tab-separated) column structure.

FieldMeaning
tsTimestamp (Unix epoch seconds, floating point for sub-second precision) — the SAME representation Module 18's libpcap format uses for packet timestamps, just at the CONNECTION level (one row per connection) rather than the PACKET level (one row per packet)
uidA unique identifier Zeek assigns to each connection — lets you cross-reference the SAME connection across Zeek's OTHER log files (http.log, dns.log, etc.), a genuinely useful correlation key in real incident investigation (directly relevant to Module 18's forensic reconstruction skillset)
orig_h / orig_pThe connection ORIGINATOR's host and port — "orig" specifically because Zeek doesn't assume which side is the "client" in a strict sense, just which side initiated the connection
resp_h / resp_pThe RESPONDER's host and port
durationHow long the connection lasted, in seconds
orig_bytes / resp_bytesTotal payload bytes sent in EACH direction — this asymmetry is EXACTLY what a real exfiltration detector (this module's own Exercise 1) would key on: large orig_bytes, tiny resp_bytes, to an unfamiliar host

2. Port Scan Detection — The Sliding Window, Traced Completely

window_ports = set()
window_start_ts = None
for r in conns:
    if window_start_ts is None or r["ts"] - window_start_ts > window_seconds:
        window_start_ts = r["ts"]
        window_ports = set()
    window_ports.add(r["resp_p"])
    if len(window_ports) >= min_distinct_ports:
        findings.append(...)
        break

Connections (already sorted by timestamp), same src->dst pair:
  ts=100, port=22
  ts=101, port=23
  ts=102, port=80
  ts=115, port=443    <- 115-100 = 15s, EXCEEDS window_seconds(10) -- RESETS
  ts=116, port=8080
  ts=117, port=3389

Trace:
  ts=100: window_start=None -> RESET. window_start=100. Add port 22. {22} (1 port)
  ts=101: 101-100=1, within window. Add port 23. {22,23} (2 ports)
  ts=102: 102-100=2, within window. Add port 80. {22,23,80} (3 ports)
  ts=115: 115-100=15 > 10 -- WINDOW RESETS. window_start=115. window_ports={}
          Add port 443. {443} (1 port)
  ts=116: 116-115=1, within window. Add port 8080. {443,8080} (2 ports)
  ts=117: 117-115=2, within window. Add port 3389. {443,8080,3389} (3 ports)

Final: only 3 distinct ports within any SINGLE 10-second window -- below
min_distinct_ports(15) -- NO alert, despite 6 total connections across
the whole log. This is EXACTLY the point of a SLIDING/RESETTING window
rather than a simple "count everything ever seen": scattered,
infrequent port touches over a long period look nothing like the tight,
rapid burst a real port scan produces.
Why does the window RESET (rather than sliding continuously, dropping only the OLDEST entry) when a gap exceeds window_seconds? This is a genuine, deliberate simplification worth understanding precisely: this module's implementation uses a "tumbling window" reset strategy (start fresh whenever a gap is detected) rather than a true continuously-sliding window (which would require tracking EVERY connection's exact age relative to the CURRENT connection, discarding individually as each ages out). The tumbling approach is simpler to implement and reason about, and for the specific pattern being detected (a CONCENTRATED BURST of port touches), correctly identifies genuine scan bursts — the tradeoff is a scan that happens to straddle EXACTLY a reset boundary could theoretically be undercounted, a real, honest limitation worth knowing about rather than assuming this detector is mathematically perfect.

3. Jitter Ratio — The Actual Statistic, Computed By Hand

The JITTER RATIO (this module's own code: jitter_ratio = stdev_interval / mean_interval) is formally known as the COEFFICIENT OF VARIATION — a standard statistical measure of RELATIVE variability, worth computing by hand at least once to fully internalize.

Worked scenario: computing jitter ratio for a genuinely regular (beacon-like) sequence

Connection timestamps: 0, 60, 121, 179, 241 (roughly every 60 seconds)

Intervals between consecutive connections:
  60-0=60, 121-60=61, 179-121=58, 241-179=62

Mean interval: (60+61+58+62)/4 = 241/4 = 60.25

Deviations from mean: 60-60.25=-0.25, 61-60.25=0.75, 58-60.25=-2.25, 62-60.25=1.75
Squared deviations: 0.0625, 0.5625, 5.0625, 3.0625
Sum of squared deviations: 8.75
Population variance: 8.75 / 4 = 2.1875
Population stdev: sqrt(2.1875) ≈ 1.479

Jitter ratio: 1.479 / 60.25 ≈ 0.0245

0.0245 is FAR below max_jitter_ratio(0.15) -- this sequence would be
flagged as beaconing: its timing variance is a tiny FRACTION of its
average interval, exactly the "suspiciously regular" signature a
human-driven browsing session essentially never produces by chance.
Why divide by the MEAN (producing a RATIO) rather than just using the raw standard deviation directly as the detection threshold? A FIXED standard-deviation threshold would behave very differently for beacons with DIFFERENT average intervals — a beacon checking in every 5 seconds with ±0.5 seconds of jitter (highly regular, relatively) has a SMALLER raw stdev than a beacon checking in every 300 seconds with ±10 seconds of jitter (ALSO highly regular, relatively, but a LARGER raw stdev) — a single fixed stdev threshold would incorrectly treat these very differently-scaled but EQUALLY suspicious patterns inconsistently. Dividing by the mean NORMALIZES the variability relative to the interval's own scale, making the SAME 0.15 threshold meaningfully comparable across beacons with wildly different check-in frequencies — a genuinely important statistical normalization technique, not an arbitrary implementation detail.

4. Why Timing Alone Can't Distinguish Beaconing From Scanning

This module's own real, documented bug (the first beaconing detector also flagged the port scan) is worth understanding completely, not just noting as a historical footnote.

Precisely why a fast port scan ALSO produces a low jitter ratio

A rapid, automated port scan often sends probes at VERY consistent,
tight intervals -- e.g., exactly every 0.05 seconds, because it's
generated by a simple, tight software loop with essentially no
variability at all (arguably MORE mechanically regular than many real
beacons, which often have realistic network-delay jitter). Computing a
jitter ratio on THESE intervals would find EXTREMELY low jitter --
exactly the same "suspiciously regular" signal the beaconing detector
was designed to catch.

The genuine, real fix (documented directly in this module's own code
comments) required TWO additional constraints working TOGETHER, not
just tuning the jitter threshold:
  1. SAME DESTINATION PORT required (by_src_dst_port groups by port too,
     not just src/dst host) -- a scan touches MANY DIFFERENT ports by
     definition; a beacon calls home to the SAME service/port every time.
  2. min_interval_seconds -- excludes scan-speed (sub-second) intervals
     outright, since real C2 beacons operate on human-meaningful
     timescales (seconds to minutes), not scan-speed milliseconds.
Comprehensive exam framing: "A detection engineer observes that timing regularity alone produces a false positive on scan traffic. Should they fix this by making the jitter threshold STRICTER, or by adding an additional, DIFFERENT signal? Justify your answer using this module's own real example." Adding a DIFFERENT signal (same-port constraint, minimum interval) is the correct fix, not tightening the SAME signal further — this module's own documented finding demonstrates WHY: both port scans and beacons can be ARBITRARILY regular in timing (a scan's regularity is a function of the scanning TOOL's implementation, not inherently different in KIND from a beacon's regularity) — no jitter THRESHOLD, however finely tuned, can reliably separate two populations that can both legitimately produce near-zero jitter. A genuinely DIFFERENT dimension (destination port constancy, which scans and beacons behave OPPOSITELY on by their very nature) is what actually provides real discriminating power — this is a general, transferable detection-engineering principle: when one signal produces overlapping false positives, look for an ORTHOGONAL signal, not just a stricter threshold on the same one.

5. The Base Rate Fallacy — Why "99% Accurate" Can Still Be Useless

Worked numerical scenario: why a "99% accurate" detector can still produce mostly false alarms

Suppose, on a real large network, genuine beaconing malware exists on
exactly 1 out of 10,000 hosts (a realistic, LOW base rate -- most hosts
are NOT compromised at any given time).

A detector that's "99% accurate" -- meaning it correctly flags 99% of
TRUE beacons (very few missed) AND correctly clears 99% of TRUE benign
hosts (only 1% false positive rate) -- applied across all 10,000 hosts:

  True beacon (1 host): 99% chance correctly flagged -> ~1 true alert
  Benign hosts (9,999 hosts): 1% false positive rate ->
    9,999 * 0.01 ≈ 100 FALSE alerts

Total alerts: ~101, of which only ~1 is real -- meaning even at "99%
accuracy," roughly 99% of the ALERTS THEMSELVES are false positives,
purely because the true base rate of actual beaconing is so low that
even a small false-positive PERCENTAGE produces an overwhelming ABSOLUTE
number of false alerts.
Why does this matter for how this module's own detectors should actually be evaluated in a real deployment? A detector's per-class accuracy percentages ALONE are insufficient to judge its real-world usefulness — the ACTUAL BASE RATE of the thing being detected (genuinely rare, for real malicious beaconing on most networks) means even a well-tuned detector will produce MANY MORE false alerts than true ones in absolute terms, unless its false-positive rate is EXTREMELY low (far lower than a naively-impressive-sounding "99%"). This is EXACTLY why this module's own Exercise 3 (add an allowlist for known-good regular traffic, e.g., legitimate health-check pings) is framed as often SAFER than trying to make the detection threshold itself smarter — explicitly excluding KNOWN sources of false positives reduces the effective false-positive rate directly and reliably, rather than hoping a single numeric threshold can somehow thread an impossibly fine needle between all true and false cases simultaneously.

6. Suricata/Snort Rule Syntax, Decoded Completely

Worked scenario: fully decoding a real rule from this module's own DEFAULT_RULES_TEXT

alert tcp any any -> any any (msg:"Possible SQL injection attempt"; content:"OR 1=1"; nocase; sid:1000001;)

alert       -- ACTION: generate an alert (vs. "drop," "pass," etc. in
               real Suricata -- this module's engine only implements
               the alert action, per its own honest scope)
tcp         -- PROTOCOL: match TCP traffic
any any     -- SOURCE IP, SOURCE PORT: "any" matches everything (this
               module's engine simplifies matching to ignore these
               entirely, per its own header comment -- a real Suricata
               rule could narrow these to specific IPs/ports)
->          -- DIRECTIONAL operator: traffic flowing FROM source TO
               destination (Suricata also supports <> for bidirectional)
any any     -- DESTINATION IP, DESTINATION PORT
(...)       -- RULE OPTIONS, semicolon-separated:
  msg:"..."     -- human-readable description shown when this rule fires
  content:"..." -- the literal byte/string pattern to search for in the
                   payload -- THIS is the actual detection logic
  nocase        -- perform the content match CASE-INSENSITIVELY
  sid:1000001   -- Signature ID -- a unique, stable identifier for THIS
                   specific rule, used for tracking/tuning/referencing
                   it independently of its (potentially-changing)
                   message text
Why does every real Suricata/Snort rule require a unique sid, separate from its human-readable msg? The msg text is meant for HUMANS reading an alert and can change over time (a rule maintainer might improve the wording) without that being a meaningfully different rule. The sid is the STABLE, MACHINE-REFERENCEABLE identity of a specific detection logic — used for suppressing/tuning a SPECIFIC rule (a real SOC might disable sid:1000001 specifically if it's producing too many false positives, without touching any other rule), tracking which rule fired in log analysis tooling, and cross-referencing a specific rule across different rule-set versions — a genuinely necessary separation between "what a human reads" and "what a machine tracks," directly parallel to Module 18's uid field serving an analogous machine-reference role for connections.

7. Full Code Walkthrough — detect_beaconing()'s Full Logic

if len(conns) < min_occurrences:
    continue
...
if len(intervals) < min_occurrences - 1:
    continue

These TWO separate minimum-count checks matter for slightly different reasons: min_occurrences ensures there's ENOUGH DATA for the statistical reasoning (jitter ratio) to be MEANINGFUL at all — a statistic computed from just 2-3 data points is not reliable evidence of a genuine PATTERN, versus coincidence. The second check (len(intervals) < min_occurrences - 1) is a defensive consistency check — with N connections there are always exactly N-1 intervals between them, so this check is technically redundant GIVEN the first check already passed, but serves as an explicit, readable safeguard against any future code change that might decouple these two counts unexpectedly — a genuinely reasonable defensive-programming habit, even when technically provably redundant given the current logic.

9. Troubleshooting And Common Confusions

Common mistake: assuming "no alert fired" means "no attack happened." Every detector in this module operates on SPECIFIC, NAMED statistical signatures (port-count-in-a-window for scans, timing-regularity-plus-port-constancy for beacons) — an attack that doesn't match these SPECIFIC patterns (a slow, low-and-slow scan spread over hours instead of a tight burst; a beacon with deliberately injected random jitter specifically to evade jitter-ratio detection, a REAL evasion technique actual malware authors use) would produce NO alert from these specific detectors, without that meaning the network is actually clean. Detection rules always have a SCOPE — understanding precisely what a detector DOES and DOES NOT cover is as important as knowing it exists at all.
