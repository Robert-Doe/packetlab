Module 14 — Deep Theory: Detection Engineering, Formally

1. Jitter Ratio, Formally Defined

conn_log_analyzer.py's beaconing detector computes jitter_ratio = stdev(intervals) / mean(intervals) — this is formally the COEFFICIENT OF VARIATION, a standard statistics concept measuring RELATIVE variability (variability scaled by the mean), distinct from raw standard deviation (which measures ABSOLUTE variability, not comparable across datasets with different means). Using the coefficient of variation rather than raw standard deviation matters here specifically because a "regular" beacon checking in every 5 seconds and one checking in every 300 seconds should both be flagged as suspicious if their TIMING PRECISION is similarly tight relative to their own interval — raw standard deviation alone would make the 300-second beacon's variability look artificially "larger" even if it's equally precise proportionally.

2. Suricata/Snort Rule Anatomy, Fully Formal

A rule's HEADER (action protocol src_ip src_port -> dst_ip dst_port) and OPTIONS (in parentheses) are two structurally separate parts:

alert tcp any any -> any any (msg:"..."; content:"OR 1=1"; nocase; sid:1000001;)
^     ^   ^^^ ^^^    ^^^ ^^^   ^--- options: matching conditions + metadata
|     |   +-- source (any host, any port)
|     +------ protocol
+------------ action (what to do on match: alert, drop, pass, reject)

content performs a literal byte-substring match against the packet payload — nocase makes it case-insensitive. sid (signature ID) is a required, globally-unique identifier for the rule, used for referencing, tuning, and disabling specific rules without needing to match on the rule's full text.

Comprehensive exam framing: "Why is content-based signature matching (this module's mini_ids_rules.py) fundamentally limited compared to behavioral/statistical detection (conn_log_analyzer.py), and why do production security programs run BOTH rather than choosing one?" Content matching can only detect patterns it was EXPLICITLY told to look for — a novel attack using different exact bytes for the same underlying technique (e.g., a differently-encoded SQL injection payload) sails through undetected. Behavioral detection catches STATISTICALLY anomalous patterns regardless of the specific bytes involved, but is inherently fuzzier (more prone to false positives, as this module's own port-scan/beaconing overlap demonstrated) and can't identify WHICH specific known threat is present, only that something looks unusual. Running both provides defense in depth against each approach's distinct blind spot.

3. The Base Rate Fallacy: Why "99% Accurate" Detection Can Still Be Useless

This is one of the single most important, and most frequently misunderstood, concepts in real detection engineering, and a classic comprehensive-exam topic. Consider a detector with a 1% false positive rate, run against 1,000,000 connections per day, where only 10 of those connections are ACTUALLY malicious:

True positives (correctly flagged attacks):     ~10 (assuming near-perfect recall)
False positives (benign traffic incorrectly flagged): 1,000,000 x 1% = ~10,000
Brain power: even with a seemingly excellent 99% accuracy rate, an analyst reviewing alerts would see roughly 10,000 false alarms for every 10 real attacks — meaning the overwhelming majority of alerts (over 99.9%) are noise, not signal. This is precisely WHY "alert fatigue" is a genuine, documented, serious problem in real Security Operations Centers, and why the actual practice of detection engineering (this module's own port-scan/beaconing refinement is a small real example) obsesses over minimizing false positive RATE specifically, not just achieving high overall "accuracy" — because the base rate of actual attacks in normal traffic is typically extremely low, making even small false-positive percentages produce overwhelming absolute noise.

4. Precision, Recall, and the Tradeoff Between Them

MetricFormulaWhat it answers
PrecisionTrue Positives / (True Positives + False Positives)"Of everything I flagged, how much was actually real?"
Recall (Sensitivity)True Positives / (True Positives + False Negatives)"Of everything actually real, how much did I catch?"

These trade off against each other: a detector tuned to catch EVERY possible attack (maximize recall) will necessarily flag more borderline/ ambiguous cases too (lower precision, more false positives — exactly Module 14's own beaconing detector before its port-constancy refinement). A detector tuned to only fire when VERY confident (maximize precision) will necessarily miss some real, subtler attacks (lower recall). Real detection engineering is a continuous exercise in choosing where on this tradeoff curve a given detector should sit, based on the actual cost of each error type in context.
