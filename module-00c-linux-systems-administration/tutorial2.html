Module 00c — Deep Theory: Permissions, Process Model, and systemd

1. The Full Permission Model: Beyond rwx

The 9 ordinary permission bits (rwx × owner/group/other) are only part of the story. Three additional bits matter for security work specifically:

BitOn a FILEOn a DIRECTORY
setuid (4000)Executing the file runs it with the FILE OWNER's privileges, not the invoking user's — this is how /usr/bin/passwd (owned by root) lets an ordinary user change their own password despite that requiring a write to /etc/shadow, a root-only file.No effect
setgid (2000)Runs with the file's GROUP privileges instead of the invoking user's group.New files created inside inherit the directory's group, not the creating user's primary group — used for shared team directories.
sticky (1000)Historically affected how the kernel cached the executable; largely meaningless on files today.Only the file's OWNER (or root) may delete/rename files inside, even if the directory itself is world-writable — /tmp's actual real-world use case, confirmed on your own system in the tutorial.
Comprehensive exam framing: "Explain why a setuid binary is a classic privilege-escalation target, and what a security auditor should specifically look for." A setuid-root binary runs with full root privileges regardless of who invokes it — if that binary has ANY exploitable bug (a buffer overflow, per Module 00b; a command injection; an unsafe file operation exploitable via a symlink race), an unprivileged user who can trigger the bug inherits root's privileges through it. An auditor should specifically enumerate all setuid/setgid binaries on a system (find / -perm -4000 -o -perm -2000) and verify each one is both necessary and free of known vulnerabilities — an unnecessary or outdated setuid binary is a disproportionately high-value attack target precisely because of what successfully exploiting it grants.

2. The Linux Process Model, and Why It Matters for Security

Every process has: a Process ID (PID), a Parent PID (PPID, forming a tree rooted at PID 1), a real UID and effective UID (usually the same, EXCEPT for setuid execution — the effective UID becomes the file owner's, while the real UID stays the invoking user's, and it's the EFFECTIVE UID the kernel actually checks for most permission decisions), and a set of open file descriptors. The distinction between real and effective UID is precisely the mechanism setuid relies on, and precisely the mechanism a well-written setuid program must carefully manage (temporarily dropping elevated privileges when they're not needed, a security best practice called "privilege dropping" or "least privilege").

Process isolation and namespaces (a preview of Module 17's containers)

Modern Linux process isolation (the foundation Docker/Kubernetes containers, referenced in the original course's Tier 7, are built on) uses kernel NAMESPACES — separate views of process IDs, network interfaces, mount points, and more, per isolated group of processes — combined with CGROUPS (resource limiting: CPU, memory quotas). A "container" is not a lightweight VM; it's a set of ordinary Linux processes given a restricted, isolated VIEW of the same kernel every other process shares, via namespaces and cgroups. Understanding this distinction (containers share a kernel; VMs each run their own) is directly relevant to reasoning about container escape vulnerabilities as a security topic.

3. systemd's Dependency Model, Formally

heartbeat.service's [Unit] section can declare relationships to other units:

DirectiveMeaning
After= / Before=ORDERING only — doesn't imply the other unit will even be started, just that IF both start, this one starts after/before the other.
Requires=A hard dependency — if the required unit fails, this one is stopped too.
Wants=A soft dependency — pulls the other unit in when this one starts, but doesn't fail this unit if the other one fails.
WantedBy= (in [Install])Which target (e.g. default.target, roughly analogous to old-style runlevels) should pull this unit in when ENABLED — this is what systemctl enable actually wires up.
Why does systemd separate "ordering" (After/Before) from "dependency" (Requires/Wants) as two independent concepts? Because they answer genuinely different questions. Ordering answers "when both of these are starting, which goes first" (e.g., a database should start before an application that connects to it). Dependency answers "does starting this unit require/imply starting that one at all." A unit can declare After= another WITHOUT Requires= it — meaning "if you're both starting, go after that one, but I don't actually need it to be running." Conflating these two questions was a real design weakness of older init systems that systemd specifically set out to fix.

4. Why systemctl --user Instead of System-Wide Units

This module used systemctl --user deliberately. A system unit (/etc/systemd/system/*.service) requires root to install and manage, runs regardless of whether any particular user is logged in, and can bind to privileged ports (below 1024) or access any file on the system. A USER unit (~/.config/systemd/user/*.service) requires no elevated privilege at all, runs within the invoking user's own session and permission boundary, and is started/stopped by that user alone — a real demonstration of the principle of least privilege applied to systemd itself: use the narrowest privilege scope that accomplishes the goal, which for a demo service, is exactly none beyond your own user account.
