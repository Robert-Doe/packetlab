Module 00c — Tutorial

Goal: real filesystem permissions, a real systemd service you bring up and tear down yourself, and real (but non-destructive) package management — on a genuine Linux system, not a simulation.

You need a real Linux shell. WSL Ubuntu (Windows), any real Linux machine, or your Module 09 lab VM all work. Every script below was tested in WSL Ubuntu with systemd running as PID 1.

Step 1 — filesystem hierarchy and permissions, proven not asserted

cd module-00c-linux-systems-administration
chmod +x filesystem_and_permissions.sh
./filesystem_and_permissions.sh
Expected (confirmed during this module's build): a new file defaults to 644 under umask 022; chmod 755 and the equivalent symbolic form produce identical results; a script WITHOUT execute permission genuinely fails with "Permission denied" when you try to run it, and succeeds the instant you chmod +x it; and /tmp's real permissions show 1777 — the sticky bit, proven on your own live system.

Step 2 — a real systemd service, start to finish

cd systemd_service_demo
mkdir -p ~/.config/systemd/user ~/module00c-demo
cp heartbeat.sh ~/module00c-demo/
chmod +x ~/module00c-demo/heartbeat.sh
cp heartbeat.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user start heartbeat.service
Expected: systemctl --user status heartbeat.service shows Active: active (running) with a real PID. Confirmed during this module's build — the service printed a heartbeat every 2 seconds, and every line appeared automatically in journalctl --user -u heartbeat.service with zero explicit logging code, because systemd captures a unit's stdout/stderr into the journal by default.
systemctl --user enable heartbeat.service   # start automatically at login
systemctl --user is-enabled heartbeat.service
systemctl --user stop heartbeat.service
systemctl --user disable heartbeat.service
Confirmed during this module's build: each command's state change is immediately reflected in is-enabled/ is-active — enabled → disabled, active → inactive.
# Clean up when done
rm -f ~/.config/systemd/user/heartbeat.service
rm -rf ~/module00c-demo
systemctl --user daemon-reload

Step 3 — package management, safely (nothing gets installed)

cd ..
chmod +x package_management.sh
./package_management.sh
Expected: real installed-package listings, real dependency metadata for curl, confirmation of which package owns /bin/bash, and a simulated install of cowsay (apt-get install --simulate) showing exactly what would happen — confirmed during this module's build with which cowsay afterward, proving nothing was actually installed.

Exercises before Module 01

  1. Add a second unit that depends on the first. Create a heartbeat-watcher.service with After=heartbeat.service in its [Unit] section, and confirm via systemctl --user list-dependencies that systemd understands the ordering.
  2. Find every SUID binary on your system. find / -perm -4000 -type f 2>/dev/null — research what the setuid bit does (a program runs with its OWNER's privileges, not the invoking user's) and why this is a classic privilege-escalation target if a setuid binary has a vulnerability.
