1. The Linux Filesystem Hierarchy, From Zero

Unlike Windows (where each disk gets its own drive letter, C:\, D:\, etc.), Linux has exactly ONE unified directory tree, starting at / (the "root" directory — unrelated to the "root" user, though both share the name). Every disk, partition, network share, or removable device gets MOUNTED (attached) at some point within this single tree, rather than getting its own separate namespace.

PathWhat actually lives there
/etcSystem-WIDE configuration files (not per-user) — e.g., /etc/resolv.conf, which Module 01's own code reads directly for DNS server configuration on Linux
/homePer-user home directories — /home/yourname, roughly analogous to C:\Users\yourname on Windows
/var"Variable" data — data that changes constantly during normal operation: logs (/var/log), mail spools, caches
/usr/binWhere most installed programs actually live — historically distinct from /bin (essential system binaries needed even in single-user recovery mode), though modern distributions commonly symlink /bin to /usr/bin, merging the distinction in practice
/procNOT a real, disk-backed filesystem at all — a live, synthetic window into kernel and process state, generated on the fly the instant you read it. cat /proc/cpuinfo doesn't read a file that "exists" on disk; the kernel generates that text dynamically, right when you ask.
/devDevice files — /dev/null (a bottomless pit that discards anything written to it and returns EOF immediately if read), /dev/zero (an infinite stream of zero bytes), /dev/sda (a real disk device) — Linux's famous "everything is a file" philosophy made literal: even physical hardware devices are interacted with through the same read/write file interface as ordinary files
/tmpTemporary files, world-writable — but protected by the sticky bit (Section 4.3), a genuinely important nuance
Brain power: why does /proc/cpuinfo "exist" as a readable file with real content, despite not being stored anywhere on disk? Because Linux's virtual filesystem layer doesn't actually require a file's content to come from a physical storage device — /proc is backed by a special filesystem DRIVER that, whenever the kernel receives a read request for a file under /proc, generates the appropriate content on the spot by querying live kernel data structures, then discards it. This is exactly why /proc/cpuinfo's content can change between two consecutive reads (if CPU frequency scaling changes, for instance) — there's no cached "file" sitting there; every read is a fresh query.

2. Permissions and chmod — The Full Bit-Math, Many Scenarios

2.1 — The three permission TRIOS, and what each bit means

Every file/directory has permissions for exactly THREE categories of user: the OWNER, the GROUP, and OTHER (everyone else). Within each category, exactly THREE bits control read (r), write (w), and execute (x) — this directly reuses Module 00a's binary/bitwise material: each trio is quite literally a 3-bit binary number, where read=4 (binary 100), write=2 (binary 010), execute=1 (binary 001), and you SUM the bits for whichever permissions you want to grant.

Worked scenario: deriving 755 from a plain-English description, completely by hand

Requirement: "the owner can read, write, and execute this file; the group and everyone else can only read and execute it (not write)."

Owner:  read + write + execute = 4 + 2 + 1 = 7
Group:  read + execute (no write) = 4 + 0 + 1 = 5
Other:  read + execute (no write) = 4 + 0 + 1 = 5

Result: 755

This is EXACTLY the value this module's own filesystem_and_permissions.sh applies via chmod 755 testfile.txt, and its symbolic-notation equivalent, chmod u=rwx,g=rx,o=rx, says the identical thing in a different notation — the script confirms both produce IDENTICAL results by checking stat's output after each.

Worked scenario: a private file only the owner can touch at all

Owner: read + write (no execute, it's data not a program) = 4 + 2 = 6
Group: nothing at all = 0
Other: nothing at all = 0

Result: 600  (chmod 600 secrets.txt -- a real, extremely common pattern
              for private key files, e.g. SSH's ~/.ssh/id_rsa)

Worked scenario: a shared script everyone on the system can run but only the owner can edit

Owner: read + write + execute = 4+2+1 = 7
Group: read + execute (no write) = 4+0+1 = 5
Other: read + execute (no write) = 4+0+1 = 5

Result: 755 -- same value as the first scenario, because "everyone can
              read/run, only the owner can modify" is a genuinely
              common pattern, appearing identically for both data files
              intended for wide reading and executable scripts intended
              for wide running.

2.2 — Reading a permission string like -rwxr-xr-x directly

-rwxr-xr-x
│└┬┘└┬┘└┬┘
│ │  │  └── OTHER: r-x (read + execute, no write)
│ │  └───── GROUP: r-x (read + execute, no write)
│ └──────── OWNER: rwx (read + write + execute)
└────────── FILE TYPE: '-' means regular file
             ('d' would mean directory, 'l' would mean symlink)

This is exactly ls -l's output format, and exactly what stat -c '%A (%a)' (used throughout this module's own scripts) prints in its first field — the symbolic string ALWAYS has this same fixed 10-character structure: 1 type character, then three groups of 3 permission characters.

2.3 — Why execute permission on a DIRECTORY means something completely different than on a file

Common confusion: "execute permission on a directory" doesn't mean "run the directory." For a regular FILE, execute permission means "this file may be run as a program/script." For a DIRECTORY, execute permission means something entirely different: "you may ENTER this directory and access items INSIDE it by name" (technically: traverse it as part of a path). A directory with read but NOT execute permission lets you LIST its contents' names (ls) but NOT actually access any specific file inside by path — a genuinely confusing distinction until you've hit it directly. This is why you'll commonly see directories with permission 755 or 750 (execute bit set) even though "running a directory" makes no literal sense — the execute bit is doing a completely different job than it does on a file.

3. umask — Why New Files Aren't Born At 777

When a program creates a new file, it typically requests a MAXIMUM starting permission — conventionally 666 (rw-rw-rw-, no execute — since "newly created data files should be runnable by default" would be a strange default) for regular files, or 777 for directories. The UMASK is then applied as a SUBTRACTIVE MASK — it REMOVES permission bits from that starting point, rather than adding them.

Worked scenario: umask 022 applied to a new file's default 666, traced bit by bit

Starting point for a new file: 666 = rw-rw-rw-
umask:                          022

umask 022 means: "remove write permission for GROUP and OTHER"
  (0 = remove nothing from owner, 2 = remove write(2) from group,
   2 = remove write(2) from other)

666
-022
----
644  =  rw-r--r--

This EXACTLY matches this module's own filesystem_and_permissions.sh
output: "A new regular file normally starts at 666 ... umask 022
removes write for group and other, leaving 644."
Why is umask SUBTRACTIVE (removing bits from a maximum) rather than a direct target value? This design lets ONE umask setting correctly apply to BOTH files (starting max 666) and directories (starting max 777) simultaneously, producing the right RELATIVE result for each without needing separate settings — umask 022 applied to a file's 666 gives 644; the SAME umask 022 applied to a directory's 777 gives 755 (again removing write from group/other) — a single system-wide default policy, expressed once, correctly covering both cases because subtraction (removing SPECIFIC bit positions) generalizes cleanly in a way a single fixed target value wouldn't.

4. Special Bits — setuid, setgid, sticky, Fully Explained

4.1 — The sticky bit, using /tmp as the concrete, universal example

This module's own script checks /tmp's real permissions directly on your live system and finds 1777 — the leading 1 is the STICKY BIT, displayed as a trailing t in the symbolic form (drwxrwxrwt).

Scenario: why /tmp needs to be BOTH world-writable AND sticky simultaneously

/tmp must be writable by EVERY user on the system (any program, run by any user, might need to create a temporary file there) — hence the 777 base permission (world-writable). But WITHOUT the sticky bit, world-writable would ALSO mean any user could DELETE or RENAME any other user's files in /tmp — a real security and reliability problem on any shared, multi-user system (one user maliciously or accidentally deleting another user's temp files). The sticky bit adds exactly ONE additional restriction on top of 777's normal permissions: even though everyone can CREATE files there, only a file's OWNER (or root) may delete or rename an EXISTING file — solving the "shared writable directory" problem with a single extra bit, rather than requiring per-user subdirectories or more complex access control.

4.2 — setuid, fully explained with a concrete scenario

Normally, a program you run executes with YOUR OWN user privileges — it can only do what YOU are allowed to do. The SETUID bit changes this: a setuid program runs with the privileges of the file's OWNER, not the user who launched it.

Scenario: /usr/bin/passwd, a real, universal setuid example

Changing your own password requires writing to /etc/shadow — a file that ordinary (non-root) users cannot write to directly, by design (if any user could edit /etc/shadow directly, they could grant themselves root access trivially). Yet ordinary users obviously NEED to be able to change their own password. The passwd program solves this with setuid: it's OWNED by root, and has the setuid bit set — so when YOU (an ordinary user) run passwd, the PROGRAM temporarily runs with ROOT's privileges (not yours), specifically long enough to perform the narrow, carefully-controlled task of updating your own password entry, then exits. You never gain root privileges yourself — only the program, and only for its own tightly-scoped purpose.

Why is this module's Exercise 2 (find every SUID binary with find / -perm -4000 -type f) framed as security-relevant, not just informational? Every setuid binary is a genuine PRIVILEGE ESCALATION SURFACE — if a setuid-root program has a vulnerability (a buffer overflow, per Module 00b, being a classic example) that lets an attacker control its behavior, that attacker inherits ROOT-level privileges through the vulnerable program, even though they only had ordinary user access to begin with. This is exactly why real security auditing (and real CTF privilege-escalation challenges, echoing Module 21) routinely starts with exactly this command — enumerating setuid binaries is one of the first things both attackers and defenders check on a new system.

4.3 — setgid, briefly, for completeness

SETGID works analogously to setuid but for GROUP ownership instead of user ownership — a setgid EXECUTABLE runs with the file's group privileges rather than the invoking user's group. Applied to a DIRECTORY (a different, also-common usage), setgid means "any NEW file created inside this directory automatically inherits the directory's own group," rather than the creating user's default group — useful for shared team directories where every file should stay owned by a common project group regardless of which team member created it.

5. Real UID vs. Effective UID — The Mechanism setuid Depends On

Every running process has (at minimum) TWO separate UID values, not just one — this is the precise mechanism that makes setuid actually work: the REAL UID identifies who ACTUALLY launched the process (your own real identity, unchanged); the EFFECTIVE UID identifies what privileges the process is CURRENTLY operating with — which is what the kernel actually checks when deciding whether to allow a given action (like writing to /etc/shadow).

Scenario: running passwd, traced through real/effective UID

You launch /usr/bin/passwd as yourself (say, UID 1000):
  Real UID:      1000  (you, unchanged, the entire time)
  Effective UID: 1000  (initially -- same as real UID, at launch)

The kernel notices passwd's setuid bit is set, owned by root (UID 0):
  Real UID:      1000  (STILL you -- this never changes)
  Effective UID: 0     (NOW root -- because of the setuid bit)

passwd can now write to /etc/shadow, because the kernel checks the
EFFECTIVE UID (0, root) when deciding whether this write is allowed --
not the real UID.

When passwd exits, this elevated effective UID goes away entirely --
your NEXT command runs with effective UID 1000 again, same as always.
Comprehensive exam framing: "Explain why the distinction between real and effective UID is necessary — why couldn't the kernel just track a single UID per process?" A single UID value couldn't represent BOTH "who is accountable for/owns this process" (needed for things like resource accounting, and for a process to be able to determine and log its OWN original identity) AND "what privilege level should currently govern this process's actions" (needed for the setuid mechanism to temporarily elevate privileges for a specific, narrow purpose) simultaneously, since these two questions can have genuinely different correct answers during a setuid program's execution. Two separate fields let the kernel answer both questions independently and correctly at every point in the process's lifetime.

6. systemd Units, Line By Line — What Every Directive Does

This module's own heartbeat.service file is short but every single line is doing real, specific work. Walk through it directive by directive.

[Unit]
Description=Module 00c heartbeat demo service

[Service]
Type=simple
ExecStart=%h/module00c-demo/heartbeat.sh
Restart=on-failure

[Install]
WantedBy=default.target
DirectiveWhat it actually does
[Unit] / Description=The [Unit] section holds metadata and dependency information about the unit generally. Description= is purely a human-readable label — shown in systemctl status output — with zero functional effect on behavior.
[Service] / Type=simpleTells systemd HOW to determine when this service has finished "starting up." Type=simple (the simplest, most common type) means: "the process named in ExecStart IS the service — consider it started the instant that process launches," as opposed to more complex types (like Type=forking, used for older-style daemons that fork into the background and expect systemd to track the CHILD process instead of the one it directly launched).
ExecStart=%h/module00c-demo/heartbeat.shThe actual command systemd runs to start this service. %h is a systemd SPECIFIER — expanded at runtime to the home directory of the user this unit runs as, specifically so this unit file works correctly for ANY user without hardcoding a specific username's home directory path.
Restart=on-failureTells systemd to AUTOMATICALLY restart this service if it exits with a non-zero (failure) status — but NOT if it exits cleanly (status 0) or is deliberately stopped via systemctl stop. This is a real reliability feature: a service that crashes due to a transient issue gets automatically relaunched without requiring a human to notice and intervene.
[Install] / WantedBy=default.targetThis section is ONLY consulted when you run systemctl enable — it does NOT affect starting the service manually. WantedBy=default.target means "when this unit is enabled, create a dependency link so that default.target (systemd's normal 'user session is ready' milestone) WANTS this unit to be started too" — this is the actual mechanism behind "start this service automatically at login," which this module's own tutorial exercises directly via systemctl --user enable.
Why does Restart=on-failure specifically distinguish "crashed" from "was deliberately stopped," rather than restarting unconditionally on ANY exit? A service you deliberately stop via systemctl stop should STAY stopped — that's the whole point of stopping it. If systemd restarted a service unconditionally regardless of why it exited, systemctl stop would become functionally useless (the service would just immediately relaunch itself). on-failure specifically threads this needle: exit code 0 (or being killed by a normal stop request) is treated as "intentional, leave it stopped"; any non-zero exit code is treated as "something went wrong, try again" — the distinction is entirely carried by the process's OWN exit status, which is exactly why well-written services are careful to exit with 0 on clean, deliberate shutdown and non-zero on genuine errors.

7. The Full systemd Service Lifecycle, Narrated

The complete story, matching exactly what this module's tutorial.html Step 2 walks through

  1. mkdir -p ~/.config/systemd/user — creates the directory where systemd looks for USER-level (not system-wide) unit files. Its existence (or non-existence) is why this course uses --user units at all: no root/sudo access is required anywhere in this entire workflow, since everything lives under YOUR OWN home directory.
  2. cp heartbeat.service ~/.config/systemd/user/ — places the unit file where systemd's user-mode instance will actually find and read it.
  3. systemctl --user daemon-reload — tells the ALREADY-RUNNING systemd user instance to re-scan its unit file directories and pick up the new (or changed) file. Without this step, systemd wouldn't even know heartbeat.service exists yet — unit files aren't watched/auto-reloaded continuously; you must explicitly request a reload after any change.
  4. systemctl --user start heartbeat.service — actually launches the service NOW, this one time. This does NOT set it up to launch automatically in the future — that's a SEPARATE decision, made via enable (step 6).
  5. systemctl --user status heartbeat.service — confirmed, during this module's real testing, to show Active: active (running) with a genuine process ID — proof the service is actually running, not just that the start command was accepted without error.
  6. systemctl --user enable heartbeat.service — this is the step that actually creates the WantedBy=default.target dependency link (Section 6's table) on disk, specifically so this service starts AUTOMATICALLY at your next login — completely independent of whether it's currently running right now.
  7. journalctl --user -u heartbeat.service — shows this specific unit's captured log output. Confirmed during this module's real build: every heartbeat message the script printed to stdout appeared here automatically, with ZERO explicit logging code written anywhere — systemd captures a unit's stdout/stderr by default, redirecting it into the structured journal log automatically.
  8. systemctl --user stop / disable — stop ends the CURRENTLY running instance immediately; disable removes the auto-start-at-login link created by enable. These are two INDEPENDENT axes (currently running vs. will-auto-start-later) — confirmed by this module's own tutorial, which runs each separately and checks is-enabled/is-active after each to show they change independently.
Brain power: why are "running now" (start/stop) and "will auto-start later" (enable/disable) deliberately SEPARATE, rather than one combined toggle? Because these answer genuinely different questions with genuinely different valid combinations in practice: a service could be currently STOPPED but ENABLED (will start at your NEXT login, but you manually stopped THIS session's instance for now) — or currently RUNNING but DISABLED (you started it manually just for this session, with no intention of it persisting across a reboot/relogin). Collapsing these into one setting would make either of these genuinely-common, genuinely-different situations impossible to express.

8. Package Management — apt, dpkg, and Dependency Resolution

CommandWhat it does
apt list --installedLists every package CURRENTLY installed on this system — purely read-only, reports existing state.
apt-cache show curlShows METADATA about a package (version, description, size, dependencies) WITHOUT installing it — apt-cache operates entirely against apt's locally-cached package INDEX (metadata downloaded during apt update), not against the actual installed system.
dpkg -S /bin/bash"Search" — given a FILE PATH, reports which installed PACKAGE owns/provided that file. dpkg (Debian Package manager, the lower-level tool apt itself is built on top of) tracks exactly which package installed every file on the system.
dpkg -L bashThe REVERSE direction — given a package NAME, lists every file that package installed.
apt-get install --simulate -y cowsayShows EXACTLY what a real install would do (which packages would be installed, upgraded, or removed, and how much disk space would be used) WITHOUT actually performing any of it — --simulate (or its shorter alias -s) is apt's "dry run" mode, confirmed during this module's own testing via a subsequent which cowsay check showing nothing was actually installed.
apt-cache depends curlShows curl's DEPENDENCY GRAPH — every OTHER package curl itself requires to function. This is exactly the mechanism that determines what ELSE gets pulled in during a real apt install curl — every listed dependency that isn't already satisfied on your system gets installed too, automatically.
Why does this module draw such a careful line — READ-ONLY commands and --simulate only, with an explicit post-hoc which cowsay verification that nothing was actually installed? Package management commands have REAL, PERSISTENT side effects on your actual system (installing packages consumes real disk space, potentially changes system behavior, and isn't trivially reversible in every case) — this is categorically different from every OTHER command in this module (permissions, systemd units), which either operate in a disposable temp directory or on a user-level systemd instance you fully control and can cleanly tear down. Package management specifically touches SYSTEM-WIDE state, which is exactly the kind of action this course's own safety principles (see SAFETY.md) treat with deliberate extra caution.

9. Full Code Walkthrough — filesystem_and_permissions.sh

9.1 — set -e and the throwaway working directory

set -e
WORKDIR=$(mktemp -d)
cd "$WORKDIR"

set -e is a bash safety directive: "if ANY command in this script fails (returns a non-zero exit status), stop the entire script immediately" — without it, a failed command's error would simply print and the script would keep going, potentially compounding into confusing later failures. mktemp -d creates a genuinely unique, freshly-generated temporary DIRECTORY (not just a filename) — guaranteeing this script never collides with a previous run's leftover files and, per the script's own final cleanup step (rm -rf "$WORKDIR"), leaves absolutely no trace once finished.

9.2 — The permission-denied proof, unpacked

if ./script.sh 2>/tmp/perm_error.txt; then
    echo "  (unexpectedly succeeded)"
else
    echo "  FAILED as expected: $(cat /tmp/perm_error.txt)"
fi

This is written as an if/else rather than just running the command directly and assuming failure — a genuinely more careful, honest testing pattern: it EXPLICITLY handles both possible outcomes (the script running despite missing execute permission would be a genuinely surprising, worth-flagging result, rather than something silently ignored), and it CAPTURES the actual error message (redirected to a temp file via 2>/tmp/perm_error.txt, since stderr is where a "Permission denied" message would appear) so the real OS-level error text is displayed, not just an assumption about what it would say.

10. Full Code Walkthrough — package_management.sh

10.1 — Why every apt/dpkg call redirects stderr with 2>/dev/null

apt list --installed 2>/dev/null | head -5

apt list (and several other apt subcommands) print a literal warning to STDERR — "WARNING: apt does not have a stable CLI interface, use with caution in scripts" — every single time they're invoked, specifically because apt's plain-text output format isn't officially guaranteed to stay identical across versions (a real, documented caveat, not a bug). 2>/dev/null discards stderr specifically so this recurring, expected warning doesn't clutter this module's own demonstration output — an intentional choice to keep the teaching output clean, not an attempt to hide a REAL error (this module's own comments are transparent about this).

10.2 — The fallback pattern in the dpkg -S line

dpkg -S /bin/bash 2>/dev/null || dpkg -S "$(readlink -f /bin/bash)"

The || ("or") operator runs the SECOND command only if the FIRST one fails. This handles a real, genuine platform quirk: on some systems, /bin/bash is itself a SYMLINK (pointing to the real binary elsewhere, like /usr/bin/bash) — and dpkg -S queries by the EXACT path string, which can fail on a symlink path even though the underlying real file IS tracked by dpkg. readlink -f resolves the symlink to its REAL, canonical target path FIRST, and the fallback retries the query against that resolved path instead — a genuinely defensive, portable scripting pattern worth recognizing.

11. Troubleshooting Scenarios You Will Actually Hit

Scenario: systemctl --user start succeeds with no error, but status shows "inactive (dead)" immediately after

This almost always means the service's ExecStart command failed IMMEDIATELY (exited with a non-zero status right away) rather than the unit failing to be RECOGNIZED at all — check journalctl --user -u heartbeat.service for the actual error output the failed process printed before exiting. Common causes: the script referenced in ExecStart isn't actually executable yet (forgot chmod +x), or the path is wrong (the %h specifier expanding to somewhere the file doesn't actually exist).

Scenario: you edit a unit file, restart the service, but your changes don't seem to take effect

This is almost always a missing systemctl --user daemon-reload step (Section 7, step 3) — systemd caches unit file CONTENTS in memory when it first loads them; simply overwriting the file on disk does NOT automatically make systemd re-read it. daemon-reload is a genuinely easy step to forget, and "I edited the file but nothing changed" is one of the single most common systemd confusions.

Scenario: systemctl --user commands fail entirely, with an error about not being able to connect to the bus

This module's own build hit a version of this on the first attempt in a fresh WSL session — likely a transient timing issue with the user-level systemd/D-Bus session not yet being fully ready immediately after WSL startup. Waiting a few seconds and retrying, or starting a fresh terminal session, typically resolves it — treat a single early failure as a possible startup-timing issue worth simply retrying, not necessarily evidence of a broken configuration.
