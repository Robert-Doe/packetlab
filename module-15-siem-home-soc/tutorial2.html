Module 15 — Deep Theory: Docker Compose and the ELK Stack, From Zero

1. Command-by-Command: Docker Compose

docker compose up -d

What it does: reads docker-compose.yml, and for each defined service, downloads the specified container IMAGE (if not already cached locally) and starts a CONTAINER from it — a running instance of that image, isolated via the same kernel namespaces/cgroups mechanism Module 00c's deep theory covered. -d means "detached" — run in the background, returning your terminal immediately, rather than attaching your terminal to the containers' combined log output (which you can still view later with docker compose logs).

Why "image" and "container" are different words for different things: an IMAGE is a read-only TEMPLATE (like a class in object-oriented programming) — a filesystem snapshot plus metadata (what command to run, what ports to expose). A CONTAINER is a RUNNING INSTANCE of an image (like an object instantiated from that class) — you can start multiple containers from the same image, each with its own isolated process/filesystem view, independent of the others.

The healthcheck block (in docker-compose.yml)

What it does: periodically runs a command INSIDE the Elasticsearch container (curl -sf http://localhost:9200/_cluster/health) to determine whether the service is actually ready to use, not just "the process has started." Why this distinction matters: Elasticsearch's process starts almost immediately, but the JAVA VIRTUAL MACHINE it runs on, its internal cluster formation, and its index initialization take real additional time — a naive "wait for the process to start" check would let Logstash (per depends_on: condition: service_healthy) try to connect and FAIL, because the underlying service, despite technically running, isn't actually ready to serve requests yet.

2. Elasticsearch's Document Model, Formally

Elasticsearch stores data as JSON DOCUMENTS, grouped into INDICES (the rough analog of a "table" in a traditional relational database, though Elasticsearch is NOT relational — no foreign keys, no joins in the traditional sense). Every document is automatically given a schema inferred from its own fields (a "dynamic mapping") unless you explicitly define one — this is why log_shipper.py's alert_to_document() function can ship arbitrary JSON shapes without any prior schema declaration, and Elasticsearch will index whatever fields it sees.

3. The Bulk API's NDJSON Format, Precisely

log_shipper.py's write_bulk_ndjson() produces alternating ACTION and SOURCE lines — this is a REQUIRED, specific format, not a stylistic choice:

{"index": {"_index": "module15-alerts"}}
{"type": "port_scan", "src": "192.168.1.30", ...}
{"index": {"_index": "module15-alerts"}}
{"type": "beaconing", "src": "192.168.1.10", ...}

Each ACTION line specifies what operation to perform (index here — create or replace) and which index it applies to; the SOURCE line immediately following it is that document's actual content. This alternating structure lets Elasticsearch process a huge batch of documents as a STREAM, one action-source pair at a time, without ever needing to parse the entire request into memory as one giant structure first (unlike a single large JSON array, which requires the full structure to be valid before ANY of it can be processed).

4. Logstash's Pipeline Stages, Formally

logstash.conf's three top-level blocks (input, filter, output) reflect Logstash's fundamental architecture: EVERY event flows through exactly this pipeline, in this order. input plugins (here, file) generate events from a source. filter plugins (here, dissect for parsing Zeek's TSV format, and date for assigning a real timestamp) transform each event. output plugins (here, elasticsearch and stdout) send the finished event somewhere. This input-filter-output separation is deliberate: the SAME filter logic could process events from a completely different input source (a Kafka topic instead of a file, for instance) without modification, and the SAME parsed event could be sent to multiple DIFFERENT outputs simultaneously — exactly why this module's config sends every event to BOTH Elasticsearch AND stdout at once.
