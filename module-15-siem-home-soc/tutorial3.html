Module 15 — Exam Practice

Answer out loud before revealing each answer.
Q1. Precisely distinguish a Docker image from a Docker container, using the class/object analogy.
A: An image is a read-only template -- a filesystem snapshot plus metadata (what command to run, what ports to expose), analogous to a class definition. A container is a running INSTANCE of an image, analogous to an object instantiated from that class -- you can start multiple independent containers from the same single image, each with its own isolated process/filesystem view via kernel namespaces and cgroups.
Q2. Why does docker-compose.yml's healthcheck matter, beyond just checking whether the Elasticsearch process has started?
A: A process starting is not the same as a service being ready to serve requests -- Elasticsearch's underlying JVM startup, internal cluster formation, and index initialization take real additional time after the process itself begins running. A naive "wait for process start" check would let a dependent service (Logstash, via `depends_on: condition: service_healthy`) attempt to connect too early and fail, even though the container is technically "running."
Q3. Why does the Elasticsearch Bulk API require alternating action/source lines in NDJSON format, rather than accepting one large JSON array of documents?
A: The alternating line format lets Elasticsearch process a large batch as a STREAM, one action-source pair at a time, without needing the entire request to be fully parsed and validated before any of it can be processed. A single large JSON array would require the WHOLE structure to be syntactically valid before any document within it could be processed, and one malformed document anywhere in the array could fail the entire batch rather than just that one entry.
Q4. Explain Logstash's input-filter-output pipeline architecture, and why separating these three stages is a deliberate design choice rather than arbitrary structure.
A: Input plugins generate events from a source (a file, a network socket, a message queue). Filter plugins transform each event (parsing, adding fields, computing a timestamp) independent of where it came from or where it's going. Output plugins send finished events somewhere (Elasticsearch, stdout, another system). Separating these means the SAME filter logic can process events from a completely different input source without modification, and a single parsed event can be sent to MULTIPLE different outputs simultaneously -- exactly why this module's config sends every event to both Elasticsearch and stdout at once, using the identical filtering logic for both destinations.
Q5. Elasticsearch is described as NOT relational. What specifically does this mean, and how does it affect how log_shipper.py can ship data with no prior schema declaration?
A: Elasticsearch has no foreign keys or traditional joins between indices, and by default uses "dynamic mapping" -- automatically inferring each document's schema from whatever fields it actually contains, rather than requiring a schema to be declared in advance. This is why `alert_to_document()` can ship arbitrary JSON shapes (different alert types with different field sets) without any prior schema declaration -- Elasticsearch indexes whatever fields it encounters in each document as they arrive.
Q6. Why does this module's own build process explicitly distinguish "fully tested" (log_shipper.py's output format) from "syntax-validated but not run" (the actual 4-container stack)?
A: Standing up a 4-container ELK+Grafana stack is a genuine, non-trivial resource commitment (Elasticsearch alone typically wants 512MB+ memory) that shouldn't happen as an unannounced side effect of building course material. What COULD be verified without running the full stack (log_shipper.py's output format correctness, docker-compose.yml's syntax via `docker compose config`, which doesn't require a running daemon) was verified; the live stack itself was left as the student's own deliberate choice about when to commit that resource, consistent with this course's broader honesty about what was and wasn't actually tested.
Q7. Synthesis: connect this module's SIEM pipeline to Module 14's detection scripts. What specifically changes, and what specifically stays the same?
A: What stays the same: the actual DETECTION LOGIC (port-scan/beaconing statistical reasoning) is unchanged -- Exercise 1 explicitly asks the student to wire Module 14's real detector functions into this pipeline rather than reinventing detection logic here. What changes: the OPERATIONAL MODEL -- Module 14 ran detection as a one-shot script producing terminal output once; this module makes detection findings PERSISTENT (stored in Elasticsearch, queryable historically) and VISUALIZABLE (Kibana/Grafana dashboards) on an ongoing basis, rather than requiring a human to re-run a script and read terminal output every time they want to check for something. The move from Module 14 to 15 is purely infrastructural, not a change in what's actually being detected or how.
