1. Docker Compose's Internal Network — Why Hostnames Differ By Context

This is the single most common source of confusion for anyone new to Docker Compose, and deserves complete precision: THE SAME SERVICE is reachable at DIFFERENT hostnames depending on WHERE you're connecting FROM.

Connecting from...Correct hostname for ElasticsearchWhy
Your own machine's browser/curl (the HOST)127.0.0.1:9200 or localhost:9200Docker Compose's ports: "127.0.0.1:9200:9200" directive PUBLISHES the container's internal port 9200 onto your HOST machine's own loopback address — from the host's perspective, it genuinely looks like something is listening on localhost:9200
ANOTHER container in the SAME Compose file (e.g., Kibana or Logstash)elasticsearch:9200Docker Compose automatically creates a PRIVATE internal network for all services in one compose file, and provides automatic DNS resolution using each service's OWN NAME (from the YAML key, e.g. elasticsearch:) as its hostname WITHIN that private network — this is EXACTLY why kibana's own ELASTICSEARCH_HOSTS=http://elasticsearch:9200 environment variable uses the SERVICE NAME, not localhost
The single most common Docker Compose networking mistake: using localhost INSIDE a container's own configuration to reach ANOTHER container. Inside any given container, localhost refers to THAT CONTAINER ITSELF (exactly Module 01 Section 2.3's loopback lesson, applied to containers instead of physical machines) — NOT the host machine, and NOT any other container. Kibana's own config correctly uses elasticsearch (the SERVICE name) specifically to avoid this exact trap — if it had instead used localhost:9200, Kibana would be trying to reach an Elasticsearch instance running INSIDE ITS OWN CONTAINER, which doesn't exist, and would fail to connect.
Why does Docker Compose provide this automatic service-name DNS resolution at all, rather than requiring hardcoded IP addresses? Container IP addresses within Docker's internal network are NOT guaranteed to stay the same across restarts — a container that's recreated (during a restart, an image update, or a `docker compose up` re-run) can be assigned a DIFFERENT internal IP address than it had before. Hardcoding IPs would break every time this happened. Service-name-based DNS resolution means configuration NEVER needs to hardcode an IP address at all — elasticsearch always resolves to "whichever container is currently running the elasticsearch service," regardless of its actual, potentially-changing internal IP.

2. Full docker-compose.yml Walkthrough, Line By Line

2.1 — The ports directive's three-part syntax

ports:
  - "127.0.0.1:9200:9200"

This is genuinely THREE distinct values, not two: HOST IP (127.0.0.1 — bind ONLY to loopback on your host, per this module's own comment: "Everything binds to 127.0.0.1 only — see SAFETY.md," directly reusing Module 01's loopback-only safety principle), HOST PORT (9200 — what you'd connect to FROM your host machine), CONTAINER PORT (9200 — what the process INSIDE the container is actually listening on). These don't have to match — you could map host port 19200 to container port 9200 ("127.0.0.1:19200:9200") if port 9200 were already in use on your host by something else, without changing anything about what Elasticsearch itself is configured to do inside its container.

2.2 — Why xpack.security.enabled=false is explicitly flagged as home-lab-only

Why does disabling Elasticsearch's built-in security features get an explicit, urgent warning comment ("NEVER do this on anything internet-facing") rather than just being silently configured? Elasticsearch's xpack.security features (authentication, TLS, role-based access control) exist specifically to prevent UNAUTHENTICATED access to your data. Disabling them is a genuinely reasonable simplification for a lab bound ONLY to 127.0.0.1 (Section 2.1's binding, meaning nothing outside your own machine can reach it AT ALL, regardless of Elasticsearch's own auth settings) — but if this SAME configuration were ever exposed on a real, internet-facing network interface (a genuine, real, and unfortunately common misconfiguration mistake in production), it would mean ANYONE who could reach that port could read, modify, or delete ALL of your indexed data with zero authentication required — a real, well-documented category of security incident. This module's own explicit warning comment is teaching real operational security discipline, not just documenting a setting.

2.3 — Volumes, precisely

volumes:
  - es-data:/usr/share/elasticsearch/data

This mounts a Docker-managed NAMED VOLUME (es-data, declared at the bottom of the file under volumes:) into the container's own data directory. Without this, ALL of Elasticsearch's indexed data would exist ONLY inside the container's own writable layer — and would be COMPLETELY LOST the moment the container is removed (not just stopped — REMOVED, which happens routinely during image updates or a docker compose down without -v). A named volume persists INDEPENDENTLY of the container's own lifecycle — this is precisely why this module's own teardown instructions distinguish docker compose down (stops and removes containers, but the named volume SURVIVES) from docker compose down -v (ALSO removes the volumes, genuinely, permanently deleting all indexed data) — a real, meaningful distinction worth being precise about before running either command.

3. depends_on And service_healthy — Why Plain depends_on Isn't Enough

logstash:
  depends_on:
    elasticsearch:
      condition: service_healthy
...
grafana:
  depends_on:
    - elasticsearch
Why does logstash use the more elaborate condition: service_healthy form, while grafana uses the simpler list form? Plain depends_on: - elasticsearch (grafana's form) only guarantees STARTUP ORDER — Docker will start the elasticsearch container BEFORE starting grafana's — but says NOTHING about whether Elasticsearch is actually READY to accept connections yet (directly reusing Module 15's OWN tutorial2.html insight: a process starting is not the same as a service being ready). Logstash's condition: service_healthy form is STRICTER — it waits until Elasticsearch's own healthcheck block (Section 2.1's neighboring configuration: curl -sf http://localhost:9200/_cluster/health, repeated every 10 seconds, up to 10 retries) reports SUCCESS, meaning Elasticsearch has ACTUALLY finished its full JVM startup and cluster formation, before even attempting to start Logstash. Grafana's own connection-retry logic (built into Grafana itself) is more tolerant of a not-yet-ready Elasticsearch, so the simpler ordering-only dependency is an acceptable choice there — a genuine, deliberate difference in how much startup-readiness guarantee each dependent service actually needs.

4. Elasticsearch's Document/Index Model, Formally

Worked scenario: tracing exactly what happens to one alert document, from Python dict to indexed, searchable data

Module 14's raw finding (a plain Python dict):
  {"type": "port_scan", "src": "192.168.1.30", "dst": "192.168.1.99",
   "distinct_ports": 40, "window_seconds": 10}

alert_to_document() adds two fields:
  {"type": "port_scan", "src": "192.168.1.30", ..., "timestamp": "2026-...",
   "source_module": "module-14-network-security-monitoring"}

write_bulk_ndjson() wraps this in the Bulk API's action+source pair:
  {"index": {"_index": "module15-alerts"}}
  {"type": "port_scan", "src": "192.168.1.30", ..., "timestamp": "2026-..."}

Once POSTed to Elasticsearch's /_bulk endpoint, Elasticsearch:
  1. Looks at the action line -- "index" into "module15-alerts"
  2. Since no explicit mapping was pre-declared for this index,
     Elasticsearch uses DYNAMIC MAPPING -- inspecting the source
     document's own fields and inferring a reasonable type for each
     (type/src/dst as "text"/"keyword", distinct_ports as a number,
     timestamp as a date -- this automatic inference is EXACTLY why
     this module's own code never needs to pre-declare a schema)
  3. The document becomes immediately searchable/aggregatable across
     ALL its fields, ready for Kibana's Discover view or a Grafana panel
     to query.

5. NDJSON — Why Not A JSON Array, Precisely

This module's own code comment states the Bulk API format precisely: "an action-and-metadata line, then a source line, repeated... NOT a JSON array." Understanding WHY this specific format was chosen (not merely THAT it's required) is worth being precise about.

Why NDJSON instead of one large JSON array containing all documents? A single JSON array requires the ENTIRE structure (every opening/closing bracket, every comma) to be syntactically complete and valid before ANY of it can be parsed at all — a single malformed document ANYWHERE in a huge array invalidates parsing of the WHOLE request. NDJSON (newline-delimited JSON) lets Elasticsearch process the bulk request as a STREAM — reading and processing one action/source PAIR at a time, without ever needing to hold the entire request in memory as one parsed structure first, and (in principle) allowing partial success reporting per-document rather than an all-or-nothing failure. This directly parallels Module 08 Section 5's explanation of WHY HTTP uses a blank-line terminator rather than a length-prefix scheme — both are examples of format designs favoring STREAMING/INCREMENTAL processing over requiring the full structure upfront.

Why validate_bulk_ndjson() checks for an EVEN line count specifically

if len(lines) % 2 != 0:
    raise ValueError("bulk file must have an even number of lines...")

Since EVERY document requires EXACTLY two lines (one action, one source — this module's own format, per Section 4's trace), a well-formed bulk file must ALWAYS have an even total line count — an ODD count is IMPOSSIBLE under correct construction and would indicate a genuine structural bug (a missing source line, or an extra stray line) BEFORE ever even attempting to parse individual lines as JSON. This is a cheap, fast STRUCTURAL sanity check performed before the more expensive per-line JSON parsing — a real, sensible validation-ordering principle (check cheap, structural invariants first; expensive, detailed validation second).

6. Kibana Data Views — What They Actually Do

Why does Kibana require you to explicitly create a "Data View" (matching a pattern like module15-alerts-*) before you can browse indexed data in Discover, rather than just showing everything automatically? A single Elasticsearch cluster can hold MANY completely unrelated indices (this module's own two: module15-conn-* and module15-alerts-*, each with genuinely different document SHAPES/fields) — a Data View tells Kibana specifically WHICH indices to include when you're browsing/ visualizing, and lets Kibana correctly identify which field should be treated as the primary TIME field for time-based visualizations (the @timestamp field Logstash's own date filter assigns, per this module's Step 3). Without an explicit Data View, Kibana would have no principled way to decide which of potentially many, differently-shaped indices you actually want to explore in any given view.

7. Full Code Walkthrough — log_shipper.py

def alert_to_document(alert: dict) -> dict:
    doc = dict(alert)  # copy, don't mutate the caller's dict
    doc["timestamp"] = datetime.now(timezone.utc).isoformat()
    doc["source_module"] = "module-14-network-security-monitoring"
    return doc

dict(alert) creates a SHALLOW COPY specifically to avoid a real, common bug class: mutating a dictionary the CALLER still holds a reference to and might reuse. If this function instead wrote directly into the passed-in alert dict (alert["timestamp"] = ...), calling this function TWICE on the SAME alert object (perhaps by accident, in a loop) would silently OVERWRITE the timestamp each time, and any other code still holding a reference to that same dict would see its unexpected mutation too — a genuinely real, worth-recognizing defensive programming pattern anytime a function receives a mutable object it doesn't intend to permanently alter for the caller.

8. Many Worked Scenarios

Scenario: you run docker compose down (without -v), then up -d again — what survives, what doesn't?

SURVIVES: es-data and grafana-data (named volumes) -- all previously
  indexed Elasticsearch documents and any Grafana dashboards/settings
  you'd saved persist across this cycle, because named volumes exist
  independently of container lifecycle (Section 2.3).
DOES NOT SURVIVE: any changes made ONLY inside a container's own
  writable layer, outside a mounted volume path -- e.g., if you'd
  manually edited a file inside the logstash container via `docker exec`
  rather than editing logstash.conf on your host (which IS mounted, per
  `./logstash.conf:/usr/share/logstash/pipeline/logstash.conf:ro`),
  that manual edit would be lost, since a fresh container starts from
  the ORIGINAL image content plus whatever's mounted from your host.

9. Troubleshooting And Common Confusions

Common mistake: trying to reach Elasticsearch at "elasticsearch:9200" from your OWN machine's browser. This will fail with a DNS resolution error — elasticsearch is a hostname that ONLY resolves within Docker Compose's internal network (Section 1); your host machine's own DNS resolver has no idea what "elasticsearch" means. Always use 127.0.0.1:9200 (or localhost:9200) from your HOST machine, and elasticsearch:9200 only from WITHIN another container's own configuration.

Confusion: "I copied alerts.jsonl into data/, but Kibana still shows the old data — why?"

Logstash's file input, by default, tracks its OWN READ POSITION per file (a "sincedb" mechanism) — it does NOT automatically re-read a file's ENTIRE contents just because the file was modified; it typically only reads NEW lines appended since its last read. If you REPLACED (rather than appended to) alerts.jsonl, Logstash's sincedb might still think it's already read past the file's current (shorter or different) content, and never re-ingest it — this module's own tutorial.html's Step 2 instruction to docker compose restart logstash after copying a new file is specifically there to force Logstash to reconsider its input state, directly addressing this exact real behavior.
