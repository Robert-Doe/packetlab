Module 01 — Tutorial

Goal: get both lab variants running, read your own machine's real network configuration through code, then cross-check that against the raw OS commands yourself so you trust what the code is telling you. Everything here reads state your OS already has — nothing sends traffic anywhere yet.

Step 1 — Python variant

# Windows
cd module-01-environment-lab-foundations
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
python netinfo_server.py

# macOS/Linux
cd module-01-environment-lab-foundations
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python netinfo_server.py
Expected output: 
================================================================
 Module 01 (Python) lab is up.
 Dashboard : http://127.0.0.1:5000
 Raw JSON  : http://127.0.0.1:5000/api/netinfo
================================================================
 * Running on http://127.0.0.1:5000
Open http://127.0.0.1:5000 — you should see a table of your real network interfaces, a default gateway that looks like 192.168.x.1 or 10.x.x.1, and DNS servers that (if you're on Cox) will typically be in the 68.105.x.x range.

Step 2 — Node variant (leave Python running, open a second terminal)

cd module-01-environment-lab-foundations
node netinfo.js
Expected output: 
================================================================
 Module 01 (Node) lab is up.
 Dashboard : http://127.0.0.1:5050
 Raw JSON  : http://127.0.0.1:5050/api/netinfo
================================================================
Open http://127.0.0.1:5050 in a second tab. It's the exact same dashboard frontend as Python's — same HTML, same JS fetch logic — pointed at a completely different backend implementation. The gateway and DNS values should match exactly between both dashboards, because they're both reading the same underlying OS state through different APIs.
Compare the two implementations directly: open netinfo_server.py and netinfo.js side by side. Python needed psutil for structured interface data but still had to text-parse ipconfig /all for gateway/DNS. Node's os.networkInterfaces() gives you structured interface data with zero external dependencies — but Node also has to text-parse ipconfig /all for gateway/DNS, because neither language's standard library exposes routing-table or resolver info directly. That's not a language limitation — it reflects that gateway/DNS config genuinely lives in OS-specific subsystems with no universal API, so both languages fall back to the same OS commands you're about to run by hand.

Step 3 — verify the code against the OS directly

Don't take the dashboards' word for it. Run these yourself and confirm the numbers match what both dashboards showed:

# Windows
ipconfig /all
ping 192.168.0.1        REM replace with your actual gateway
tracert 8.8.8.8
arp -a

# macOS/Linux
ifconfig            (or: ip addr)
ping -c 4 192.168.0.1
traceroute 8.8.8.8
arp -a
Expected: the gateway IP in your ipconfig/ifconfig output should be the exact same address both dashboards reported. ping to your gateway should succeed with sub-5ms latency (it's one hop, on your own LAN). tracert/traceroute to 8.8.8.8 should show your gateway as hop 1, then jump out to Cox's network for the next few hops before reaching Google's network — this is your first real look at routing, which Module 05 covers properly.

Step 4 — put something in the ARP table on purpose

If your dashboard's ARP table looked sparse, that's because your machine only remembers devices it's recently talked to. Generate a fresh entry:

# ping a device on your LAN you haven't talked to recently — your phone's
# IP, a smart TV, another laptop. Check your router's admin page for a
# device list if you don't know one offhand.
ping 192.168.0.50      REM use a real IP from your own network

Refresh either dashboard — that device should now appear in the ARP table. This is the mechanic Module 03 builds on: your machine had to broadcast "who has 192.168.0.50?" and cache the MAC address that answered.

Exercises before Module 02

  1. Add a "last updated" timestamp to both /api/netinfo responses (Python: datetime.now().isoformat(); Node: new Date().toISOString()) and display it on the dashboard. This is your first small edit to lab code you didn't write from scratch — get comfortable modifying both variants.
  2. Add an interface filter. Both dashboards currently show every interface, including inactive VPN/virtual adapters. Add a query param (/api/netinfo?up_only=true) that filters to only interfaces where is_up is true, in both the Python and Node servers.
  3. Explain the gap. In your own words (a few sentences, doesn't need to be a file yet — Module 18 wants a formal write-up habit, this is just practice) — why does neither Python's standard library nor Node's expose default gateway or DNS servers directly, when both expose interface addresses directly? What does that tell you about how "structured" networking APIs versus OS shell commands are layered on most operating systems?
Before Module 02: you should have both dashboards running side by side, have verified their numbers against raw OS commands yourself, and have a fresh ARP entry you personally created.
