Module 17 — Tutorial

Goal: design a real 3-tier cloud network (VPC, public/private subnets, chained security groups, a load balancer) as actual Terraform, audit its security group logic before ever deploying anything, then deploy it yourself on your own free-tier AWS account.

This course will never create a cloud account or enter payment details on your behalf. AWS account creation, billing setup, and running terraform apply against real infrastructure are all steps you perform yourself, on your own account, with your own credentials. What this module DID verify: sg_rule_auditor.py/.js are fully tested against both a correct and a deliberately broken security group design. What it could NOT verify (no Terraform CLI or HCL parser was available in this build environment): that terraform/main.tf passes terraform validate — do this yourself as Step 1 below, before ever running apply.

Step 1 — validate the Terraform yourself, first

cd module-17-cloud-networking/terraform
terraform init
terraform validate
terraform plan
Expected: validate reports the configuration is syntactically valid. plan shows what WOULD be created (a VPC, 4 subnets, an internet gateway, a NAT gateway, 3 security groups, a load balancer) without creating anything yet. Read through the plan output carefully — this is the real "dry run" step nobody should skip before apply.

Step 2 — audit the security group design before deploying

cd ..
python sg_rule_auditor.py
Expected: zero findings against the real 3-tier design (web-sg, app-sg, db-sg) — confirming app-sg and db-sg's security-group-reference pattern (rather than raw CIDR blocks) is what keeps them safe. Two findings against the deliberately misconfigured example (open SSH and MySQL to the whole internet) — confirming the auditor actually catches real mistakes, not just passing everything.
node sg_rule_auditor.js
Identical findings (verified during this module's build with a byte-diff).

Step 3 (your own AWS account) — deploy it for real

terraform apply
Expected: after confirming the plan, real AWS resources are created. Note the alb_dns_name output — that's a real, publicly resolvable DNS name for your load balancer. Confirm you can reach it (it'll show a "no healthy targets" error until you actually deploy something to the app tier — that's expected and correct, given the health check configuration).

Step 4 — tear it down when you're done

terraform destroy
Expected: every resource this configuration created is removed. AWS's free tier has real limits and real resources cost real money past those limits — always destroy lab infrastructure you're not actively using.

Exercises before Module 18

  1. Extend the auditor to check egress rules too. main.tf's security groups all allow unrestricted egress (0.0.0.0/0, all ports) — reasonable for a lab, but worth flagging as a lower-severity finding in a stricter review. Add this check to both language variants.
  2. Add a 4th tier. Extend the Terraform with a dedicated "cache" tier (Redis/Memcached) reachable only from app-sg, matching this module's existing chain pattern — then confirm sg_rule_auditor.py still reports zero findings once you model it correctly in the sample data too.
  3. Compare cloud security groups to Module 10's NAT/firewall. Write a few sentences on what's structurally similar (stateful, default-deny, explicit allow rules) and what's different (security groups reference OTHER security groups directly, not just IP ranges — something Module 10's simulated firewall never modeled) between an AWS security group and a home router's NAT/firewall.
