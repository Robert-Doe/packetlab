Q1. Explain why terraform plan can run without any AWS credentials producing errors about missing resources, but still meaningfully report what WOULD change.
A: This is a trick premise -- plan DOES need valid credentials to query the real infrastructure state (it calls the AWS API to check current resource status). What it does NOT need is permission to CREATE/MODIFY anything -- read-only credentials are sufficient for plan, since it only compares and reports, never writes. Only apply requires write permissions. This distinction (read vs. write credential scope) is itself a real security practice: giving a CI pipeline read-only credentials for automatic plan runs on every pull request, while reserving write credentials for a separate, gated apply step.
Q2. What specifically determines whether a subnet is "public" or "private" in AWS? Is this a property of the subnet resource itself?
A: No -- it is entirely a property of the subnet's associated ROUTE TABLE, not any inherent flag on the subnet resource itself. A subnet whose route table sends 0.0.0.0/0 to an Internet Gateway is "public"; one that routes it through a NAT Gateway (or has no default route) is "private." The aws_subnet resource type is structurally identical either way -- only the aws_route_table it's associated with differs.
Q3. Connect this module's NAT Gateway to Module 10's NAT theory. What is functionally the same, and what is different?
A: Functionally the same: both perform address translation so that private-address hosts can reach the internet outbound while remaining unreachable for unsolicited inbound connections -- the same conntrack-style state tracking concept from Module 10 applies. What's different: Module 10's NAT was a feature of a router/firewall you configure and run yourself (iptables rules on a Linux box); AWS's NAT Gateway is a fully MANAGED service -- you don't administer the underlying software, patch it, or scale it; you simply declare it exists and AWS operates it, billed by usage rather than requiring you to run infrastructure.
Q4. Why does terraform destroy matter operationally in a way that has no real analog in this course's local Python/JS labs?
A: Local labs (a Flask server on :5000, a DNS server on :5053) cost nothing to leave running or forget about -- stopping the Python process ends all resource usage instantly and completely. Real cloud resources (a NAT Gateway, a load balancer) bill CONTINUOUSLY for as long as they exist, regardless of whether you're using them. Forgetting to run destroy after a lab exercise has an ongoing real dollar cost that accumulates silently until someone notices -- a genuinely different failure mode than anything else in this course.
Q5. A security group rule references another security group as its source, rather than a CIDR block. What does this buy you that a CIDR-based rule cannot?
A: A CIDR-based rule allows traffic from a fixed IP range -- if the allowed instances' IP addresses change (autoscaling launches new instances with new IPs, for example), the rule must be manually updated to stay correct. A security-group-referencing rule instead allows traffic from "whatever instances currently have this security group attached," automatically staying correct as instances are created or destroyed -- membership-based, not address-based, matching this module's app-sg referencing web-sg directly rather than hardcoding the web tier's IP range.
Q6. Briefly, how does a Kubernetes NetworkPolicy's approach to segmentation differ from this module's AWS security groups, and how is it conceptually similar?
A: Similar: both express "what can talk to what" as a declarative POLICY enforced by the platform, rather than packet-filtering rules you manually maintain on each host. Different: security groups attach to EC2 instances/ENIs and typically reference other security groups or CIDR blocks; NetworkPolicies attach to PODS and select their peers by POD LABELS -- a finer-grained unit of segmentation appropriate to an environment where many containers share a single underlying host, unlike EC2 instances which are already isolated at the VM level.
Q7. Synthesis: this module's Exercise 3 asks you to compare cloud security groups to Module 10's NAT/firewall. Give the single most important structural similarity.
A: Both are STATEFUL by default -- a security group automatically allows the RETURN traffic for any connection its rules permitted outbound (or inbound), without needing an explicit matching rule in the opposite direction, exactly like Module 10's conntrack-based stateful firewall automatically permitting a TCP connection's response packets once the initial outbound SYN was allowed. This is the same "track connection state, don't just filter each packet in isolation" design principle appearing at two completely different layers of the stack -- a Linux kernel feature in Module 10, a managed cloud primitive here.
