Module 17 — Deep Theory: Terraform's Model and Cloud Networking, From Zero

1. Command-by-Command: The Terraform Lifecycle

terraform init

What it does: downloads and installs the PROVIDER plugins your configuration references (here, hashicorp/aws, declared in main.tf's required_providers block) — Terraform's core engine knows nothing about AWS, Azure, or any specific cloud vendor's API; providers are the plugins that translate Terraform's generic resource model into actual API calls for a specific platform. This must run once (and again whenever you add/change providers) before any other Terraform command works.

terraform validate

What it does: checks your configuration's syntax and INTERNAL consistency (are all referenced resources/variables actually defined, are argument types correct) — entirely OFFLINE, without contacting AWS at all, and without needing real credentials. This is exactly the check this course's own build environment couldn't perform (no Terraform CLI was available), which is why the tutorial explicitly asks the student to run it themselves before trusting the configuration.

terraform plan

What it does: compares your CONFIGURATION (what you wrote) against the current STATE (Terraform's own record of what it last knows to actually exist, stored in a terraform.tfstate file) and against the REAL infrastructure (by querying the cloud provider's API) — then computes and displays exactly what changes would be needed to make reality match your configuration, WITHOUT actually making any changes yet.

Why does Terraform need its OWN state file, rather than just querying the cloud provider directly every time? The state file lets Terraform track resources IT created specifically (vs. other resources that might exist in your account for unrelated reasons), map your configuration's logical resource names (like aws_vpc.main) to the cloud provider's own real, opaque resource IDs, and detect DRIFT — cases where someone manually changed a resource outside of Terraform, which plan would then flag as an unexpected difference needing reconciliation.

terraform apply / terraform destroy

What each does: apply executes the plan (creating/modifying/destroying real resources to match your configuration) after you confirm; destroy is functionally "apply, but the target configuration is nothing" — it removes every resource Terraform's state file shows it created for this configuration. Why destroying lab infrastructure specifically matters: cloud resources bill CONTINUOUSLY while they exist (a running load balancer, a NAT gateway) — unlike this course's local Python/JS labs, where "forgetting" to clean up costs nothing, forgetting to destroy real cloud infrastructure has an ongoing real dollar cost.

2. Public vs. Private Subnets, the Actual Routing Distinction

Nothing about a subnet is inherently "public" or "private" — the distinction is ENTIRELY about its ROUTE TABLE. A public subnet's route table has a route to an Internet Gateway for 0.0.0.0/0 (direct internet reachability, both directions). A private subnet's route table instead routes 0.0.0.0/0 through a NAT Gateway (outbound-only, per Module 10's NAT theory) — or has no default route at all, meaning no internet access whatsoever. This is exactly why main.tf defines separate aws_route_table resources for public and private subnets, each with a different default route target — the subnet resource itself is identical in structure either way.

3. Kubernetes Network Policies and Service Mesh, Briefly (Beyond This Module's Terraform)

Once workloads run as CONTAINERS orchestrated by Kubernetes (rather than VMs behind security groups), network segmentation is expressed differently: a Kubernetes NetworkPolicy resource declares which PODS (not IP ranges) can communicate with which other pods, based on POD LABELS — conceptually the same "reference the other thing directly, not its IP" pattern this module's app-sg referencing web-sg demonstrated, just at pod-label granularity instead of security-group granularity. A SERVICE MESH (e.g., Istio) goes further, injecting a proxy alongside every container specifically to enforce fine-grained policy AND provide mutual TLS (Module 13's mTLS, applied automatically between every pod-to-pod connection) without the application code itself needing to implement any of it.
