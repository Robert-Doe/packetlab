Module 21 — Tutorial: Research Methodology & CTF Practice

Goal: practice the actual WORKFLOW behind two things every security researcher eventually does — solving a CTF-style challenge end to end (find it, prove it, submit it) and writing a research finding that stands on its own (a question, related work, method, evidence, limitations) — plus the ethics of disclosing what you find responsibly.

Step 1 — solve this module's own CTF challenge

cd module-21-research-methodology-ctf-practice
wsl
gcc -O0 -o ctf_challenge/crackme ctf_challenge/crackme.c
python3 ctf_challenge/solve_crackme.py ctf_challenge/crackme --verify
Expected: key=0x37 flag='flag{r3vers1ng_1s_ju5t_r34d1ng}', followed by the binary itself confirming CORRECT — confirmed during this module's build. This is the same single-byte-XOR-brute-force technique from Module 20's string_deobfuscator.py, applied to a differently-shaped problem: a comparison target instead of a network address.

Step 2 — cross-language check

node ctf_challenge/solve_crackme.js ctf_challenge/crackme
Expected: the identical key and flag recovered, confirmed byte-identical to the Python output during this module's build.
A genuine environment limitation: running node solve_crackme.js ... --verify from WINDOWS Node cannot execute the compiled binary — it's a Linux ELF file (WSL's gcc built it), and Windows can't run ELF binaries directly. This isn't a bug; run --verify from within WSL instead (where Python is available by default), per DECISIONS.md.
