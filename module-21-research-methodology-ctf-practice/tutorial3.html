Q1. Define "falsifiable" precisely, and explain why "this system is secure" fails the test while "this system resists SQL injection via parameterized queries, tested against 200 payloads" passes it.
A: A claim is falsifiable if some possible observation or result could show it to be WRONG. "This system is secure" has no observation that could definitively contradict it -- a system that hasn't been broken yet is not proven unbreakable, so the claim can never be conclusively falsified by any single test. "Resists SQL injection via parameterized queries, tested against 200 payloads" IS falsifiable -- a single successful injection among those 200 payloads (or a demonstrably different bypass) would directly contradict it. The narrower, more specific claim is falsifiable precisely because it specifies exactly what observation would disprove it.
Q2. solve_crackme.py's regex search could, in principle, find a false positive -- a string that happens to match flag{...} but isn't the actual answer. Why does the --verify step specifically resolve this, and why is regex matching alone insufficient?
A: A regex match only confirms the decoded bytes have the SHAPE of a flag (starts with `flag{`, ends with `}`) -- it says nothing about whether that specific string is the one the challenge actually checks for. Only running the real challenge binary against the candidate and observing its actual pass/fail verdict is authoritative, because the challenge's own comparison logic (not a pattern-shape heuristic) is the actual ground truth of correctness -- the same "don't just assert, actually test" principle this course applied as far back as Module 05's routing bug, which code review alone did not catch.
Q3. Distinguish coordinated disclosure from full disclosure from non-disclosure, and state the core tradeoff each one makes.
A: Full disclosure publishes immediately with no advance vendor notice -- forces urgency, but leaves users unprotected from the moment of publication until a fix exists. Coordinated disclosure notifies the vendor privately first and publishes only after a fix ships or a reasonable window elapses (conventionally ~90 days) -- protects users during the fix window, but depends on the vendor actually acting, which is why the time-bound window exists as a backstop. Non-disclosure never publishes at all -- avoids ever tipping off attackers, but denies other defenders and researchers the benefit of the finding, and removes any external pressure on the vendor to fix the issue.
Q4. Why does disclosure_timeline_checker.py treat early disclosure (before 90 days, no patch) as a flag needing justification rather than an automatic violation?
A: The 90-day window is a widely-adopted CONVENTION (associated with policies like Google Project Zero's), not a universal legal requirement -- and legitimate reasons to deviate genuinely exist, such as active exploitation already observed in the wild (where delaying disclosure would leave users MORE exposed, not less) or a vendor that has gone completely unresponsive after repeated good-faith contact attempts. Treating every early disclosure as an unconditional error would misrepresent how the field actually reasons about disclosure ethics -- a norm with documented, justifiable exceptions, not an absolute rule.
Q5. research_notes_checker.py requires both a "summary" and separate "evidence" field in the results section. Why isn't a strong, confident summary sufficient on its own?
A: A summary is a CLAIM; evidence is what makes the claim checkable by someone who wasn't there. A confidently-stated summary with no evidence is indistinguishable, to a skeptical reader, from a confidently-stated summary that happens to be wrong -- the confidence of the language carries no actual information about whether the claim is true. This is the same evidence-to-conclusion standard Module 18's forensic incident report required (specific packet numbers, timestamps, payload contents supporting each claim), applied here to research findings instead of incident findings.
Q6. Why does this module deliberately reuse Module 20's exact single-byte-XOR technique for crackme.c instead of introducing a new, harder obfuscation scheme?
A: The skill being practiced in THIS module is the CTF WORKFLOW itself (recognize the challenge category, apply a known technique, recover an answer, verify it, submit it) -- not the acquisition of a new technique. Reusing an already-mastered technique on a differently-shaped problem (a comparison target instead of a network address) isolates and tests whether that technique GENERALIZES, which is a more honest test of real understanding than either re-teaching the same trick from scratch or introducing an unrelated new skill that would conflate "did you learn the workflow" with "did you learn something brand new."
Q7. Synthesis: explain the shared epistemic structure connecting a CTF flag submission, a peer-reviewed research finding, and this course's own repeated "test what you built" discipline (Module 05's routing bug, Module 19's firewall verification, this module's --verify step).
A: All three follow the same structure: form a specific, checkable CLAIM (a candidate flag; a hypothesis; "this rule enforces isolation"), gather evidence through a defined, reproducible PROCESS (brute-force search; a documented experiment; an actual ping test), and accept the claim only once INDEPENDENTLY VERIFIED against ground truth (the challenge binary's own exit code; peer review/ reproducibility by others; the observed real behavior, not the configuration's stated intent). The domains are completely different -- a game, a scholarly field, a home-lab firewall rule -- but the underlying discipline (don't trust a plausible-looking claim without independently checking it against reality) is identical, and is precisely the standard a comprehensive exam committee applies to every answer you give them.
