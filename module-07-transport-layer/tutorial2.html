Module 07 — Deep Theory: TCP Reliability, Command by Command, Plus Congestion Control

1. Command-by-Command: Catching Real TCP States

netstat -an | findstr 9007 (Windows)

What each piece does: netstat reports active network connections and listening ports. -a means "show ALL connections and listening ports" (without it, some categories are hidden by default). -n means "numeric" — show raw IP addresses and port numbers rather than trying to resolve them to hostnames/service names, which is both faster and more precise for this kind of debugging. The output is piped (|) into findstr 9007, Windows' text-search utility, filtering the (potentially very long) full connection list down to just lines containing "9007" — the port tcp_echo_server.py listens on.

ss -tan | grep 9007 (Linux)

What each piece does: ss ("socket statistics") is the modern Linux replacement for the older netstat (which is deprecated on current Linux distributions but still common on Windows/Mac). -t restricts output to TCP sockets specifically (excluding UDP, Unix domain sockets, etc.); -a shows all sockets, not just established ones; -n again means numeric output. grep 9007 is the Linux/Mac equivalent of findstr — a general-purpose text search tool, filtering the output to matching lines.

Why does this command let you see a REAL kernel-level TCP state, when your own Python code never asked the kernel for it? Because TCP state (CLOSED, ESTABLISHED, TIME_WAIT, etc.) isn't something your application-level socket code tracks at all — it's tracked entirely inside the OS kernel's own TCP/IP stack implementation, for every socket on the system, regardless of which program owns it. netstat/ss are simply reading and reporting that kernel-internal state directly — this is precisely why this state is visible externally even though tcp_echo_client.py never explicitly asked for or printed it.

2. TCP's Reliability Mechanism, Fully Formal

tcp_state_machine.py deliberately simplified the ESTABLISHED state into "data transfer happens here" — the real mechanism underneath that simplification is worth understanding precisely for a comprehensive exam:

  • Sequence numbers: every byte TCP sends is assigned a sequence number (starting from a random Initial Sequence Number chosen at connection setup, for security — a predictable ISN historically enabled TCP session-hijacking attacks). The receiver uses sequence numbers to reassemble data in the CORRECT ORDER even if segments arrive out-of-order over the network.
  • Acknowledgment numbers: the receiver continuously tells the sender "I've successfully received everything up through byte N" via the ACK field. If the sender doesn't receive an ACK for previously-sent data within a calculated timeout, it RETRANSMITS — this is the actual mechanism providing "reliable delivery," not a single state transition but continuous, ongoing behavior throughout ESTABLISHED.
  • The sliding window: rather than waiting for an ACK after every single segment (which would be extremely slow), TCP allows multiple unacknowledged segments "in flight" simultaneously, up to a window size the receiver advertises (based on its own available buffer space) — this window can grow or shrink dynamically as conditions change.

3. Congestion Control: The Piece This Course's Code Never Simulates

Beyond RELIABILITY (does the data arrive, correctly ordered), TCP separately solves CONGESTION AVOIDANCE — preventing a sender from overwhelming the NETWORK PATH itself (routers' buffers, shared link capacity), as distinct from overwhelming the RECEIVER's buffer (which the sliding window / receive-window mechanism already handles).

Brain power: why does TCP treat PACKET LOSS specifically as its primary signal for "the network is congested," when loss can also be caused by unrelated things (a flaky Wi-Fi link, a genuine hardware error)? Historically, on wired networks, packet loss was OVERWHELMINGLY caused by router buffers overflowing under congestion, not by transmission errors — making loss a reasonably reliable congestion signal for the era TCP's classic congestion control algorithms (Reno, Tahoe) were designed in. This assumption becomes LESS reliable on modern wireless links (Wi-Fi, cellular), where loss from interference/signal quality is common and unrelated to actual congestion — which is part of why newer congestion control algorithms (e.g., BBR, used increasingly at Google/YouTube-scale) instead estimate congestion from measured bandwidth and round-trip-time changes, not loss alone.

4. Why the Initial Sequence Number Is Randomized

If a TCP connection's sequence numbers started predictably (e.g., always at 0), an attacker who could GUESS or predict a victim's sequence numbers could potentially inject forged data into an existing connection, or hijack a session, without needing to actually intercept the real traffic — they'd just need to send a spoofed packet with the source address forged and a correctly-guessed sequence number. Randomizing the Initial Sequence Number (a real historical security fix, following documented real-world TCP sequence-prediction attacks in the 1990s) makes this dramatically harder, since an attacker off-path (not actually intercepting real traffic) can no longer reliably predict what sequence number a legitimate segment would need.
