Module 07 — Tutorial

Goal: see TCP's reliability and UDP's lack of it side by side, on purpose-built demos, then confirm TCP's actual connection states on your own machine with the tools every network engineer reaches for first.

Step 1 — the state machine, on paper first

cd module-07-transport-layer
python tcp_state_machine.py
Expected: a full connect-transfer-close sequence for Client/Server, then a bonus "simultaneous close" scenario showing the CLOSING state — a transition that exists ONLY to handle both sides closing at nearly the same instant. Read every line; this is the reference you'll compare real output against in Step 3.

Step 2 — TCP: reliable, in order, exactly once

# terminal 1
python tcp_echo_server.py
# terminal 2
python tcp_echo_client.py
Expected: all 5 messages echo back identical to what was sent, in order. Nothing in tcp_echo_client.py handles retries, reordering, or loss — because TCP's own state machine (the one you just read in Step 1) does that work underneath the socket API, invisibly.

Step 3 — catch the real states with netstat/ss

While the client from Step 2 is still connected (add a time.sleep(5) in the client if you need more time), run in a third terminal:

# Windows
netstat -an | findstr 9007
# macOS/Linux
ss -tan | grep 9007
Expected: a line showing ESTABLISHED — the real OS-level TCP state, not a simulation, for the exact connection tcp_state_machine.py predicted. Run the same command again immediately after the client finishes and disconnects — you should catch TIME_WAIT for a few seconds before it disappears entirely. This was confirmed working during this module's own build.

Step 4 — UDP: no guarantees, made visible

# terminal 1
python udp_echo_server.py
# terminal 2
python udp_echo_client.py
Expected: roughly 30% of the 15 datagrams show "NO REPLY" — the server deliberately drops them to make loss visible instead of theoretical. Note the client has NO retry logic at all; a lost datagram is simply gone, forever, as far as this code is concerned. That's the entire meaning of "unreliable, connectionless" made concrete instead of quoted from a textbook.

Step 5 — run both the Node variants and compare

node tcp_echo_server.js     # separate port (9017) from the Python variant
node tcp_echo_client.js
node udp_echo_server.js     # separate port (9019)
node udp_echo_client.js
Same reliability/unreliability story, same percentages (allowing for the different, but equally seeded, random drop pattern) — two completely different socket APIs (socket vs. Node's net/dgram), same protocol-level guarantees underneath.

Exercises before Module 08

  1. Build retry logic on top of UDP. Modify udp_echo_client.py to resend a datagram up to 3 times if no reply arrives within the timeout, before giving up. Congratulations — you've just built a tiny piece of what DNS does over UDP (Module 08) and what TCP does automatically underneath every socket you've ever opened.
  2. Watch a real TCP connection's sequence numbers. Re-run Module 02's Wireshark capture setup against tcp_echo_server.py/client.py instead of the HTTP demo. Find the SYN packet's initial sequence number, and confirm each subsequent segment's sequence number increases by exactly the number of payload bytes in the previous segment — this is the mechanism underneath "TCP delivers data in order," made visible.
  3. Reproduce the simultaneous-close scenario for real. Modify both tcp_echo_server.py and a new client so both call close() at nearly the same moment (using threading and a shared start signal). Capture it in Wireshark and look for a CLOSING-adjacent pattern (both sides sending FIN before receiving the other's ACK) — harder to trigger reliably than the textbook case, which is itself an instructive lesson about timing-dependent protocol edge cases.
Before Module 08: you should be able to explain, without notes, what specifically TCP guarantees that UDP doesn't, and be able to point to the exact state transition where the guarantee "TCP delivers data reliably" actually happens (hint: it's not one transition — it's the retransmission/ACK behavior that happens continuously WHILE both sides sit in ESTABLISHED, which this module's state machine simplifies into "data transfer" but real TCP implements as a whole additional protocol layer of its own). Module 08 builds real DNS, DHCP, and HTTP servers — the application-layer protocols that ride on top of the transport guarantees (or lack thereof) you just watched directly.
