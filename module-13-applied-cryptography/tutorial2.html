Module 13 — Deep Theory: TLS 1.3, Certificate Chains, Command by Command

1. Decoding TLS_AES_256_GCM_SHA384, Piece by Piece

Every part of a TLS 1.3 cipher suite name specifies one concrete algorithm:

ComponentMeaning
AES_256The SYMMETRIC cipher used to encrypt the actual application data, with a 256-bit key — this is the "cheap, fast, bulk encryption" primitive Module 00a's headfirst.md previewed
GCMGalois/Counter Mode — the specific MODE OF OPERATION AES runs in, providing both encryption AND built-in authentication (detecting tampering) in one combined operation, called an AEAD (Authenticated Encryption with Associated Data) cipher
SHA384The hash function used for the handshake's own integrity/key-derivation purposes (HKDF, TLS 1.3's key derivation function, uses this internally) — NOT the same as an HMAC key or the certificate's own signature algorithm
Notice what's MISSING from TLS 1.3's cipher suite name compared to TLS 1.2's: TLS 1.2 suite names also specified the KEY EXCHANGE algorithm (e.g. TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384). TLS 1.3 removed this from the suite name because TLS 1.3 MANDATES (EC)DHE key exchange for every connection — there's no longer a choice to specify, since TLS 1.3 deliberately removed the older, weaker non-forward-secret key exchange options TLS 1.2 still allowed. This is a real, deliberate security hardening: TLS 1.3 structurally cannot negotiate a connection lacking forward secrecy, unlike TLS 1.2.

2. The TLS 1.3 Handshake, Message by Message

What actually happens when tls_client.py connects, underneath the single wrap_socket() call:

Client -> Server: ClientHello (supported cipher suites, a DH key share, SNI)
Server -> Client: ServerHello (chosen cipher suite, server's own DH key share)
                    [Server now derives handshake keys -- rest of server's
                     messages are already encrypted, unlike TLS 1.2]
Server -> Client: EncryptedExtensions, Certificate, CertificateVerify, Finished
Client:            verifies certificate chain (toy_ca.py's verify_chain() logic,
                    performed automatically by the TLS library)
Client -> Server: Finished
                    [Application data now flows, encrypted with derived session keys]
Comprehensive exam framing: "TLS 1.3 reduced the handshake to effectively '1 round trip' compared to TLS 1.2's 2. What specifically changed to make this possible?" TLS 1.2 required a separate round trip to first AGREE on parameters (cipher suite, key exchange method) before actually performing the key exchange. TLS 1.3 has the CLIENT proactively GUESS which key exchange group the server will accept and send its own key share immediately in the ClientHello (rather than waiting to be told what to send) — if the guess is right (usually is, for well-supported groups), the server can respond with everything needed to complete the handshake in one reply, collapsing what took 2 round trips into effectively 1. (If the client guesses wrong, an extra round trip — HelloRetryRequest — is still needed, an edge case worth knowing exists.)

3. Certificate Chain Validation, the Full Algorithm

toy_ca.py's verify_chain() checks ONE signature (leaf signed by root). A real browser's validation, for a typical 3-certificate chain (leaf → intermediate → root), performs SEVERAL checks, all of which must pass:

  1. Signature chain: leaf's signature verifies against intermediate's public key; intermediate's signature verifies against root's public key (exactly this module's check, chained one level deeper)
  2. Root trust: the ROOT certificate must already be present in the verifier's trusted root store (the ~100-150 CAs your OS/browser ships with) — nothing "verifies" the root itself; it's trusted by inclusion in this store, which is why Module 13's toy CA correctly fails verification everywhere except this course's own explicit cafile=ca_cert.pem trust
  3. Validity period: the current date must fall within EVERY certificate's own not_valid_before/not_valid_after window in the chain
  4. Revocation status: none of the certificates in the chain have been REVOKED before their natural expiration (checked via CRL or OCSP — exactly the check that produced this module's real schannel/curl finding)
  5. Name matching: the leaf certificate's Subject Alternative Name (or, historically, Subject Common Name) must match the hostname the client actually connected to

4. CRL vs. OCSP: Two Approaches to Revocation Checking

A CRL (Certificate Revocation List) is a periodically-published, downloadable LIST of every revoked certificate's serial number from a given CA — a client downloads the whole list and checks locally. OCSP (Online Certificate Status Protocol) instead lets a client ask, in REAL TIME, "is THIS ONE specific certificate revoked?" without downloading an entire list. OCSP is more bandwidth-efficient and provides fresher information, but requires a live query to the CA's OCSP responder for every connection (a real privacy concern — the CA learns which sites you're visiting — and a real availability concern if the responder is slow or down, which is why "OCSP stapling," where the SERVER itself periodically fetches and attaches its own OCSP response to the handshake, exists as a hybrid improvement).

5. Certificate Pinning and mTLS, Briefly

Certificate pinning: a client HARD-CODES which specific certificate (or public key) it will accept for a given host, rather than trusting ANY certificate that chains to a trusted root. This defends against a compromised or coerced CA issuing a fraudulent-but-technically-valid certificate for your domain — at the cost of operational fragility (rotating your own certificate now requires updating every pinned client too). mTLS (mutual TLS): this module's handshake only authenticated the SERVER (the client verified the server's certificate; the server never verified the client's identity). mTLS adds a CLIENT certificate too, with the server performing the same chain-verification logic against the client's cert — commonly used for service-to-service authentication in internal infrastructure, where both parties need cryptographic proof of the other's identity, not just one direction.
