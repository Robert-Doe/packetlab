Module 13 — Exam Practice

Answer out loud before revealing each answer.
Q1. Decompose TLS_AES_256_GCM_SHA384 into its components and explain what each one does.
A: AES_256: the symmetric cipher encrypting bulk application data, 256-bit key. GCM: the mode of operation, providing combined encryption AND authentication (an AEAD construction) in one operation. SHA384: the hash function used in TLS 1.3's key derivation (HKDF), not the certificate's own signature algorithm or an HMAC key directly.
Q2. Why does TLS 1.3's cipher suite naming omit the key exchange algorithm that TLS 1.2's suite names included?
A: TLS 1.3 mandates (EC)DHE key exchange for every connection -- there's no longer a choice to specify or negotiate, since TLS 1.3 deliberately removed the older, non-forward-secret key exchange options TLS 1.2 still permitted. Since every TLS 1.3 connection uses the same category of key exchange, naming it in the suite string would be redundant.
Q3. Explain precisely how TLS 1.3 achieves an effectively 1-round-trip handshake, and name the edge case where an extra round trip is still needed.
A: The client proactively sends a key share for a GUESSED key exchange group in its very first message (ClientHello), rather than waiting to be told which group to use. If the guess matches what the server supports (the common case for well-supported groups), the server can respond with everything needed to complete the handshake in a single reply. The edge case: if the client's guessed group isn't supported, the server sends a HelloRetryRequest, requiring an additional round trip -- an exception to the "1-RTT" characterization worth knowing.
Q4. List all 5 categories of check a real browser performs when validating a certificate chain, beyond just verifying signatures.
A: (1) Signature chain validity (each certificate's signature verifies against its issuer's public key, all the way up). (2) Root trust (the root certificate must already be present in the verifier's trusted root store). (3) Validity period (current date within every certificate's not-before/not-after window). (4) Revocation status (none of the certificates have been revoked, via CRL or OCSP). (5) Name matching (the leaf certificate's SAN/CN must match the hostname actually connected to).
Q5. Distinguish CRL from OCSP, and explain the specific tradeoffs of each.
A: A CRL is a periodically-published list of every revoked certificate's serial number from a CA -- a client downloads the whole list and checks locally, which is bandwidth-inefficient and can be stale between publications. OCSP lets a client ask in real time whether ONE specific certificate is revoked, more bandwidth-efficient and fresher, but requires a live query to the CA's OCSP responder for every connection -- a privacy concern (the CA learns which sites you visit) and an availability concern if the responder is slow or unreachable, which is why OCSP stapling (the server itself periodically fetches and attaches its own OCSP response) exists as a hybrid improvement.
Q6. Explain certificate pinning: what specific attack does it defend against, and what operational cost does it impose?
A: Pinning hard-codes which specific certificate (or public key) a client will accept for a given host, rather than trusting ANY certificate that chains to a trusted root. It defends against a compromised or coerced CA issuing a fraudulent-but-technically-chain-valid certificate for a domain it shouldn't have authority over. The operational cost: rotating your own certificate now requires updating every client that has it pinned, creating real fragility if pinned clients can't be updated in sync with certificate rotation.
Q7. Synthesis: explain mTLS and why it's specifically useful for service-to-service authentication in internal infrastructure, connecting to Module 13's own one-directional handshake.
A: This module's TLS handshake authenticated only the SERVER -- the client verified the server's certificate, but the server never verified the client's identity cryptographically. mTLS adds a CLIENT certificate, with the server performing the same chain-verification logic against it, achieving mutual (bidirectional) cryptographic identity proof. This is specifically valuable for service-to-service communication in internal infrastructure (e.g., microservices, Module 17's cloud networking context) where BOTH parties need proof of the other's identity -- not just "is this a legitimate server" (one-directional, sufficient for a browser visiting a public website) but also "is this a legitimate, authorized calling service," which one-directional TLS alone cannot establish.
