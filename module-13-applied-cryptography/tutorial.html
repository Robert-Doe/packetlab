Module 13 — Tutorial

Goal: build a real Certificate Authority, issue a real certificate, and use it to complete a real TLS 1.3 handshake — then watch that same handshake genuinely fail when the CA isn't trusted, exactly like a browser's "connection not private" warning.

Step 1 — build a real CA and issue a real certificate

cd module-13-applied-cryptography
python -m venv venv && venv\Scripts\activate
pip install -r requirements.txt
python toy_ca.py
Expected: a self-signed root CA (RSA-2048), a leaf certificate for lab.test signed by that CA, a successful signature verification, and — critically — a FAILED verification when checked against a different, unrelated CA (InvalidSignature). This last check is exactly what a browser does when a site presents a certificate signed by a CA it doesn't recognize.

Step 2 — a real TLS handshake, both outcomes

# terminal 1
python tls_server.py
# terminal 2
python tls_client.py
Expected: Attempt 1 (trusting the toy CA) succeeds — TLS 1.3, a real negotiated cipher suite (TLS_AES_256_GCM_SHA384 during this module's testing), and the peer certificate's subject correctly showing lab.test. Attempt 2 (not trusting the toy CA) FAILS with a real CERTIFICATE_VERIFY_FAILED error — and the server's own log shows the client's rejection arriving as a real TLS alert (UNKNOWN_CA). Both sides of a real failed handshake, visible.

Step 3 — cross-language interop

# server still running from Step 2
node tls_client.js
Expected: Node's completely independent TLS implementation (not a port of the Python code — the actual tls module, calling into a different OpenSSL binding) validates the SAME Python-generated certificate correctly, negotiates real TLS 1.3, and gets the same real response. Confirmed during this module's build: Attempt 2 fails with Node's own UNABLE_TO_VERIFY_LEAF_SIGNATURE error — different wording than Python's error, same underlying cryptographic fact.
If you try curl on Windows: Windows' curl uses the OS's schannel library by default, which does certificate revocation checking (CRL/OCSP) — and a toy CA has no revocation infrastructure, so schannel fails with CERT_TRUST_REVOCATION_STATUS_UNKNOWN even though the certificate itself is completely valid (confirmed during this module's build: adding --ssl-no-revoke succeeds). This is a real, useful lesson about a difference between TLS libraries, not a flaw in your certificate.

Exercises before Module 14

  1. Tamper with a certificate and watch verification fail for real. Load leaf_cert.pem, flip a single byte in its DER-encoded signature, and try verify_chain() again — confirm it now raises InvalidSignature. This is the actual mechanism (not a policy, not a convention) that makes certificate tampering detectable.
  2. Build an intermediate CA. Real PKI is rarely just root → leaf; it's root → intermediate → leaf. Extend toy_ca.py to issue an intermediate CA certificate (signed by the root, itself allowed to sign other certs via BasicConstraints(ca=True)), then issue a leaf from the intermediate instead of the root. Verify the full 3-certificate chain.
  3. Inspect a real website's certificate chain. Visit any HTTPS site in a browser, view its certificate details — find the chain from leaf → intermediate → root, and identify which real CA organization issued it. Compare its structure to what toy_ca.py built.
Before Module 14: you should be able to explain, from memory, what specifically makes a certificate trustworthy (a valid signature chain back to something you already trust) versus what doesn't matter (who claims to have issued it, in plain text — anyone can put any name in a Subject field). Module 14 puts everything from Modules 01-13 together into real network security monitoring — Wireshark mastery, and your first taste of intrusion detection.
