Module 04 — Exam Practice

Answer out loud before revealing each answer. Work the binary math on paper for the computation questions -- don't just recall the final number.
Q1. What specific problem did CIDR solve that classful (A/B/C) addressing could not?
A: Classful addressing only offered three fixed network sizes (/8, /16, /24), forcing organizations to round up to a size that often wasted enormous numbers of addresses (e.g., needing 300 addresses meant taking an entire Class B's 65,536, since a Class C's 254 wasn't enough). CIDR allows any prefix length from 0-32, letting allocated network size match actual need -- directly addressing IPv4 address space exhaustion concerns that classful addressing was making worse.
Q2. Compute, by hand, the network address, broadcast address, and usable host range of 172.16.50.100/22. Show the binary work for the third octet.
A: /22 = 255.255.252.0. Third octet: 50 = 00110010, mask's third octet = 252 = 11111100. AND: 00110010 & 11111100 = 00110000 = 48. Network = 172.16.48.0. Block size = 2^(32-22) = 1024 addresses, so broadcast = 172.16.51.255 (48 + 4 - 1 = 51 for the third octet, .255 for the last). Usable range: 172.16.48.1 - 172.16.51.254 (1022 usable hosts).
Q3. Why must a VLSM-allocated subnet's starting address be an exact multiple of its own block size, rather than any arbitrary unused address?
A: The network address is defined as (IP AND mask) -- for this operation to correctly identify a subnet's own clean starting boundary, every bit in the host portion (where the mask has 0s) must be simultaneously zero at that address. This is only true at addresses that are exact multiples of the block size -- e.g. a /25 (128-address) block can only correctly start at .0 or .128 within a /24, never at .64, because .64 has a 1 bit within what would be the host portion, meaning AND-ing with a /25 mask wouldn't return .64 itself.
Q4. Explain why /31 is a special case, and what real-world scenario RFC 3021 was written to address.
A: The usual "reserve network and broadcast addresses" convention requires enough address space to distinguish "the whole block" and "everyone in it" from individual hosts -- meaningless in a 2-address block, since reserving 2 addresses would leave zero for actual hosts. RFC 3021 addressed point-to-point WAN/router links specifically, where a link inherently has exactly 2 devices and "broadcast to everyone on this segment" is a meaningless concept anyway -- redefining /31 so both addresses are usable host addresses, eliminating the waste of a traditional /30 (4 addresses, only 2 usable) for such links.
Q5. Why does vlsm_allocate() sort requirements largest-first before allocating, rather than allocating in the order given?
A: Larger blocks have stricter alignment requirements (fewer valid starting positions within the base network) than smaller blocks. Placing large, alignment-picky requirements first and letting smaller, more flexible requirements fill the remaining gaps afterward minimizes wasted address space and avoids a scenario where allocating in arbitrary order leaves insufficient contiguous, correctly-aligned space for a later large requirement even though the total remaining address count would technically have been sufficient.
Q6. Why is Node's cross-language self-test (shelling out to subnet_calc.py) still valid proof of correctness, given Node has no bundled IP-address standard library to test against directly?
A: Because subnet_calc.py was ALREADY independently validated against Python's own official `ipaddress` standard library module across 500 random cases. Confirming Node's output matches Python's output transitively confirms Node against the same authoritative source, one hop removed -- a valid chain of trust, not a weaker or circular test, as long as the Python side's own validation is trustworthy (which it is, confirmed separately).
Q7. Synthesis: a network engineer says "I always just use /24 for everything, it's simpler." What's the real cost of this approach, connecting to VLSM's actual purpose?
A: Using a fixed /24 (254 usable hosts) for every segment regardless of actual need wastes address space badly for small segments (a 2-host point-to-point link consuming 254 potential addresses) and could be insufficient for segments genuinely needing more than 254 hosts. VLSM's entire purpose is matching each segment's allocated size to its actual requirement -- a large segment gets a large block, a point-to-point link gets a /31, minimizing waste while still guaranteeing enough room for legitimate growth in each segment sized appropriately. The "simplicity" of always using /24 trades real address efficiency for convenience, which matters more at scale (a large organization or ISP) than in a small home lab where the waste is easily affordable.
