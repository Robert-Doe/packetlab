Module 00b — Tutorial

Goal: compile and run real C, see exactly what Python's struct and Node's Buffer are doing underneath, and watch a real buffer overflow corrupt memory — safely, in a sandbox, purely to understand why the bug class exists.

You need a C compiler. On Windows, the easiest path is WSL (Windows Subsystem for Linux) with Ubuntu — wsl --install if you don't have it, then sudo apt install gcc inside it. Every command below assumes you're running from inside a Linux shell (WSL, or any real Linux/Mac machine).

Step 1 — the exact same protocol bytes, in C

cd module-00b-c-for-protocol-internals
gcc -Wall -o protocol_struct protocol_struct.c
./protocol_struct
Expected: sizeof() confirms each packed struct is exactly the byte count the protocol spec requires (14/20/20), and the printed hex — confirmed during this module's build — is byte-for-byte identical to Module 02's Python layer_builder.py output for the same logical values (aa bb cc 00 00 01 aa bb cc 00 00 02 08 00 for the Ethernet header, etc.). Same protocol, two completely different languages, identical wire bytes.

Step 2 — pointers, made visible

gcc -Wall -o pointers_and_memory pointers_and_memory.c
./pointers_and_memory
Expected: real memory addresses printed (yours will differ from any example), and confirmation that &numbers[1] sits exactly 4 bytes after &numbers[0] — proving array indexing really is pointer arithmetic, not a separate mechanism. The final section shows a function writing INTO a buffer the caller owns, exactly the pattern recv() uses.

Step 3 — a real buffer overflow, two ways

gcc -Wall -o overflow_protected buffer_overflow_demo.c
./overflow_protected
Expected (confirmed during this module's build): the program prints its progress, then aborts with *** stack smashing detected ***: terminated. Notice adjacent_guard printed UNCHANGED (0x1234) both before and after the overflow — modern GCC's stack protector doesn't just add a canary value, it also reorders local variables to keep buffers away from scalars specifically to prevent this kind of adjacent-variable corruption. The corruption still happened — just to the compiler's own hidden canary, not to your visible variable — which is exactly what triggered the abort.
gcc -Wall -fno-stack-protector -o overflow_unprotected buffer_overflow_demo.c
./overflow_unprotected
Expected (confirmed during this module's build): adjacent_guard now shows 0x41414141 after the copy — literally the ASCII bytes for "AAAA", the overflowing input, having spilled directly into adjacent memory. The program then segfaults shortly after, because the overflow kept going past adjacent_guard and corrupted the function's saved stack metadata too.
This demonstrates memory CORRUPTION — a crash, and visibly clobbered adjacent data. It does not construct a working exploit (no shellcode, no control-flow hijack to attacker-chosen code). That's a meaningfully different, further topic than this module covers.

Step 4 — the memory-safe contrast

node memory_safety_contrast.js
Expected: Node's Buffer.write() silently truncates an oversized write (no crash, no corruption, buffer length unchanged) while Uint8Array.set() throws a catchable RangeError instead — two different but both SAFE behaviors, neither of which is "let it silently corrupt whatever memory happens to be next," which is what C's strcpy() just did.
