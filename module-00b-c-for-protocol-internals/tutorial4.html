1. What Memory Actually Is — RAM, Addresses, and Bytes

Before pointers make any sense, get the physical picture solid. Your computer's RAM (Random Access Memory) is, conceptually, one enormous array of BYTES — literally billions of them, each one holding a number from 0 to 255 (Module 00a Section 2.3 — exactly what an 8-bit value can represent). Every single byte in this giant array has a unique numeric ADDRESS — its position in the array, exactly the way every house on a street has a unique address. "Random Access" specifically means the CPU can jump directly to ANY address in roughly constant time — unlike, say, a tape you'd have to wind through sequentially.

When a C program declares int x = 5;, what ACTUALLY happens: the compiler reserves some number of consecutive bytes (4, for a typical int) somewhere in this giant array, and "x" becomes a human-readable NAME the compiler uses, at compile time, to remember which specific address those 4 bytes start at. At runtime, there is no "x" anywhere in memory — only 4 bytes at some specific address, holding the bit pattern for the number 5.

Brain power: if variable names don't exist at runtime, only addresses and bytes, what is a POINTER, at the most basic level? A pointer is simply a variable whose VALUE is an address — a number identifying WHERE some other data lives in that giant byte array, rather than being the data itself. Section 2 makes this completely concrete with real, runnable code.

2. Pointers, From Absolute Zero, With Many Scenarios

2.1 — Declaring and using a pointer, mechanically

int x = 5;
int *p = &x;   /* p now HOLDS the address of x */

printf("%d\n", x);    // 5           -- the VALUE stored at x's address
printf("%p\n", (void*)&x);  // e.g. 0x7ffee3a1c  -- x's ADDRESS itself
printf("%p\n", (void*)p);   // e.g. 0x7ffee3a1c  -- SAME address, now held in p
printf("%d\n", *p);   // 5           -- DEREFERENCING p: "go to the address p holds, read what's there"

Three distinct operators are doing three distinct jobs here: &x ("address-of") asks "where does x live?" and produces an address. int *p declares a variable whose type is "pointer to int" — meaning it's meant to HOLD an address of somewhere an int lives. *p ("dereference") means "go to the address stored in p, and treat whatever is there as an int" — reading (or writing) the actual data, not the address.

Worked scenario: modifying a variable through a pointer, traced step by step

int x = 5;
int *p = &x;
*p = 99;              // "go to the address p holds, and STORE 99 there"
printf("%d\n", x);    // prints 99 -- x itself changed!

This is not magic and not "aliasing" in some mysterious sense — p holds the EXACT SAME address x lives at, so writing through *p writes to the exact same bytes that reading x reads from. There is only ONE piece of memory involved the whole time; x and *p are two different NAMES for accessing the identical bytes.

2.2 — Array indexing IS pointer arithmetic

This module's own pointers_and_memory.c proves something most beginners are simply told to accept: numbers[1] and *(numbers + 1) are not just similar — they are LITERALLY the same operation, and the compiler treats numbers[i] as pure syntactic sugar for *(numbers + i).

Worked scenario: proving array indexing is pointer arithmetic, with real addresses

int numbers[3] = {10, 20, 30};

printf("%p\n", (void*)&numbers[0]);   // e.g. 0x7ffee3a1c0
printf("%p\n", (void*)&numbers[1]);   // e.g. 0x7ffee3a1c4  <- exactly 4 bytes later
printf("%p\n", (void*)&numbers[2]);   // e.g. 0x7ffee3a1c8  <- exactly 4 bytes later again

Each address is exactly 4 bytes after the previous one — because sizeof(int) == 4 on this platform, and numbers + 1 doesn't mean "add 1 to the address's raw number" — it means "advance by 1 ELEMENT of whatever type this pointer points to," which the compiler automatically translates into "add 1 × sizeof(int) bytes." This is precisely why pointer arithmetic is TYPE-AWARE: char * arithmetic advances 1 byte per step, int * arithmetic advances 4 bytes per step, and a struct ipv4_header * (Section 3) would advance a full 20 bytes per step — all from the exact same +1 syntax.

Why does this matter for understanding recv()-style network code (this module's own simulate_recv_into_buffer() pattern)? A function that "writes incoming network data into a buffer the CALLER owns" is using EXACTLY this mechanism: the caller passes a POINTER to some memory it already allocated (an address), and the function writes bytes starting at that address, advancing byte by byte as data arrives. No "array" object is ever passed around — only an address and, critically, a SEPARATE size parameter telling the function how many bytes of space actually exist at that address (Section 6 covers exactly what happens when that size parameter is missing or ignored).

2.3 — What a "null pointer" and "dangling pointer" actually are

Scenario: the difference between a pointer that points nowhere, and one that points somewhere INVALID

A NULL pointer (int *p = NULL;) holds the special address value 0, by convention meaning "intentionally points to nothing." Dereferencing it (*p) is undefined behavior — most commonly, on a real OS, this triggers a segmentation fault (the OS detects the program trying to access address 0, which it has deliberately never mapped to any real memory precisely so this mistake is loud and immediate rather than silent).

A DANGLING pointer is different and more dangerous: it holds the address of memory that WAS valid but has since been freed or gone out of scope — the pointer variable itself hasn't changed, but what it points to is no longer legitimately yours to read or write. Dereferencing a dangling pointer might crash, might silently read garbage leftover data, or (worst case) might read or corrupt memory that's since been reallocated for something completely different — a real, serious bug class in C and C++ (this course doesn't build a dangling-pointer demo directly, but recognizing the distinction from a null pointer is a real, frequently-tested concept).

3. Structs, Padding, and Alignment — Full Byte-Offset Diagrams

3.1 — Why structs need __attribute__((packed)) at all

By DEFAULT, a C compiler is free to insert invisible PADDING bytes between struct fields, to align each field to an address that's a multiple of its own size — because many CPUs access aligned data faster (and some older/embedded CPUs cannot access misaligned data at all). This default is a PERFORMANCE optimization for ordinary in-memory data structures — but it is exactly WRONG for network protocol headers, which define an EXACT byte layout with zero slack, specified by a standards document (an RFC), not by whatever your particular CPU finds convenient.

Worked scenario: what protocol_struct.c's ethernet_header would look like WITHOUT packing

struct ethernet_header {       // WITHOUT __attribute__((packed))
    uint8_t  dst_mac[6];       // 6 bytes, offset 0-5
    uint8_t  src_mac[6];       // 6 bytes, offset 6-11
    uint16_t ethertype;        // needs 2-byte alignment --
                                // offset 12 IS already a multiple of 2, so
                                // NO padding needed here specifically
};
// sizeof would be 14 in THIS particular case -- but this is a coincidence
// of THESE field sizes/order, not a guarantee, which is exactly why
// __attribute__((packed)) is used explicitly rather than relied upon by luck.

Now compare a case where padding WOULD silently appear:

struct hypothetical_bad_layout {   // WITHOUT packed -- illustrative, not in this module's real code
    uint8_t  a;      // offset 0
    uint32_t b;      // needs 4-byte alignment -- compiler inserts
                      // 3 PADDING bytes at offset 1,2,3 (invisible, unused)
                      // b actually starts at offset 4
};
// sizeof = 8, NOT 5 (1 + 4) -- 3 invisible padding bytes were inserted

This second example is EXACTLY the failure mode __attribute__((packed)) exists to prevent: if you tried to send this second struct's raw bytes over a network expecting a receiver to parse it per an RFC's exact byte layout, the receiver would misinterpret every field after the padding — reading garbage where b's real value should be, because it would expect b at byte offset 1, not offset 4.

4. Endianness — htons/htonl Traced Byte By Byte

4.1 — What "byte order" even means, concretely

A multi-byte number (like the 16-bit total_length field, value 40) can be stored in memory in more than one valid byte ORDER. "Big-endian" stores the MOST significant byte FIRST (at the lowest address); "little-endian" stores the LEAST significant byte first. Both are internally consistent — the ambiguity only matters when two DIFFERENT machines (potentially using different native byte orders) need to exchange the same bytes and agree on how to interpret them.

Worked scenario: the number 40, in both byte orders, fully shown

40 decimal = 0x0028 in hex (a 16-bit value)

Big-endian storage (network byte order -- what actually goes on the wire):
  byte[0] = 0x00   (the MOST significant byte, 0x00)
  byte[1] = 0x28   (the LEAST significant byte, 0x28)

Little-endian storage (what a typical x86/x86-64 CPU uses NATIVELY in memory):
  byte[0] = 0x28   (the LEAST significant byte first)
  byte[1] = 0x00   (the MOST significant byte second)

Both representations encode the SAME number (40) — they differ only in WHICH byte comes first in memory/on the wire. This is precisely why protocol_struct.c calls htons(40) rather than just assigning 40 directly: on a little-endian machine (virtually all consumer x86/x86-64/ARM hardware today), the raw in-memory representation of the integer 40 would place the bytes in LITTLE-endian order — but the IPv4 spec REQUIRES big-endian ("network byte order") on the wire. htons() ("host to network, short" — "short" meaning a 16-bit value) performs the actual byte-SWAP when the host is little-endian (and does nothing at all, a no-op, on a big-endian host — which is why the function exists at all: the SAME source code produces correct wire bytes regardless of which byte order the host CPU natively uses).

Why is the standard called "network byte order" and not just "big-endian"? Because the terminology deliberately ties the CONCEPT (a specific, fixed byte order) to its PURPOSE (interoperability across a network of possibly-different-endianness machines) — any two machines, regardless of their own NATIVE/host byte order, can correctly exchange data as long as they both agree to convert to/from this one standard order at the network boundary. This is exactly the same "agree on ONE canonical format at the boundary, regardless of internal representation" principle Module 08's DNS wire format and Module 18's libpcap format both apply.

4.2 — htonl vs. htons — why two different functions

htons() ("host to network SHORT") operates on 16-bit values; htonl() ("host to network LONG") operates on 32-bit values — protocol_struct.c uses htonl(1000) for the TCP header's 32-bit sequence number specifically because a 16-bit swap function applied to a 32-bit value would swap the WRONG byte boundaries, producing a completely wrong result rather than an error — always match the swap function's bit-width to the field's actual size.

5. The Stack, In Complete Detail — What A "Stack Frame" Physically Is

5.1 — The stack as a real, physical region of memory

Every running program has a dedicated region of its address space called THE STACK, used specifically for function calls' local variables and bookkeeping. It's called a "stack" because it grows and shrinks in LIFO (last-in-first-out) order — exactly like a physical stack of plates: calling a function PUSHES a new "stack frame" on top (reserving space for that function's local variables), and returning from a function POPS that frame off, instantly freeing that space for reuse by whatever gets called next.

5.2 — vulnerable_copy()'s actual stack frame, laid out concretely

When main() calls vulnerable_copy(), a new stack frame is pushed containing (roughly, compiler- and platform-dependent in exact details, but this ordering is representative of what actually happens on typical x86-64/gcc, WITHOUT the stack protector reordering discussed in Section 7):

Higher memory addresses
    |
    | [return address]      -- where to jump back to in main() when
    |                          vulnerable_copy() finishes
    | [saved base pointer]  -- main()'s own frame pointer, saved so
    |                          it can be restored on return
    | [adjacent_guard]      -- the 4-byte int, value 0x1234
    | [small_buffer[7]]     -- the LAST byte of the 8-byte buffer
    | [small_buffer[6]]
    | ...
    | [small_buffer[0]]     -- the FIRST byte of the 8-byte buffer
    |
Lower memory addresses  <- the stack GROWS DOWNWARD (toward lower
                            addresses) on essentially all common
                            architectures, meaning small_buffer sits
                            at a LOWER address than adjacent_guard

The single most important fact this diagram reveals: small_buffer sits at a LOWER address than adjacent_guard, and writing PAST the end of small_buffer (via an oversized strcpy()) writes toward HIGHER addresses — directly toward, and then past, adjacent_guard, and eventually toward the saved base pointer and return address themselves. This is not a metaphor — this is the literal, physical reason a buffer overflow can corrupt a neighboring variable and, if it goes far enough, even the function's own return address.

Brain power: if the stack "grows downward," why does writing PAST the end of a buffer corrupt data at HIGHER addresses, rather than lower ones? Because strcpy() writes FORWARD, byte by byte, starting at small_buffer's own starting address and increasing — it has no concept of "the stack grows downward" at all; it simply keeps incrementing the destination address by one for each source byte until it hits a null terminator. Since adjacent_guard happens to sit at a HIGHER address than small_buffer in this frame's layout, that's the direction the overflow travels into.

small_buffer has room for exactly 8 bytes (indices 0-7).
The source string has 20 'A' characters PLUS a null terminator = 21 bytes total.

strcpy() copies byte by byte, with ZERO awareness of small_buffer's real size:

  small_buffer[0] = 'A'   (0x41)
  small_buffer[1] = 'A'
  small_buffer[2] = 'A'
  small_buffer[3] = 'A'
  small_buffer[4] = 'A'
  small_buffer[5] = 'A'

  -- everything below this line is OUT OF BOUNDS, but strcpy() keeps going --

  [byte at small_buffer+8]  = 'A'   <- this address is adjacent_guard's
  [byte at small_buffer+9]  = 'A'      first byte!
  [byte at small_buffer+10] = 'A'

  [byte at small_buffer+12] = 'A'   <- continues past adjacent_guard too,

                                        stack metadata

6.2 — Trace 2: the PROTECTED build (default gcc stack protector)

With the stack protector active, gcc does two things this module's own real testing confirmed empirically: it inserts a hidden "canary" value between the buffer and the return address (Section 7 explains the mechanism), AND — this is the part that surprised this module's own build — it REORDERS local variables specifically to place buffers CLOSER to the canary/return address and scalar variables like adjacent_guard FURTHER AWAY, specifically to defeat exactly the kind of "corrupt the neighboring variable" demonstration this module originally intended.

What actually happened in the protected build, per this module's own confirmed testing

adjacent_guard printed UNCHANGED (0x1234) both before AND after the overflow — the overflow's bytes went somewhere else in the reordered frame, hit the (differently-positioned) canary value instead, and the program detected the corrupted canary and called abort(), printing *** stack smashing detected ***: terminated. The corruption still genuinely happened — it just landed on the compiler's own hidden protection value instead of the visible adjacent_guard variable, which is EXACTLY the intended effect of the mitigation.

Comprehensive exam framing: "A student expects a stack buffer overflow to always corrupt the very next declared variable in source-code order. Explain why this assumption is unreliable on a modern compiler." Modern compilers (gcc, clang, by default) actively REORDER local stack variables specifically as a security mitigation — placing buffers as close as possible to the stack canary/return address and scalar variables further away, precisely to minimize the chance an overflow reaches something the program actually uses for a security- relevant decision before it's detected. Source-code declaration order is NOT a reliable predictor of actual memory layout once this optimization is active — this module's own real, observed testing (Section 6.2) demonstrates exactly this: adjacent_guard, declared immediately after small_buffer in the source, was NOT the first thing corrupted once the compiler's reordering was active.

7. Stack Canaries — What They Detect And How

A "canary" (named after the historical practice of caged canaries in coal mines, whose deaths from gas before humans noticed served as an early-warning signal) is a specific, hard-to-guess value the compiler inserts BETWEEN a stack buffer and the critical data (saved base pointer, return address) an overflow would otherwise reach.

7.1 — The mechanism, precisely

  1. At the START of a function that has a stack buffer, the compiler inserts code to write a canary value (typically derived from a per-process random value chosen at program startup, making it hard for an attacker to predict or guess in advance) into a specific stack location, right before the return address.
  2. At the END of that function, right before actually returning, the compiler inserts code to RE-READ that same stack location and compare it against the expected canary value.
  3. If they DON'T match, something between steps 1 and 2 overwrote the canary — the ONLY way this can happen in normal operation is a buffer overflow that wrote PAST its intended space and reached the canary's position. The generated code calls abort() immediately (triggering SIGABRT, the signal Section 9's code comment discusses) rather than allowing the function to actually return using a potentially-also-corrupted return address.
Why does a corrupted canary specifically imply the RETURN ADDRESS might ALSO be corrupted, given the canary sits BETWEEN the buffer and the return address? Because strcpy() (and buffer overflows generally) write FORWARD, byte by byte, with no way to selectively "skip over" the canary and land only on data further along — if the overflow was long enough to reach and corrupt the canary, and the return address sits at an EVEN HIGHER address (further in the same forward-writing direction), a sufficiently long overflow would have kept going and corrupted the return address too. Detecting the canary's corruption is used as an EARLY-WARNING PROXY specifically because checking the actual return address directly, after it's already been used to jump execution, would be too late — the canary check happens BEFORE the vulnerable return actually executes.

8. strcpy vs. strncpy vs. snprintf — Precisely

FunctionBounds-aware?Behavior
strcpy(dst, src)NOCopies bytes from src until it finds a null terminator, with ZERO knowledge of how large dst actually is. This is exactly the bug this module demonstrates — the function has no way to know or check "is there actually room."
strncpy(dst, src, n)PartiallyCopies AT MOST n bytes — genuinely prevents the overflow. But has a real, frequently-tripped-over gotcha: if src is n bytes or longer, strncpy() does NOT null-terminate dst automatically — the caller must do so manually (exactly what this module's Exercise 1 asks you to add: "null-terminate manually").
snprintf(dst, n, "%s", src)Yes, fullyCopies at most n-1 bytes AND always null-terminates correctly (reserving the last byte specifically for the terminator) — generally considered the safest, most modern choice for this kind of copy, precisely because it has no equivalent gotcha to strncpy's missing-terminator trap.
Common mistake when "fixing" a strcpy() bug: switching to strncpy() but forgetting the manual null-termination step. strncpy(small_buffer, input, sizeof(small_buffer)) alone is STILL potentially unsafe — if input is 8 or more bytes long, small_buffer ends up completely full of copied bytes with NO null terminator anywhere, meaning any subsequent code that treats small_buffer as a normal C string (searching for its end via the null terminator, like printf("%s", small_buffer) does) will keep reading PAST the buffer's end looking for a terminator that isn't there — a DIFFERENT out-of-bounds READ bug, distinct from but just as real as the original overflow. The correct fix (this module's own Exercise 1) copies at most sizeof(small_buffer) - 1 bytes, reserving the LAST byte specifically to be manually set to '\0'.

10. Full Code Walkthrough — buffer_overflow_demo.c

10.1 — setvbuf(), and why it was necessary

setvbuf(stdout, NULL, _IONBF, 0);

This line exists because of a REAL bug this module's own build hit: printf()'s output isn't necessarily written to your terminal immediately — by default, stdout is often LINE-buffered (when connected to a terminal) or fully BUFFERED (when redirected to a file or pipe), meaning output waits in an internal buffer until either a newline is written (line-buffered) or the buffer fills up (full buffering) or the program exits NORMALLY. When the stack protector calls abort() (Section 7), the process terminates via a SIGNAL (SIGABRT) — an ABNORMAL exit that does NOT run the normal end-of-program cleanup that would otherwise flush any still-buffered output. Without setvbuf(..., _IONBF, 0) ("IO No Buffering," buffer size 0), every printf() call in the protected build's output was silently LOST — the program's actual behavior was correct the whole time, but nothing was visible, purely because of an unrelated I/O buffering detail. This is a genuinely common, real-world debugging trap: "my program isn't doing X" often actually means "my program did X, but the evidence never got flushed before the process ended."

10.2 — The if/else after the copy, and why BOTH branches matter

if (adjacent_guard != 0x1234) {
    printf("  >>> adjacent_guard was CORRUPTED by the overflow. <<<\n");
} else {
    printf("  adjacent_guard is unchanged (input fit, or your compiler's\n");
    printf("  stack layout put something else adjacent -- see DECISIONS.md)\n");
}

This code is written to give a MEANINGFUL result either way — not just for the unprotected build (where adjacent_guard IS corrupted, per Section 6.1) but ALSO for the protected build (where, per Section 6.2's real finding, it ISN'T corrupted, because the compiler reordered variables and redirected the corruption elsewhere). The else branch's comment explicitly acknowledges the possibility that stack layout could differ — this is honest, defensive documentation of a REAL platform/compiler-dependent behavior, not a bug being hidden.

11. Troubleshooting and Common Confusions

Confusion: "If I run the protected build multiple times, will adjacent_guard always print exactly 0x1234, every single time?"

On THIS module's specific compiler/platform combination, yes, consistently — but this is NOT guaranteed universally. Stack layout and variable reordering decisions are made by the SPECIFIC compiler version you're using, and different compilers (or even different optimization levels of the same compiler) could make different reordering choices. This is precisely why the tutorial frames the observed 0x1234-unchanged result as "confirmed during this module's build" rather than as an absolute, universal law of C — it's an empirical finding about THIS specific tested environment, one you should verify for yourself rather than assume holds everywhere.

Confusion: "gcc -Wall didn't warn me about the dangerous strcpy() call — shouldn't a good compiler catch this?"

-Wall enables a broad, commonly-useful set of warnings, but detecting "this specific strcpy call MIGHT overflow this specific buffer" in general requires genuinely sophisticated data-flow analysis that basic compiler warnings don't perform (though some compilers DO offer additional, stricter warning flags, like -Wstringop-overflow on newer gcc versions, that can catch SOME cases where the buffer and the source are both compile-time-visible enough to analyze). The stack protector (Section 7) is a RUNTIME mitigation specifically because reliably catching every possible overflow at COMPILE time, for arbitrary code, is not generally solvable — this is directly related to the halting problem's undecidability, a genuinely deep computer science result, not merely "the compiler didn't try hard enough."
