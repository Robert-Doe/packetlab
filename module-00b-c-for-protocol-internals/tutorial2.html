Module 00b — Deep Theory: Memory, Layout, and Undefined Behavior

1. The Stack Frame, Precisely

Every function call in C allocates a "stack frame" — a region of the call stack holding that function's local variables, saved registers, and bookkeeping needed to return control to the caller. A simplified layout (exact details vary by architecture/compiler, but the CONCEPT is universal):

Higher addresses
  +------------------------+
  | caller's frame...      |
  +------------------------+
  | return address         |  <- where execution resumes after this function returns
  +------------------------+
  | saved frame pointer     |  <- caller's frame pointer, saved so it can be restored
  +------------------------+
  | [stack canary]          |  <- if stack protection is enabled (buffer_overflow_demo.c)
  +------------------------+
  | local variables...      |  <- small_buffer, adjacent_guard, etc.
  +------------------------+
Lower addresses (stack grows DOWNWARD on most architectures)

This is exactly why a buffer overflow is dangerous beyond just corrupting a neighboring variable: on most architectures, the stack grows toward LOWER addresses, but writing PAST the end of a buffer moves toward HIGHER addresses — directly toward the saved frame pointer and, beyond that, the RETURN ADDRESS. This is why overflow_unprotected eventually segfaulted: the 20-byte write into an 8-byte buffer went far enough to corrupt not just adjacent_guard but the function's own return address, so when vulnerable_copy() tried to return, the CPU jumped to a garbage (attacker-influenced, in a real attack) address instead of back into main().

Comprehensive exam framing: "Explain, at the memory layout level, why a stack buffer overflow can lead to arbitrary code execution, not just data corruption." Answer: because the return address — the value that determines where the CPU resumes execution after the current function returns — is typically stored on the stack, ABOVE (at a higher address than) local buffers. An overflow large enough to reach that far can overwrite the return address with an attacker-chosen value, causing the CPU to jump to and execute code at that address when the function returns — this is the actual mechanism behind classic "stack smashing" exploits, though this module's demo deliberately stops at OBSERVING corruption, not weaponizing it.

Why GCC's stack protector reorders variables (not just adds a canary)

A canary alone (a secret value placed between locals and the return address, checked before returning) would catch return-address corruption — but it does nothing to protect a scalar local variable that happens to sit BETWEEN a buffer and the canary. GCC's -fstack-protector (the default in modern GCC/Clang builds) additionally reorders locals so that arrays/buffers are placed at HIGHER addresses within the frame, closer to the canary, and scalar variables are placed at LOWER addresses, farther from any buffer that could overflow into them. This is exactly why adjacent_guard stayed 0x1234 in the protected build — the compiler moved it out of the overflow's path, confirmed empirically during this module's own testing.

2. Endianness, Formally (and Why Module 02's htons() Exists)

A multi-byte value (say, the 16-bit number 0x1234) can be stored in memory two ways:

OrderByte at lower addressByte at higher addressUsed by
Big-endian ("network byte order")0x12 (most significant)0x34 (least significant)Every multi-byte network protocol field (IP addresses, ports, TCP sequence numbers)
Little-endian0x34 (least significant)0x12 (most significant)x86/x86-64 CPUs' native in-memory integer representation

This mismatch — most desktop/server CPUs are little-endian internally, but every network protocol specifies big-endian on the wire — is EXACTLY why htons()/htonl() ("host to network, short/long") exist: they convert a value from whatever the CPU's native byte order is to the byte order the network expects, and are no-ops on a big-endian machine (rare today, but the functions exist to make code portable regardless). Module 02's Python code used struct.pack("!H", ...) — the ! character means "network byte order," doing the exact same conversion Python's way.

Brain power: if you forgot to call htons() before writing a 16-bit port number into a packet header on a little-endian machine, what would actually happen? The two bytes would be written in the WRONG order — port 8080 (0x1F90) would be sent as bytes 90 1f instead of the correct 1f 90. The receiving end (following the network-byte-order convention) would interpret this as port 0x901F = 36895, a completely different, wrong port. This is a real, common bug class in raw network programming — and exactly why every protocol header field in this course's Python code used explicit byte-order format characters (!, >) rather than relying on defaults.

3. Undefined Behavior: C's Sharpest Edge

buffer_overflow_demo.c's strcpy() overflow is not just "a bug" in the way a Python IndexError is a bug — it is undefined behavior, a specific, formal category in the C standard meaning: once this happens, the C standard places ABSOLUTELY NO CONSTRAINTS on what the program does next. Not "it will crash." Not "it will corrupt adjacent memory in a predictable way." The standard permits literally any outcome, including ones that look completely fine until they don't (this is why UB bugs are notoriously hard to track down — a program with UB can appear to work correctly for months, then fail mysteriously after an unrelated compiler upgrade or optimization flag change, because the compiler was always free to assume UB never happens and optimize accordingly).

Why does C allow this at all, rather than mandating safe, defined behavior for every operation? Performance and historical context. C was designed in the early 1970s to be a thin abstraction over the hardware, for writing an operating system (Unix) that needed direct, fast, unencumbered access to memory. Every bounds check, every safety guarantee, costs CPU cycles. C's design philosophy trusts the programmer completely and pays zero runtime cost for that trust — which is exactly why kernels, embedded systems, and performance-critical networking code are still frequently written in C (or C++, or increasingly Rust, which provides memory safety WITHOUT C's runtime-cost tradeoff, via compile-time ownership checking) despite the well-known danger.

4. Struct Padding and Alignment, Beyond `packed`

Without __attribute__((packed)), here's what the compiler does and why. Consider:

struct example {
    uint8_t  a;   /* 1 byte */
    uint32_t b;   /* 4 bytes -- but wants to start at an address divisible by 4 */
};

The compiler inserts 3 padding bytes after a so that b starts at offset 4 (not offset 1), because most CPU architectures read a 4-byte value fastest — sometimes require it entirely — when that value starts at an address divisible by its own size (its "natural alignment"). sizeof(struct example) without packed would report 8, not 5, because of this invisible padding. This is precisely the mismatch that would silently corrupt every protocol header this course builds if packed were omitted — the compiler's "helpful" default optimization actively works against a fixed wire-format specification.
