Module 00b — Exam Practice

Answer out loud before revealing each answer.
Q1. Why does __attribute__((packed)) matter for a struct representing a network protocol header, but not for most ordinary C structs?
A: Without it, the compiler inserts padding bytes between fields to align each one to its natural alignment boundary (e.g., a 4-byte int starting at an address divisible by 4), for CPU read performance. A network protocol's wire format is a FIXED byte layout defined by a specification, with no room for compiler-inserted padding — using an unpacked struct to represent it would produce a struct whose `sizeof()` doesn't match the real wire format, and whose fields land at the wrong byte offsets entirely.
Q2. Explain array indexing (arr[i]) in terms of pointer arithmetic. What does the compiler actually do when it sees arr[i]?
A: `arr[i]` is defined to be exactly equivalent to `*(arr + i)` — take the array's base address, add i times the size of one element (pointer arithmetic automatically scales by the pointed-to type's size), then dereference the resulting address. This is why `sizeof(int)` mattered in `pointers_and_memory.c`'s demo: `&numbers[1]` was exactly 4 bytes after `&numbers[0]` because each `int` is 4 bytes, and the compiler multiplied the index by that size automatically.
Q3. What specifically does htons() do, and why is it a no-op on some machines but not others?
A: htons() ("host to network, short") converts a 16-bit value from the host machine's native byte order to network byte order (big-endian), which every multi-byte network protocol field uses on the wire. It's a no-op on a big-endian machine (host order already matches network order) but actually swaps bytes on a little-endian machine (most x86/x86-64 systems) — the function exists specifically so the same source code produces correct behavior regardless of the host CPU's native endianness.
Q4. A colleague forgets to call htons() before writing a port number into a raw packet's header on a little-endian machine. What specifically goes wrong?
A: The two bytes of the port number get written in the CPU's native (little-endian) order instead of network (big-endian) order -- effectively byte-swapped relative to what the wire format requires. Port 8080 (0x1F90) would be transmitted as bytes 0x90 0x1F instead of the correct 0x1F 0x90, and any receiver correctly following network byte order would interpret this as an entirely different port number (0x901F = 36895), not raise an obvious error.
Q5. Define "undefined behavior" as the C standard uses the term. Why is it a stronger, scarier concept than "this specific operation crashes"?
A: Undefined behavior means the C standard places NO constraints whatsoever on program behavior once it occurs -- not "it crashes," not "it produces a predictable wrong value," but literally anything, including appearing to work correctly. This is scarier than a guaranteed crash because a program with UB can pass all its tests for months and then fail unpredictably after a seemingly unrelated change (different compiler version, different optimization level, different surrounding code) -- the compiler is legally permitted to assume UB never happens and optimize on that assumption, which can make UB-triggering code behave inconsistently across builds.
Q6. In buffer_overflow_demo.c's PROTECTED build, adjacent_guard stayed unchanged even though the program still detected corruption and aborted. Explain exactly why, mechanically.
A: GCC's stack protector (-fstack-protector, on by default in modern GCC) does two things, not one: it inserts a secret canary value between local buffers and the return address, checked before the function returns; AND it reorders local variables within the stack frame so that arrays/buffers are placed closer to the canary and scalar variables are placed farther away, specifically to reduce the chance that overflowing a buffer corrupts a scalar variable the program still trusts. In this build, `adjacent_guard` was moved to a stack position the overflow's 20 bytes never reached, while the hidden canary (which WAS in the overflow's path) got corrupted and triggered the "stack smashing detected" abort.
Q7. Explain, at the memory layout level, why a large enough stack buffer overflow can corrupt a function's RETURN ADDRESS, and why that specifically matters more than corrupting an ordinary local variable.
A: On most architectures, the stack grows toward lower addresses as new frames are pushed, but writing past the end of a buffer (via an unbounded copy like strcpy) proceeds toward HIGHER addresses -- directly toward the saved frame pointer and the return address, which are typically stored above local variables in the current frame. If the overflow is large enough to reach the return address and overwrite it with an attacker-chosen value, the CPU will jump to that address when the function returns -- turning a data-corruption bug into a control-flow hijack, which is qualitatively more dangerous than corrupting a local variable the program merely reads.
Q8. Why does Node's Buffer.write() silently truncate an oversized write while Uint8Array.set() throws a RangeError -- and why are BOTH considered "memory safe" despite behaving differently from each other?
A: Both APIs internally track the allocated buffer's exact size and check every write against it -- they simply chose different responses to an out-of-bounds attempt (silent truncation vs. a catchable exception), which is a design/API choice, not a safety difference. Both are "memory safe" in the sense that matters: neither one EVER allows a write to proceed past the buffer's actual allocated bounds into unrelated memory, which is the specific guarantee C's strcpy() does not provide at all.
Q9. Why is C still used for kernels, embedded systems, and performance-critical networking code despite memory-safety risks that languages like Python, JS, and Rust don't share?
A: C provides a thin, low-overhead abstraction directly over hardware, with no runtime cost paid for safety checks it doesn't perform -- every bounds check, garbage collection pause, or ownership verification a safer language performs costs real CPU cycles and/or memory. For code where performance and direct hardware/memory control are critical (kernels, device drivers, high-throughput networking stacks), this tradeoff has historically been considered worth the safety risk, though languages like Rust increasingly offer a genuine third option: compile-time-enforced memory safety with comparable runtime performance, without C's runtime-cost tradeoff or its safety gaps.
Q10. Synthesis: connect this module's buffer overflow demo to Module 16's vulnerability assessment work. What class of real-world CVE does this module's bug directly explain the mechanism behind?
A: Memory corruption CVEs -- a large fraction of historically severe, remotely-exploitable vulnerabilities (including ones in network-facing services parsing untrusted protocol data) are fundamentally buffer overflows or related memory-safety bugs (use-after-free, out-of-bounds read/write) in C/C++ code, following exactly the mechanism this module demonstrated: an unbounded copy operation writing attacker-influenced data past a buffer's intended boundary, corrupting adjacent memory -- in the worst case, including a saved return address, enabling remote code execution. Module 16's vulnerability database entries (like the vsftpd 2.3.4 backdoor, which is actually a deliberately-planted backdoor rather than a memory-safety bug, worth distinguishing) sit alongside a much larger historical category of genuine memory-corruption CVEs that trace directly back to this module's core lesson.
