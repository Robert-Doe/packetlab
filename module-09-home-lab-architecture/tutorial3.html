Module 09 — Exam Practice

Answer out loud before revealing each answer.
Q1. Explain precisely why a hypervisor's "Internal Network" mode provides structurally stronger isolation than relying on a firewall rule alone on a bridged network.
A: An Internal Network is isolated at the virtual switching layer -- there is simply no path for traffic to leave that network to anywhere outside the VMs explicitly attached to it, regardless of any firewall rule's presence, absence, or misconfiguration. A bridged network places the VM on the same broadcast domain as the real host network, with isolation depending ENTIRELY on a firewall rule being correctly present and correctly configured -- a policy decision that could fail, versus a structural property that has nothing to misconfigure into a leak.
Q2. What does a hypervisor's NAT network mode do, and why is it safe to use for a lab's simulated WAN without exposing anything to the real internet?
A: It gives attached VMs outbound internet access by routing their traffic through the host's own connection, with the hypervisor performing NAT to translate VM-internal addresses for outbound traffic. It does NOT allow unsolicited inbound connections from the internet to reach the VM by default -- the same "unsolicited inbound gets dropped" property real home routers exhibit (Module 10) -- which is exactly why it's safe to use as a simulated WAN: outbound lab traffic works normally, but nothing external can reach into the lab unprompted.
Q3. Why did this module choose pfSense/OPNsense (BSD-based, built on pf) rather than assembling firewall/router functionality from a general-purpose Linux install with iptables?
A: pfSense/OPNsense provide a maintained, purpose-built distribution with a proper web admin UI, an installable package ecosystem (VPN, IDS/IPS, DNS server packages), and firewall logic (BSD's pf) that is mature, widely-deployed, and professionally audited across many production and educational environments. Hand-assembling equivalent functionality from a general Linux install with raw iptables rules is possible but more error-prone and lacks the same level of scrutiny and tooling maturity -- a meaningful difference for a security-focused education specifically trying to build correct intuitions.
Q4. Explain the "asymmetric trust" / "least privilege applied directionally" pattern using this module's own Main/Lab firewall rule as the example, and name one other real-world architecture that uses the identical underlying principle.
A: Each zone is granted only the minimum access it needs for its actual purpose, with nothing granted symmetrically by default -- Main can reach Lab (administering it is a legitimate, needed action) but Lab cannot reach Main (a compromised lab VM shouldn't be able to reach trusted devices). The identical underlying principle appears in DMZ (demilitarized zone) enterprise network architecture: a public-facing web server zone can be reached from the internet, but that zone itself cannot freely reach the internal corporate network -- the same directional, minimum-necessary-access logic applied to a different specific pair of zones.
Q5. Why does this module recommend building the virtual lab BEFORE attempting the optional production bridge-mode path, beyond general caution?
A: Learning pfSense/OPNsense's interface, VLAN configuration, and firewall rule syntax and learning to safely reconfigure a household's actual internet gateway are two genuinely separate skills. The virtual lab lets a student fail at the first skill (misconfigure a rule, break a VM's networking, even reinstall the firewall entirely) as many times as needed, for free, with zero real-world consequence. By the time a student would even consider the production path, the remaining risk is isolated to "am I confident in my own configuration" rather than simultaneously learning the tool AND risking the household's internet in the same attempt.
Q6. Synthesis: connect this module's Internal Network isolation to Module 03's VLAN isolation. What's genuinely the same, and what's genuinely different?
A: Genuinely the same: both create separate broadcast domains where traffic simply has no path to cross the boundary by default -- Module 03's VLAN tags control which switch ports a flood reaches; a hypervisor's Internal Network controls which VMs a virtual switch's traffic reaches, the identical underlying concept at a different layer of virtualization. Genuinely different: Module 03's VLANs still require a router/Layer-3 device to move traffic BETWEEN VLANs when desired (with firewall rules then governing that crossing); a hypervisor's Internal Network requires a VM (like pfSense) attached to multiple networks simultaneously to bridge them at all -- the mechanism achieving isolation is analogous, but implemented at different architectural layers (physical/virtual switch tagging vs. hypervisor virtual network membership).
