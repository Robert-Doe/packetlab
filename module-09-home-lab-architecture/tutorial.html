Module 09 — Tutorial

Goal: design a real segmentation plan for your actual home network, then implement it in a risk-free virtual lab first. Read home_lab_design.md in full before starting.

This module is different from every one before it. Modules 01-08 ran entirely in a sandbox — a mistake cost you a restart. This module's optional production path (cox_bridge_mode_guide.md) touches your household's actual internet connection. Do the virtual lab first. Don't attempt the production path unless you specifically want your home network restructured, and only after you've read the safety notes in that file in full.

Step 1 — generate your real segmentation plan

cd module-09-home-lab-architecture
python lab_plan_generator.py 192.168.0.0/24

Replace 192.168.0.0/24 with your own real home subnet if different — check Module 01's dashboard output if you don't remember it.

Expected: a 3-VLAN plan (Main, IoT/Guest, Lab) sized to the host counts hardcoded in the script (20/30/10 — edit these in main() to match your actual device count), plus a firewall rule outline expressing the isolation goals from home_lab_design.md. Confirm none of the three CIDR blocks overlap — this is the same VLSM packing logic from Module 04, applied to a plan you might actually use.

Step 2 — build the virtual lab

Follow virtual_lab_setup_guide.md completely. This is entirely contained inside your hypervisor — no risk to your real network at any point.

Expected outcome: a working pfSense/OPNsense VM with 3 virtual networks attached, a client VM on the "Main" network that can reach the internet through the firewall's NAT, and at least one firewall rule you wrote yourself (blocking Lab → Main, per Step 1's plan) that you've verified works by trying to ping across it.

Step 3 — verify the isolation rule the way Module 03 taught you to think about it

From a client VM on your "Lab" virtual network, try to ping a client on "Main." It should fail. From "Main," ping "Lab" (if you allowed that direction) — it should succeed. This is the exact same broadcast-domain isolation concept `switch_sim.py` demonstrated in software back in Module 03 — except now a real (if virtual) firewall is the thing enforcing it, with actual stateful rule evaluation instead of just VLAN-tag flood-avoidance.

Step 4 (optional, advanced) — production bridge mode

Only if you want to: read cox_bridge_mode_guide.md in full, in particular the "before you start" checklist, before touching your Cox gateway's admin page.

Exercises before Module 10

  1. Resize the plan for your real device count. Count your actual devices per category (personal, IoT/guest, lab) and edit lab_plan_generator.py's segments list to match. Re-run and confirm the block sizes make sense.
  2. Add a 4th segment. Many households want a separate "Cameras/NVR" VLAN, isolated even from IoT/Guest. Add it to both the Python and JS generator and update the firewall rule outline logic to include it in the IoT/Guest-style full isolation loop.
  3. Write the actual pfSense rules. Take Step 1's firewall rule outline and translate each ALLOW/BLOCK line into an actual pfSense "Firewall → Rules" entry on your virtual lab's Lab and IoT/Guest interfaces. Confirm with a real ping test that each rule does what its outline comment says.
Before Module 10: you should have a working virtual lab with at least 2 isolated network segments and one enforced firewall rule between them. Module 10 goes deeper into exactly how that firewall makes its allow/block decisions — NAT and stateful filtering, traced packet by packet the way Module 05 traced routing decisions.
