Module 18 — Deep Theory: The libpcap File Format and Forensic Reconstruction, From Zero

1. Command-by-Command

python pcap_writer.py

What it does: constructs a real, standards-conformant .pcap file byte-by-byte — first a 24-byte GLOBAL HEADER, then one PACKET RECORD per captured frame, each consisting of its own small header followed by the raw Ethernet frame bytes. Nothing here calls an actual capture library — the "capture" is entirely synthetic, built the same way Module 02's layer_builder.py built raw frames by hand with struct.pack, just written to disk in the exact binary layout Wireshark itself expects.

file incident.pcap

What it does: the Unix/Linux file utility inspects a file's leading bytes (its "magic number") against a database of known formats and reports what it recognizes — entirely independent of anything in this course. That it correctly identifies incident.pcap as a genuine pcap capture file is external, disinterested proof the hand-written binary format is actually correct, not merely "close enough that this course's own reader accepts it."

python pcap_reader.py incident.pcap

What it does: the REVERSE of the writer — opens the file, parses the 24-byte global header first (confirming the magic number and extracting the byte-order/timestamp-precision settings it declares), then loops reading one packet record header (16 bytes) plus that record's declared number of captured bytes, repeating until EOF.

python incident_timeline.py incident.pcap

What it does: applies Module 14's detection logic (port-scan pattern matching, large-transfer/exfiltration pattern matching) RETROSPECTIVELY to a static, already-complete capture file, rather than to a live stream — the exact same statistical reasoning, applied after the fact instead of in real time. This is precisely what distinguishes forensics (reconstructing what already happened from surviving evidence) from monitoring (detecting what's happening now).

2. The libpcap Global Header, Byte by Byte

Every valid .pcap file begins with exactly this 24-byte structure:

BytesFieldPurpose
0–3Magic number0xa1b2c3d4 (or its byte-swapped form 0xd4c3b2a1) — this single field is BOTH a format signature AND a self-describing byte-order flag: a reader that sees the swapped value knows the whole file was written on a machine with the opposite endianness and must byte-swap every subsequent multi-byte field
4–5Major versionFormat version, currently 2
6–7Minor versionFormat version, currently 4
8–11Reserved (timezone, historically)Effectively always 0 in modern captures
12–15Reserved (timestamp accuracy, historically)Effectively always 0 in modern captures
16–19SnaplenMaximum number of bytes captured per packet (65535 here — "capture everything," per Step 1's own `file` output)
20–23Link-layer typeWhat kind of frame follows each packet record — 1 means Ethernet, the same numbering scheme this module's writer declares explicitly
Why encode byte order via a magic-number self-check, rather than a separate explicit "byte order" field? A dedicated byte-order field would ITSELF need to be read correctly before you'd know how to interpret it — a chicken-and-egg problem. Using the magic number double-duty (a fixed, known value that LOOKS different depending on which byte order produced it) sidesteps this entirely: a reader tries interpreting the first 4 bytes as-is, and if they don't match 0xa1b2c3d4, tries the byte-swapped interpretation instead — whichever matches tells the reader definitively which byte order the rest of the file uses, with no additional field needed.

3. The Packet Record Format

After the global header, each captured packet is stored as its own 16-byte record header followed by the raw captured bytes:

BytesFieldPurpose
0–3Timestamp (seconds)Unix epoch seconds when this packet was captured
4–7Timestamp (microseconds)Sub-second precision — this is exactly the field whose Python int()-truncation vs. JS Math.round() rounding mismatch caused this module's cross-language byte-mismatch bug, fixed by aligning both languages to the same rounding rule
8–11Captured lengthHow many bytes of this packet were ACTUALLY stored (may be less than the original frame if snaplen truncated it)
12–15Original lengthHow large the frame actually was on the wire, even if truncated
Brain power: why store BOTH a captured length and an original length, rather than just one "length" field? These can legitimately differ: a capture tool configured with a small snaplen (say, only the first 96 bytes of each packet, common when you only care about headers, not payload, to save disk space) stores fewer bytes than the packet actually contained on the wire. Preserving the ORIGINAL length even when truncated lets later analysis still report accurate statistics (real payload sizes, real total traffic volume) even though the payload bytes themselves aren't available for deeper inspection.

4. Forensic Reconstruction as a Reasoning Process

incident_timeline.py's 3-finding output is not magic — it is the same evidence-to-conclusion reasoning any incident responder performs manually, automated: cluster the reconnaissance SYNs by (a) common source, (b) tight time window, (c) many distinct destination ports — Module 14's own port-scan signature, applied to already-captured packets. Find the payload matching a known exploit trigger string (Module 16's CVE-2011-2523 signature) to mark the transition from reconnaissance to active exploitation. Find a sustained, high-volume transfer to a THIRD-PARTY address (not the original two hosts) to mark exfiltration. The chronological ORDER of these three findings is itself part of the evidence — reconnaissance must precede exploitation must precede exfiltration for the narrative to be coherent, and a forensic report should say so explicitly.
