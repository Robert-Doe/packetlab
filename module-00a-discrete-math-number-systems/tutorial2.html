Module 00a — Deep Theory: Number Systems, Boolean Algebra, and Modular Arithmetic

This chapter goes past "run the script and see it work." It's the material a comprehensive exam committee could reasonably expect you to derive from first principles, not just recognize. Read it slowly. Every section ties to a specific later module — that connection is the point, not decoration.

1. Positional Number Systems, Formally

A positional (or "place-value") number system represents a quantity as a sequence of digits, where each digit's contribution to the total value depends on its POSITION, not just its face value. Formally, for a number written as digits d_{n-1} d_{n-2} ... d_1 d_0 in base b:

value = Σ (d_i × b^i)   for i = 0 to n-1

This single formula IS decimal, binary, octal, and hexadecimal — the only thing that changes between them is b (10, 2, 8, 16 respectively) and which digit symbols are valid (decimal: 0-9; binary: 0-1; octal: 0-7; hex: 0-9 then a-f for 10-15).

Why base 2 specifically, for computers

Not an arbitrary choice: a transistor (or any binary switch) reliably distinguishes exactly two states (on/off, high-voltage/low-voltage) far more cheaply and reliably than it could distinguish ten distinct voltage levels for a decimal computer. Binary isn't "the computer's number system by convention" — it's the number system that matches the physical reality of the hardware most directly.

Why base 16 specifically, for humans reading binary

Because 16 = 2⁴, exactly. This is the entire reason hex exists as a convenience layer: converting between binary and hex requires ZERO arithmetic — you can do it by pure lookup, because every possible 4-bit pattern maps to exactly one of 16 hex digits with no remainder ever left over. Octal (base 8 = 2³) has the same clean property with 3-bit groups, which is why octal shows up in Unix file permissions (Module 00c) — three permission bits (read/write/execute) per group, three groups (owner/group/other), and octal represents each group as one digit with zero arithmetic.

2. Two's Complement: How Computers Represent Negative Numbers

Straight binary (as covered above) only represents non-negative integers. Real systems — including every C int you'll write in Module 00b, and every signed field in a protocol header — need negative numbers too. The near-universal solution is two's complement:

To negate a number in two's complement:
  1. Flip every bit (this alone is called "one's complement")
  2. Add 1

Example, 8-bit: negate 5 (00000101)
  Flip:  11111010
  Add 1: 11111011   <- this is -5, in 8-bit two's complement
Why two's complement instead of "just use a sign bit"? A naive "sign-magnitude" scheme (leftmost bit = sign, rest = magnitude) has a serious flaw: it produces TWO representations of zero (00000000 and 10000000), which complicates hardware and software that has to special-case both. Two's complement has exactly ONE representation of zero, and — critically — addition and subtraction work IDENTICALLY for signed and unsigned numbers using the exact same adder circuit, with overflow simply wrapping around (modular arithmetic again!). This is why C's int and Python's internal representations (before Python's arbitrary-precision promotion) use two's complement — it's not a convention, it's what makes hardware arithmetic units simple and uniform.
Brain power: Module 07's tcp_state_machine.py and Module 18's forensics work both deal with TCP sequence numbers, which are UNSIGNED 32-bit fields that wrap modulo 2³². Why does TCP use unsigned wraparound (Module 00a's modular arithmetic) rather than two's-complement signed representation for sequence numbers? Because a sequence number has no meaningful concept of "negative" — it's a monotonically increasing counter of bytes sent, and when it wraps past 2³²-1 back to 0, that's not an error condition to detect (the way signed integer overflow often is in C) — it's expected, routine behavior TCP's comparison logic is specifically designed to handle correctly (using modular "distance" comparisons, not naive greater-than checks).

De Morgan's Laws

NOT (A AND B)  =  (NOT A) OR (NOT B)
NOT (A OR B)   =  (NOT A) AND (NOT B)

This isn't just a symbolic manipulation rule — it's the reason firewall rule logic ("block everything EXCEPT these ports" vs. "allow only these ports") are related-but-distinct framings of the same underlying set, and it's directly useful for simplifying complex Suricata/Snort rule conditions (Module 14) or firewall ACLs (Module 10) into their clearest form.

NAND and NOR are "functionally complete"

A fact worth knowing for exam purposes: EVERY boolean function — no matter how complex — can be built from NAND gates alone (or NOR gates alone). This is why real CPU hardware is often built predominantly from NAND gates: you don't need separate physical AND, OR, and NOT circuits if you can compose all of them from one universal building block. This isn't directly used elsewhere in this course, but it's a classic comprehensive-exam "do you actually understand digital logic, or just use it" question.

4. Modular Arithmetic: The Formal Structure Cryptography Depends On

Definition

a ≡ b (mod n) means a and b leave the same remainder when divided by n — equivalently, n evenly divides (a - b). This defines an equivalence relation that partitions all integers into exactly n "residue classes" (in mod 12 clock arithmetic, every integer belongs to one of 12 classes: {..., -12, 0, 12, 24, ...}, {..., -11, 1, 13, 25, ...}, and so on).

Properties that make modular arithmetic usable for cryptography

  • Closure under addition/multiplication: (a mod n) + (b mod n) ≡ (a + b) mod n, and similarly for multiplication. This is WHY mod_exp() can take the modulus at every intermediate step instead of only at the end — the result is mathematically guaranteed identical either way, but taking the modulus early keeps every intermediate number small.
  • Modular inverse: for some pairs (a, n), there exists a number a⁻¹ such that a × a⁻¹ ≡ 1 (mod n) — the modular equivalent of division. This exists if and only if gcd(a, n) = 1 (a and n share no common factors). Computing modular inverses (via the Extended Euclidean Algorithm) is a required step in RSA key generation (Module 13's territory) — the decryption exponent d is literally defined as the modular inverse of the encryption exponent e, modulo φ(n).

Fermat's Little Theorem (why RSA's math actually works)

If p is prime and a is not divisible by p, then:  a^(p-1) ≡ 1 (mod p)

This single theorem (and its generalization, Euler's theorem, for composite moduli) is the mathematical bedrock RSA's correctness proof rests on. You don't need to reproduce the full RSA correctness proof for most exam contexts, but you SHOULD be able to state that RSA's security and correctness both trace back to properties of modular exponentiation over numbers built from large primes — which is exactly what mod_exp() computes, just at toy scale.

Comprehensive exam framing: "Why can't you just compute base ** exponent directly and then take the modulus, for real cryptographic key sizes?" Answer: for a 2048-bit RSA exponent, the un-reduced power would be a number with roughly 10^600 digits — more digits than atoms in the observable universe. `mod_exp()`'s square-and-multiply approach keeps every intermediate value bounded to roughly the size of the modulus itself (a few thousand bits), which is the ONLY reason modular exponentiation at cryptographic scale is computationally feasible at all. This is a complexity argument (O(log n) modular multiplications instead of computing an astronomically large intermediate number) as much as a cryptography one.

5. Diffie-Hellman, Properly: The Discrete Logarithm Problem

modular_arithmetic.py's demo works because of one specific computational asymmetry: given g, p, and a, computing g^a mod p is fast (via square-and-multiply). But given g, p, and g^a mod p, recovering a — the "discrete logarithm" — is believed to be computationally infeasible for large enough p, with no known efficient (polynomial-time) algorithm on classical computers.

Brain power: notice the word "believed." Unlike some mathematical facts, the hardness of the discrete logarithm problem is NOT proven — it's an open conjecture, supported by decades of failed attempts to find an efficient algorithm, not a mathematical proof of impossibility. This is true of essentially every widely-deployed public-key cryptosystem (RSA's security rests on the believed hardness of integer factorization; ECDH rests on the believed hardness of the elliptic curve discrete log problem). A comprehensive exam question like "is RSA provably secure?" has a precise correct answer: no — its security is CONJECTURED, based on the best known attacks being infeasible, not on a mathematical impossibility proof. (This is also exactly why quantum computers running Shor's algorithm are a genuine threat to RSA/DH/ECDH specifically — Shor's algorithm efficiently solves both factoring and discrete log on a sufficiently large quantum computer, which is why "post-quantum cryptography" is an active research area building on DIFFERENT hard problems believed to resist quantum attack.)

The vulnerability raw Diffie-Hellman does NOT solve: authentication

diffie_hellman_demo() proves two parties can agree on a shared secret without transmitting it — but it proves NOTHING about who those two parties actually are. A man-in-the-middle attacker who can intercept and modify traffic between Alice and Bob can run a SEPARATE DH exchange with each of them, ending up with two different shared secrets (one with "Alice," one with "Bob") while both endpoints believe they're talking directly to each other. This is precisely why real-world protocols never use raw, unauthenticated DH — TLS (Module 13) combines a DH-family key exchange WITH certificate-based authentication (the server proves its identity via a certificate chain) specifically to close this gap. Raw DH solves confidentiality of the key exchange; it does nothing for authentication, which is a separate problem requiring a separate mechanism (PKI, Module 13).

6. XOR, Checksums, and Error Detection (a preview of Module 02's checksum16)

Module 02's checksum16() function sums 16-bit words with carry-wraparound and complements the result. This is a member of a broader family of error-detection techniques built on the algebra of GF(2) — the "Galois Field" of two elements, where addition IS XOR (no carry) and every element is its own additive inverse. CRC (Cyclic Redundancy Check), used in Ethernet's frame check sequence, is a more sophisticated member of this same family: it treats the message as coefficients of a polynomial over GF(2) and computes a remainder after polynomial division by a fixed "generator polynomial." You won't need to implement CRC in this course, but you should be able to state, at an exam level, that checksums and CRCs are fundamentally applications of modular arithmetic and XOR-based algebra to the problem of detecting (not correcting) transmission errors — and that they detect ACCIDENTAL corruption reliably but provide no protection against a deliberate, intelligent attacker who can recompute a valid checksum for tampered data (which is exactly why cryptographic integrity — HMAC, Module 12's PMK/PTK work — is a fundamentally different, stronger guarantee than a checksum).
